# 2편. 사람이 먼저 채점한다

> 시리즈: AI 답변을 채점하는 법 — LLM-as-a-Judge 밑바닥부터
> 이 편에서 배우는 것: judge를 만들기 전에 왜 사람 라벨이 먼저 있어야 하는지, 5점 척도 대신 PASS/FAIL을 쓰는 이유, 채점자는 몇 명이어야 하는지, 그리고 채점하다 보면 기준이 저절로 바뀌는 현상(criteria drift)에 대처하는 법.

이 편은 이 시리즈에서 가장 지루하고, 가장 건너뛰고 싶고, **가장 중요한** 편입니다.

## 왜 사람이 먼저인가

judge를 만들면 자동으로 채점이 됩니다. 그럼 사람이 채점할 필요가 없어 보이죠. 그런데 순서가 반대입니다.

```
사람 라벨이 없으면  →  judge가 맞는지 틀리는지 알 수 없음
                    →  틀린 judge로 프롬프트를 튜닝
                    →  점수는 오르는데 제품은 안 좋아짐
```

**자를 만들지 않고 길이를 재는 것**과 같습니다. 눈금이 이상한 자로 아무리 정밀하게 재봐야 소용이 없죠.

그래서 사람 라벨의 역할은 이렇습니다.

> **사람 라벨 = judge를 검증하는 정답지**
>
> 챗봇을 채점하는 건 judge가 하고, **judge를 채점하는 건 사람**입니다.

한 가지 더. 사람이 직접 대화를 읽는 과정 자체가 엄청난 가치를 만듭니다. 로그를 50개만 읽어봐도 "아, 우리 챗봇이 여기서 이렇게 망가지는구나"가 보입니다. **그 발견이 rubric의 원재료가 됩니다.** 이 과정을 건너뛰고 상상으로 rubric을 쓰면, 현실에 없는 문제를 잡는 기준표가 나옵니다.

## 라벨을 어떻게 설계할 것인가

### 5점 척도의 유혹

처음에는 이렇게 하고 싶어집니다.

```
1점 — 아주 나쁨
2점 — 나쁨
3점 — 보통
4점 — 좋음
5점 — 아주 좋음
```

정보가 많아 보이니까요. 그런데 실제로 해보면 무너집니다.

**첫째, 사람도 일관성이 없습니다.** 같은 답변을 월요일에는 4점, 금요일에는 3점 줍니다. 특히 3점과 4점의 경계는 아무도 설명하지 못합니다.

**둘째, LLM은 더 심합니다.** judge에게 1~5점을 매기라고 하면 대부분 3점과 4점에 몰립니다. 극단을 피하는 성향이 있어서, 정작 우리가 궁금한 "좋다/나쁘다"의 구분이 흐려집니다.

**셋째, 점수를 어떻게 쓸지가 애매합니다.** 평균 3.7점이 3.9점으로 올랐다면 좋아진 걸까요? 0.2점이 무슨 의미인지 아무도 모릅니다.

### 그래서 이진에 가깝게

실무에서 가장 잘 작동하는 건 이겁니다.

```
PASS      — 이 답변으로 고객에게 나가도 괜찮다
FAIL      — 나가면 안 된다
UNCLEAR   — 판단이 안 선다 (선택)
```

**"고객에게 나가도 되는가"** 라는 기준이 좋은 이유는, 실제 의사결정과 직결되기 때문입니다. 3.7점이냐 3.9점이냐는 아무 결정도 못 내리지만, "이대로 나가면 안 됨"은 즉시 행동으로 이어집니다.

`UNCLEAR`를 둘지는 취향입니다. 두면 애매한 걸 억지로 밀어넣지 않아도 되지만, 남용하면 라벨이 안 모입니다. **전체의 10%를 넘으면 기준이 흐릿하다는 신호**로 보세요.

### "나쁨"에서 멈추지 마세요

여기가 실무에서 가장 큰 차이를 만드는 부분입니다. `FAIL`을 눌렀으면 **"그럼 뭐라고 답했어야 하는가"를 같이 적게 하세요.**

```
[케이스 0042]
고객:   어제 주문한 거 아직도 안 왔어요
콩돌이: 주문번호를 알려주시면 확인해 드릴게요!

라벨:   FAIL
이상적: "확인해보니 어제 주문하신 예가체프가 오늘 오전 출고됐어요.
        내일 도착 예정입니다!"
이유:   로그인 고객인데 주문번호를 되물었음. 조회할 수 있는 정보를
        고객에게 시켰다.
```

"FAIL"만 있으면 무엇이 문제인지 나중에 알 수 없습니다. **이상적 답변과 이유가 있으면 세 가지로 쓸 수 있습니다.**

1. **rubric을 쓸 때의 재료** — "로그인 고객에게 주문번호를 되묻지 말 것"이라는 조항이 여기서 나옵니다
2. **챗봇 프롬프트를 고칠 때의 재료** — 아예 예시로 프롬프트에 박아넣을 수도 있습니다
3. **judge에게 줄 few-shot 예제** (3편에서 다룹니다)

**FAIL 케이스의 "이유"를 나중에 모아서 읽으면 패턴이 보입니다.** 50개 중 12개가 "되묻기 문제"라면, 그게 다음에 고칠 1순위입니다.

## 몇 개나 라벨링해야 하나

| 목적 | 필요한 라벨 수 |
|---|---|
| judge가 완전 헛소리인지만 확인 | 30~50 |
| **judge를 실제로 신뢰하고 쓰기** | **100~150** |
| judge를 세밀하게 튜닝 | 200+ |

**100~150개가 현실적인 목표**입니다. 4편에서 볼 통계적 이유가 있는데, 간단히 말하면 100개 미만에서는 일치율의 오차범위가 너무 커서 "80%인지 88%인지"를 구분할 수 없습니다.

시간으로 환산하면, 케이스 하나에 30초~1분 정도 걸리니 **100개면 1~2시간**입니다. 한 번 앉아서 끝낼 수 있는 분량이고, 실제로 **한 번에 몰아서 하는 게 좋습니다.** 이유는 곧 나옵니다.

## 채점자는 몇 명이어야 하나

직관적으로는 "여러 명이 매겨서 평균 내면 더 정확하겠지"입니다. 그런데 실무 문헌은 오히려 반대를 권합니다.

> **정답지는 한 명이 일관되게 만드는 게 낫다.**

여러 명이 매기면 각자의 기준이 섞여서 **평균은 흐릿해집니다.** "고객에게 나가도 되는가"의 기준은 제품의 방향성 문제이지 다수결로 정할 일이 아닙니다. 그래서 실무에서는 제품을 가장 잘 아는 한 사람(PM이든 시니어 엔지니어든)이 **"자애로운 독재자"** 역할로 기준을 잡습니다.

그럼 두 번째 사람은 아예 필요 없을까요? **다른 용도로 필요합니다.**

> **두 번째 사람은 라벨을 늘리려는 게 아니라, 이 문제가 얼마나 어려운지를 재려는 것입니다.**

두 사람이 같은 케이스 30개를 독립적으로 채점해서 일치율을 봅니다. 26개가 맞아서 87%가 나왔다면, 그 숫자가 **judge를 평가할 때의 기준점**이 됩니다.

```
사람 A vs 사람 B  →  87% 일치 (26/30)  ← 기준점
judge vs 사람 A   →  83% 일치          ← 사실상 사람 수준. 훌륭함.
judge vs 사람 A   →  63% 일치          ← 사람보다 한참 못함. 개선 여지 있음.
judge vs 사람 A   →  97% 일치          ← 좋은 신호일 수도, 아닐 수도. 아래 참고.
```

> **여기 쓴 87%는 날것 그대로의 일치율입니다.** 4편에서 이 숫자가 **한쪽 라벨이 많을수록 저절로 부풀려진다**는 걸 보게 되고, 그래서 우연을 걷어낸 **Cohen's kappa(κ)** 로 다시 계산합니다. 같은 30개가 4편·6편에서는 **κ = 0.68**로 등장하는데, 다른 데이터가 아니라 **같은 데이터를 다른 자로 잰 것**입니다. 지금은 "두 사람도 완벽히 같지는 않다"만 잡고 가면 됩니다.

> **"천장"이라는 표현을 쓰지 않은 이유**
>
> 흔히 사람끼리의 일치율을 judge의 상한선이라고 말하는데, **엄밀히는 수학적 상한이 아닙니다.** judge가 사람 A의 기준을 사람 B보다 더 잘 모사하는 것은 얼마든지 가능합니다 — A의 기준이 일관적이라면 judge가 그 패턴을 B보다 정확히 학습할 수 있으니까요.
>
> 다만 **실무에서는 기준점으로 쓰기 좋습니다.** judge가 사람끼리보다 훨씬 잘 맞는다면 축하하기 전에 두 가지를 확인하세요. 데이터가 너무 쉽거나(전부 명백한 FAIL), judge가 정답지를 미리 본 것(3편의 few-shot 누출)일 수 있습니다. 확인해서 문제가 없다면 진짜로 좋은 judge인 겁니다.

정리하면:

- **정답지 제작:** 한 명이 100~150개
- **기준점 측정:** 두 번째 사람이 그중 30개만 겹쳐서

## 채점하다 보면 기준이 바뀝니다

이건 논문으로도 확인된 현상입니다. Shankar 등이 2024년에 발표한 *"Who Validates the Validators?"* 에서 **criteria drift(기준 표류)** 라고 이름 붙였습니다.

무슨 일이 벌어지냐면 이렇습니다.

```
케이스 1~10:   "친절하면 PASS"
               (아직 뭘 봐야 할지 모름)

케이스 30~40:  "친절하기만 하고 정보가 없으면 FAIL"
               (같은 패턴을 여러 번 보고 나서 기준이 생김)

케이스 80~100: "정보가 있어도 고객이 두 번 묻게 만들면 FAIL"
               (기준이 더 정교해짐)
```

문제는 **케이스 1~10의 라벨이 옛날 기준으로 붙어 있다**는 겁니다. 정답지 안에 서로 다른 두 개의 자가 섞여 있는 셈이죠. 이 상태로 judge를 검증하면 일치율이 낮게 나오는데, judge가 못해서가 아니라 정답지가 흔들려서입니다.

**대처법 세 가지입니다.**

**하나, 기준을 적으면서 채점하세요.** 별도 메모장을 열어두고, 새로운 판단 기준이 생길 때마다 한 줄씩 적습니다.

```
[채점 기준 메모]
- 로그인 고객에게 주문번호 되묻기 → FAIL          (케이스 7에서 발견)
- 배송일을 "곧"이라고만 하면 → FAIL, 날짜 필요    (케이스 23에서 발견)
- 사과만 하고 해결책 없으면 → FAIL                (케이스 41에서 발견)
- 이모지 1~2개는 OK, 3개 이상은 감점              (케이스 55에서 발견)
```

이 메모가 나중에 **rubric의 초안이 됩니다.** 3편에서 그대로 씁니다.

**둘, 다 끝나고 처음 20개를 다시 보세요.** 기준이 완성된 상태로 재채점하면 몇 개는 바뀝니다. 15분이면 됩니다.

**셋, 한 번에 몰아서 하세요.** 며칠에 나눠 하면 그 사이에 기준이 더 표류합니다. 앞서 "한 번에 앉아서"라고 한 이유가 이것입니다.

> **기준을 미리 완벽하게 쓰고 시작하려 하지 마세요.** 실제 데이터를 보기 전에 쓴 기준은 현실과 안 맞습니다. **20~30개를 먼저 보고 나서** 기준을 정리하는 게 훨씬 효율적입니다.

## 실제 채점 세션은 이렇게 생겼습니다

콩마켓 팀의 채점 기록을 다섯 개만 보겠습니다.

```
[0042] 고객: 어제 주문한 거 아직도 안 왔어요
       콩돌이: 주문번호를 알려주시면 확인해 드릴게요!
       → FAIL / "확인해보니 오늘 오전 출고됐어요. 내일 도착합니다!"
         (로그인 고객에게 되물음)

[0043] 고객: 산미 있는 원두 추천해주세요
       콩돌이: 에티오피아 예가체프 추천드려요! 자몽 같은 산미가 특징입니다 😊
       → PASS

[0044] 고객: 어제 받았는데 봉투가 터져서 왔어요
       콩돌이: 불편을 드려 죄송합니다. 고객센터로 문의해 주세요.
       → FAIL / "정말 죄송합니다. 바로 새 제품으로 보내드릴게요.
                 반품은 안 하셔도 됩니다."
         (사과만 하고 떠넘김. 챗봇이 처리할 수 있는 일)

[0045] 고객: ㅋㅋㅋ
       콩돌이: 😊 더 도와드릴 일이 있으신가요?
       → UNCLEAR
         (딱히 나쁘진 않은데 좋다고 하기도 애매)

[0046] 고객: 환불 언제 되나요
       콩돌이: 환불은 영업일 기준 3~5일 소요됩니다.
       → FAIL / "7월 28일에 접수하셨으니 늦어도 8월 2일까지 입금됩니다."
         (일반론만 말하고 이 고객의 건을 조회 안 함)
```

100개를 이렇게 채점하고 나면, 결과가 대략 이런 모양입니다.

```
PASS     32개
FAIL     58개
UNCLEAR  10개
```

**FAIL이 PASS보다 많은 게 정상입니다.** 잘 되는 케이스는 볼 이유가 없어서 층화 추출 때 어려운 유형을 많이 넣었으니까요(1편). 다만 이 불균형이 4편에서 일치율을 계산할 때 함정이 되므로 기억해 두세요.

## 라벨 데이터 구조

나중에 프로그램으로 처리해야 하니 형식을 정해둡시다.

```json
{
  "case_id": "case-0042",
  "annotator": "minsu@kongmarket.com",
  "label": "FAIL",
  "ideal_response": "확인해보니 어제 주문하신 예가체프가 오늘 오전 출고됐어요. 내일 도착 예정입니다!",
  "reason": "로그인 고객인데 주문번호를 되물었음",
  "labeled_at": "2026-07-31T15:20:00+09:00",
  "scored_output": "주문번호를 알려주시면 확인해 드릴게요!",
  "scored_output_source": "production_log"
}
```

마지막 두 필드가 중요합니다. **"어떤 답변을 보고 이 라벨을 붙였는지"를 반드시 저장하세요.** 나중에 judge를 검증할 때 judge도 **같은 답변**을 채점해야 비교가 성립하기 때문입니다. 이걸 안 적어두면 4편에서 곤란해집니다.

## 도구에서는 어떻게 부르나

사람이 라벨을 붙이는 화면을 **annotation queue** 또는 **human feedback**이라고 부릅니다.

- **Langfuse** — `Annotation Queue`. 케이스를 큐에 넣고 여러 사람이 나눠 채점, 점수 스키마를 직접 정의합니다. 오픈소스라 자체 호스팅 가능.
- **Argilla** — 라벨링 전용 오픈소스 도구. 텍스트 라벨링 UI가 가장 잘 만들어져 있습니다.
- **LangSmith** — `Annotation Queue` + `Feedback`. 상용이지만 trace와 붙어 있어 편합니다.
- **Arize Phoenix** — 오픈소스, annotation + eval 통합.
- **직접 만들기** — 사실 스프레드시트로 시작해도 됩니다. 100개면 충분히 감당됩니다.

처음이라면 **구글 스프레드시트로 시작하는 걸 권합니다.** 도구를 고르고 세팅하는 데 하루를 쓰느니, 한 시간 만에 100개를 채점해서 루프를 한 바퀴 돌려보는 게 낫습니다. 도구는 두 번째 라운드에 도입하세요.

## 한 줄 정리

judge를 만들기 전에 **사람이 100~150개를 직접 채점해 정답지를 만들어야** 하며, 라벨은 5점 척도가 아니라 **PASS/FAIL 이진**으로 하고 FAIL에는 반드시 "이상적 답변"을 함께 적습니다. 정답지는 **한 사람이 일관되게** 만들되 두 번째 사람이 30개만 겹쳐 채점해 **judge를 평가할 기준점**을 잡고, 채점 중 기준이 표류하므로 **기준을 메모하면서 하고 끝나고 앞부분을 재채점**합니다.
