# 1편. 무엇을 채점할 것인가 — 테스트 케이스와 데이터셋

> 시리즈: AI 답변을 채점하는 법 — LLM-as-a-Judge 밑바닥부터
> 이 편에서 배우는 것: 평가의 단위를 "대화 전체"가 아니라 "한 턴"으로 잡아야 하는 이유, 실제 로그에서 평가용 케이스를 뽑는 방법, 그리고 과거 대화로 평가할 때 반드시 조심해야 하는 정보 누출.

judge를 만들기 전에 할 일이 있습니다. **무엇을 채점할지 정하는 것**입니다. 당연해 보이지만 여기서 잘못 시작하면 뒤의 모든 숫자가 무의미해지기 때문에, 한 편을 통째로 씁니다.

## 대화 전체를 평가하면 안 되는 이유

콩돌이의 상담 대화 하나를 가져와 봅시다.

```
고객:   어제 주문한 거 아직도 안 왔어요
콩돌이: 주문번호를 알려주시면 확인해 드릴게요!
고객:   20260731-4471 요
콩돌이: 확인했습니다. 오늘 오전 출고돼서 내일 도착 예정이에요.
고객:   아 네 감사합니다
```

"이 대화가 좋은가?"를 평가하고 싶어집니다. 그런데 프롬프트를 v2로 바꾸면 어떻게 될까요?

```
고객:   어제 주문한 거 아직도 안 왔어요
콩돌이: 확인해보니 어제 주문하신 예가체프가 오늘 오전 출고됐어요. 내일 도착합니다!
고객:   ??? (이 고객은 뭐라고 답했을까요?)
```

**두 번째 턴부터는 알 수 없습니다.** 실제 고객은 주문번호를 물었기 때문에 번호를 답한 것이고, 안 물어봤다면 뭐라고 했을지 우리는 모릅니다. "감사합니다"였을 수도, 다른 질문을 던졌을 수도 있죠.

대화 전체를 재생성하려면 **고객 역할도 AI로 흉내내야** 합니다. 그러면 평가 대상이 두 개(챗봇 + 가짜 고객)로 늘어나고, 결과가 나빴을 때 누구 탓인지 알 수 없게 됩니다.

> **그래서 표준은 이렇습니다.**
> **앞의 대화 맥락은 그대로 고정하고, 마지막 한 턴만 다시 생성해서 그것만 채점한다.**

```
[고정 — 손대지 않음]
고객: 어제 주문한 거 아직도 안 왔어요

[재생성 — 채점 대상]
콩돌이: ???
```

이렇게 하면 v1과 v2가 **완전히 같은 상황**에서 답한 것이 되어 사과 대 사과 비교가 됩니다. 이 한 덩어리를 **테스트 케이스(test case)** 라고 부릅니다.

## 테스트 케이스의 구조

JSON으로 그려보면 이렇습니다.

```json
{
  "id": "case-0042",
  "context": [
    { "role": "user", "content": "안녕하세요" },
    { "role": "assistant", "content": "안녕하세요! 콩마켓입니다 😊" },
    { "role": "user", "content": "어제 주문한 거 아직도 안 왔어요" }
  ],
  "metadata": {
    "logged_in": true,
    "customer_tier": "regular",
    "source_log_id": "log-99812",
    "captured_at": "2026-07-28T10:12:00Z"
  }
}
```

여기에 **정답 답변은 들어 있지 않다**는 점을 눈여겨보세요. 0편에서 봤듯 정답이 하나가 아니기 때문에, 우리가 저장하는 건 **상황**뿐입니다. 답변은 평가할 때마다 새로 만들고, 그 답변을 judge가 채점합니다.

```
테스트 케이스(상황) + 프롬프트 v1 → 답변 A → judge → PASS/FAIL
테스트 케이스(상황) + 프롬프트 v2 → 답변 B → judge → PASS/FAIL
```

## 로그에서 케이스를 뽑는 법

실제 상담 로그가 5,000건 쌓여 있다고 합시다. 여기서 200건을 골라야 하는데, 어떻게 고를까요?

### 방법 1: 무작위 — 기본이지만 함정이 있음

```python
import random
cases = random.sample(all_logs, 200)
```

가장 공정해 보입니다. 실제 트래픽 분포를 그대로 반영하니까요. 그런데 문제가 있습니다. **흔한 질문이 대부분을 차지합니다.**

콩마켓 로그의 실제 분포가 이렇다고 해보죠.

| 유형 | 비율 |
|---|---|
| 배송 조회 | 62% |
| 상품 문의 | 21% |
| 환불/교환 | 12% |
| 기타 (컴플레인, 잡담 등) | 5% |

무작위로 200건을 뽑으면 환불 케이스는 24건, 컴플레인은 10건밖에 안 들어옵니다. 그런데 **정작 챗봇이 사고를 치는 건 환불과 컴플레인에서**입니다. 배송 조회는 쉬워서 어느 프롬프트로도 잘합니다.

### 방법 2: 층화 추출 — 유형별로 할당량을 정하기

**층화 추출(stratified sampling)** 은 유형별로 몇 개씩 뽑을지 미리 정하는 방식입니다.

```python
QUOTA = {
    "배송조회": 60,
    "상품문의": 50,
    "환불교환": 50,
    "기타":     40,
}

cases = []
for category, n in QUOTA.items():
    pool = [log for log in all_logs if log["category"] == category]
    cases += random.sample(pool, min(n, len(pool)))
```

이렇게 하면 어려운 유형이 충분히 들어옵니다. 실무에서는 대부분 이 방식을 씁니다.

**뽑고 나면 `id`를 키로 하는 dict으로 바꿔두세요.**

```python
dataset = {case["id"]: case for case in cases}
```

앞으로 나올 코드는 전부 `dataset[case_id]` 형태로 케이스를 찾고, 채점 결과도 `{case_id: 판정}` 형태로 주고받습니다. **케이스와 답변과 판정을 `case_id`로 묶는 것**이 3편부터 6편까지 이어지는 약속입니다. 리스트로 들고 다니면 순서가 어긋나는 순간 조용히 엉뚱한 답변을 채점하게 됩니다.

> **주의:** 층화로 뽑으면 통과율이 **실제 서비스 품질보다 낮게** 나옵니다. 어려운 케이스를 일부러 많이 넣었으니까요. 이 숫자는 "우리 챗봇의 실제 정확도"가 아니라 **"v1과 v2를 비교하는 자[尺]"** 로만 써야 합니다. 대외 발표용 숫자로 쓰면 안 됩니다.

### 방법 3: 실패 케이스만 모으기 — 하지 마세요

"어차피 고칠 건데 실패한 것만 모으면 되지 않나?" 싶지만, 이러면 **회귀를 못 잡습니다.**

프롬프트 v2가 실패 케이스 50개를 다 고쳤다고 칩시다. 그런데 그 과정에서 잘 되던 배송 조회를 망가뜨렸다면? 데이터셋에 성공 케이스가 없으니 **끝까지 모릅니다.** 배포하고 나서 고객이 알려줍니다.

**실패 케이스는 반드시 성공 케이스와 섞어야 합니다.** 위 층화 추출에 "과거에 잘하던 케이스" 몫을 따로 두는 게 좋습니다.

## 몇 개나 필요한가

가장 많이 받는 질문인데, 답은 **"용도에 따라 다르다"** 입니다.

| 용도 | 권장 규모 | 이유 |
|---|---|---|
| 개발 중 빠른 확인 | 20~30 | 몇 분 안에 돌아야 함 |
| 프롬프트 A/B 비교 | 150~300 | 4편에서 볼 통계적 이유 |
| 배포 전 회귀 검사 | 100~200 | 넓게 훑어야 함 |

**200건이 실무의 좋은 출발점**입니다. 이보다 적으면 차이가 노이즈에 묻히고, 이보다 많으면 사람이 라벨을 붙이기 버겁습니다. (사람 라벨 이야기는 2편에서 합니다.)

시작할 때 흔한 실수는 **너무 크게 시작하는 것**입니다. 1,000건짜리 데이터셋을 만들어놓고 사람이 라벨을 못 붙여서 방치하느니, 100건으로 시작해 루프를 한 바퀴 돌려보는 게 훨씬 낫습니다.

## 과거 데이터를 쓸 때의 함정 — 미래 정보 누출

이게 이 편에서 가장 중요한 부분입니다. 그리고 놓치기 쉽습니다.

3개월 전 대화를 오늘 평가한다고 해봅시다.

```
[2026-04-15 실제 대화]
고객:   추천 좀 해주세요, 산미 있는 걸로
콩돌이: 에티오피아 예가체프 어떠세요? 자몽 같은 산미가 특징이에요.
```

오늘 이 케이스를 v2로 다시 돌리면, 콩돌이는 **오늘의 재고와 오늘의 상품 목록**을 보게 됩니다. 4월에는 없던 신상품 "케냐 AA"를 추천할 수도 있죠. 그러면 판정이 이상해집니다 — 4월의 콩돌이는 알 수 없었던 정보로 답한 것이니까요.

> **원칙: 테스트 케이스를 실행할 때는 그 시점에 존재했던 정보만 보이게 해야 한다.**

실무에서 자주 새는 곳들입니다.

- **상품/재고 데이터** — 그때의 스냅샷을 써야 합니다
- **고객 프로필** — 그 이후에 쌓인 구매 이력이 들어가면 안 됩니다
- **대화 기록(메모리)** — 그 시점 이후의 대화를 챗봇이 참조하면 안 됩니다
- **현재 시각** — "오늘 배송됩니다" 같은 답변이 달라집니다. 케이스에 기준 시각을 박아두고 그 값을 주입하세요

케이스 구조에 시각을 명시적으로 넣어두면 좋습니다.

```json
{
  "id": "case-0042",
  "reference_time": "2026-04-15T14:30:00+09:00",
  "context": [ "..." ],
  "snapshot": {
    "catalog_version": "2026-04-15",
    "customer_profile_as_of": "2026-04-15T14:30:00+09:00"
  }
}
```

이걸 안 하면 **평가는 돌아가는데 결과를 믿을 수 없는** 상태가 됩니다. 가장 알아채기 어려운 종류의 버그입니다.

## 개인정보는 어떻게 하나

실제 고객 대화를 평가 데이터로 쓴다는 건 **개인정보를 다룬다**는 뜻입니다. 최소한 이 정도는 챙겨야 합니다.

- **접근 권한** — 평가 데이터셋에도 원본 로그와 같은 수준의 접근 통제를 겁니다
- **가명화** — 이름·전화번호·주소는 치환합니다. 다만 과하게 지우면 대화가 부자연스러워져서 평가가 왜곡되니, "홍길동 → 김민수"처럼 **형태를 유지한 치환**이 좋습니다
- **제외 목록** — 고객이 데이터 사용에 동의하지 않았거나 민감한 내용(결제 분쟁, 건강 관련)이 있는 대화는 아예 뽑지 않습니다

데이터셋을 만드는 코드에 이 필터를 **처음부터** 넣어두세요. 나중에 붙이면 이미 만들어진 데이터셋이 오염된 채로 돌아다닙니다.

## 정리: 데이터셋 만들기 체크리스트

```
□ 평가 단위를 "한 턴"으로 잡았는가 (맥락 고정 + 마지막 턴만 재생성)
□ 유형별 할당량을 정했는가 (어려운 유형이 충분히 들어갔는가)
□ 성공 케이스도 섞었는가 (회귀를 잡기 위해)
□ 150~300건 규모인가
□ 시점 정보를 케이스에 박아두었는가 (미래 정보 누출 차단)
□ 개인정보 필터를 데이터셋 생성 코드에 넣었는가
□ 데이터셋에 버전을 붙였는가 (나중에 "그때 그 데이터셋"을 재현하기 위해)
```

마지막 항목을 덧붙이자면 — 데이터셋은 **한 번 만들면 바꾸지 마세요.** 케이스를 추가하거나 빼면 이전 결과와 비교할 수 없게 됩니다. 바꾸고 싶으면 `v2`로 새로 만들고, 어느 버전으로 잰 숫자인지 항상 함께 기록하세요.

## 도구에서는 어떻게 부르나

거의 모든 평가 도구가 이 개념을 **dataset**이라고 부릅니다.

- **promptfoo** — YAML의 `tests:` 배열. 각 항목이 하나의 케이스이고, `vars:`에 상황을 담습니다.
- **Langfuse** — `Dataset` + `DatasetItem`. `input`(상황)과 선택적 `expected_output`을 가집니다.
- **DeepEval** — `EvaluationDataset` + `LLMTestCase`. `input`, `actual_output`, `context` 필드 구성입니다.
- **OpenAI Evals** — JSONL 한 줄이 한 케이스.

이름과 필드는 조금씩 다르지만 **"상황을 저장하고, 출력은 실행할 때마다 새로 만든다"** 는 구조는 같습니다. 도구를 처음 열었을 때 이 대응만 잡으면 나머지는 금방 읽힙니다.

## 한 줄 정리

평가의 단위는 **대화 전체가 아니라 맥락이 고정된 한 턴**이고, 케이스는 **유형별 할당량을 정해 150~300건** 뽑되 성공 케이스를 반드시 섞으며, 과거 데이터를 쓸 때는 **그 시점에 없던 정보가 새어 들어가지 않도록** 시각과 스냅샷을 케이스에 박아두어야 합니다.
