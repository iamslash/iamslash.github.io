# 1편. LLM 답변을 자동으로 채점하기 — judge와 rubric

> 시리즈: AI 답변을 채점하는 법 — LLM-as-a-Judge
> 이 편에서 배우는 것: 챗봇 답변은 왜 `assert`로 테스트할 수 없는지, LLM에게 채점을 시키는 방법, 그리고 채점 기준표(rubric)를 쓰는 요령.

온라인 원두 쇼핑몰 **"콩마켓"** 에 고객 상담 챗봇 **"콩돌이"** 를 붙였다고 해봅시다. 시스템 프롬프트 한 장짜리 흔한 구성입니다.

```
[프롬프트 v1]
너는 콩마켓의 고객 상담원이다. 친절하고 간결하게 답하라.
```

로그를 열어보니 이런 대화가 있습니다.

```
고객:   어제 주문한 거 아직도 안 왔어요
콩돌이: 주문번호를 알려주시면 확인해 드릴게요!
```

이 고객은 **로그인 상태**라 주문 내역을 이미 조회할 수 있었습니다. 굳이 물어볼 필요가 없었죠. 그래서 프롬프트에 한 줄을 추가합니다.

```
[프롬프트 v2]
너는 콩마켓의 고객 상담원이다. 친절하고 간결하게 답하라.
+ 로그인한 고객이면 주문번호를 묻지 말고 최근 주문을 조회해서 안내하라.
```

배포하려는 순간 불안해집니다.

> **정말 좋아진 게 맞나? 다른 데가 망가진 건 아닐까?**

이 시리즈는 이 질문에 답하는 방법입니다.

## `assert`가 안 되는 이유

일반 코드라면 고민할 필요가 없습니다.

```python
assert add(2, 3) == 5   # 통과 or 실패. 끝.
```

정답이 **하나**니까요. 그런데 챗봇은 이렇습니다.

```
고객: 어제 주문한 거 아직도 안 왔어요

A: "확인해보니 어제 주문하신 예가체프가 오늘 오전 출고됐어요. 내일 도착합니다!"
B: "앗, 기다리셨겠어요. 방금 보니 오늘 오전에 출고됐고 내일 받으실 수 있어요."
C: "고객님의 주문은 정상적으로 처리되었으며 배송 중입니다."
```

A와 B는 표현이 완전히 다른데 둘 다 좋습니다. C는 틀린 말은 아니지만 언제 오는지를 안 알려줬으니 아쉽죠. **정답이 여러 개고, 좋고 나쁨이 정도의 문제**입니다.

그럼 사람이 읽으면 되지 않을까요? 정확합니다. 문제는 **규모**입니다. 하루에 대화가 1,000건 쌓이는데 프롬프트를 고칠 때마다 다시 읽을 수는 없습니다.

## 그래서 LLM에게 채점을 시킵니다

발상은 단순합니다. **LLM이 답변을 잘 만든다면, 채점도 할 수 있지 않을까?**

```
[채점 지시서]
로그인한 고객에게 주문번호를 되물었다면 FAIL이다.
필요한 정보를 스스로 조회해서 안내했다면 PASS다.

[대화]
고객:   어제 주문한 거 아직도 안 왔어요
콩돌이: 주문번호를 알려주시면 확인해 드릴게요!

→ FAIL
```

이게 **LLM-as-a-Judge**입니다.

> - **judge**: 채점을 담당하는 LLM. 평가 대상 챗봇과 별개로 돕니다.
> - **rubric**: judge에게 주는 채점 기준표. 사실상 프롬프트 한 장입니다.

## 무엇을 채점할 것인가

대화 전체를 평가하려 하면 막힙니다. 프롬프트를 v2로 바꾸면 콩돌이 답이 달라지고, 그러면 **고객이 뭐라고 반응했을지 알 수 없기** 때문입니다. 실제 고객은 주문번호를 물었으니 번호를 답한 것이지, 안 물어봤다면 뭐라고 했을지 모릅니다.

> **그래서 표준은 이렇습니다.**
> **앞의 대화는 그대로 고정하고, 마지막 한 턴만 다시 생성해서 그것만 채점한다.**

```
[고정 — 손대지 않음]
고객: 어제 주문한 거 아직도 안 왔어요

[재생성 — 채점 대상]
콩돌이: ???
```

이 한 덩어리를 **테스트 케이스**라고 부릅니다. 실제 로그에서 뽑아 이렇게 저장합니다.

```python
dataset = {
    "case-0042": {
        "context": [
            {"role": "user", "content": "어제 주문한 거 아직도 안 왔어요"},
        ],
        "metadata": {"logged_in": True},
    },
    # ... 200개쯤
}
```

**정답 답변은 저장하지 않습니다.** 정답이 여러 개니까요. 우리가 저장하는 건 **상황**뿐이고, 답변은 평가할 때마다 새로 만듭니다.

앞으로 나올 코드는 전부 `case_id`를 키로 케이스·답변·판정을 묶습니다. 리스트로 들고 다니면 순서가 어긋나는 순간 조용히 엉뚱한 답변을 채점하게 됩니다.

> **케이스를 뽑을 때 하나만 조심하세요.** 무작위로 뽑으면 쉬운 배송 조회가 대부분을 차지합니다. 정작 챗봇이 사고 치는 건 환불이나 컴플레인이죠. **유형별로 할당량을 정해서** 어려운 케이스가 충분히 들어가게 하세요. 대신 그러면 통과율이 실제 품질보다 낮게 나오니, 이 숫자는 **v1과 v2를 비교하는 자[尺]로만** 쓰고 대외 발표용으로 쓰면 안 됩니다.

## 그전에 — 사람이 먼저 채점합니다

judge를 만들기 전에 할 일이 있습니다. **사람이 50~100개를 직접 채점하는 것**입니다.

건너뛰고 싶어지지만, 이게 없으면 나중에 **judge가 맞는지 틀리는지 알 방법이 없습니다.** (2편의 주제가 이것입니다.)

채점은 이렇게 합니다. 5점 척도는 쓰지 마세요 — 사람도 3점과 4점을 구분 못 하고, LLM은 더합니다.

```
[0042] 고객(로그인): 어제 주문한 거 아직도 안 왔어요
       콩돌이: 주문번호를 알려주시면 확인해 드릴게요!
       → FAIL
         이상적: "확인해보니 오늘 오전 출고됐어요. 내일 도착합니다!"
         이유:   로그인 고객에게 되물음

[0043] 고객: 산미 있는 원두 추천해주세요
       콩돌이: 에티오피아 예가체프 추천드려요! 자몽 같은 산미가 특징입니다
       → PASS

[0044] 고객: 어제 받았는데 봉투가 터져서 왔어요
       콩돌이: 불편을 드려 죄송합니다. 고객센터로 문의해 주세요.
       → FAIL
         이상적: "정말 죄송합니다. 바로 새 제품으로 보내드릴게요."
         이유:   사과만 하고 떠넘김
```

**`FAIL`에서 멈추지 말고 "그럼 뭐라고 답했어야 하나"를 꼭 적으세요.** 이게 곧 rubric의 재료가 됩니다.

그리고 **기준을 메모하면서 채점하세요.** 처음 10개를 볼 때와 80개를 본 뒤의 기준이 다릅니다. 이건 논문으로도 확인된 현상(criteria drift)이라 피할 수 없고, 대신 메모해두면 그게 rubric 초안이 됩니다.

```
[채점하며 적은 메모]
- 로그인 고객에게 주문번호 되묻기 → FAIL
- 배송일을 "곧"이라고만 하면 → FAIL, 날짜 필요
- 사과만 하고 조치 없으면 → FAIL
```

100개면 1~2시간입니다. **한 번에 몰아서** 하세요. 며칠에 나누면 기준이 더 흔들립니다.

## rubric 쓰기

이제 위 메모를 rubric으로 옮깁니다. 흔한 실패작부터 보죠.

### 나쁜 rubric

```
아래 고객 상담 답변이 좋은 답변인지 평가하라. PASS 또는 FAIL로 답하라.
```

동작은 합니다. 그런데 **"좋은"의 정의가 없어서 judge가 자기 취향대로 판단합니다.** 실제로 이런 일이 벌어집니다.

```
콩돌이: 주문번호를 알려주시면 확인해 드릴게요!

judge: PASS — "정중하게 추가 정보를 요청했음. 적절한 응대."
사람:  FAIL — "로그인했는데 왜 물어봐."
```

### 좋은 rubric

```
당신은 콩마켓의 고객 상담 품질 검수자다. 상담원의 답변 하나를 평가한다.

## 평가 질문
"이 답변을 그대로 고객에게 보내도 되는가?"

## FAIL 조건 (하나라도 해당하면 FAIL)
1. 고객이 로그인 상태(logged_in=true)인데 주문번호처럼
   이미 조회 가능한 정보를 되물었다.
2. 배송/환불 시점을 "곧", "빠른 시일 내"처럼 모호하게만 말하고
   구체적 날짜를 주지 않았다.
3. 사과나 공감만 하고, 상담원이 할 수 있는 조치를 안 했다.
4. 제공된 주문/상품 정보와 다른 말을 했다.

## PASS 조건
위에 해당하지 않고, 고객이 물은 것에 실제로 답했다.

## 평가하지 말 것
- 말투나 이모지는 평가 대상이 아니다.
- 답변 길이는 평가 대상이 아니다. 짧아도 필요한 정보가 있으면 PASS.
- 당신이라면 다르게 썼을 것 같다는 이유로 FAIL을 주지 마라.

## 판정
명확히 FAIL 조건 해당 → FAIL / 문제없음 → PASS / 정보 부족 → UNCLEAR
```

차이는 셋입니다.

**FAIL 조건을 번호로 나열했습니다.** judge는 "좋은 답변" 같은 추상어를 제멋대로 해석하지만, 번호 붙은 조건은 그대로 따릅니다.

**"평가하지 말 것"이 있습니다.** 이게 의외로 큰 효과를 냅니다. 그냥 평가를 시키면 judge가 온갖 것에 트집을 잡습니다 — 말투가 딱딱하다, 이모지가 없다, 좀 짧다. 범위를 잘라주면 본론에 집중합니다.

**UNCLEAR의 조건을 좁혔습니다.** "애매하면"이 아니라 "**정보가 부족해서** 판단 불가일 때"입니다. 안 그러면 어려운 케이스를 전부 UNCLEAR로 도망칩니다.

> 조건이 20개가 되면 judge가 뒷부분을 흘립니다. **5~8개**가 적당하고, 그 이상이면 rubric을 둘로 나누세요(정확성 judge / 말투 judge).

## 출력 스키마 — 순서가 정확도를 바꿉니다

judge가 자유롭게 답하면 파싱이 지옥이 됩니다. 구조화 출력을 씁니다.

```python
from pydantic import BaseModel
from typing import Literal

class Finding(BaseModel):
    quote: str      # 답변에서 그대로 인용한 문장
    issue: str      # 어떤 조건에 해당하는지

class Judgment(BaseModel):
    findings: list[Finding]                        # ① 근거
    reasoning: str                                  # ② 종합
    verdict: Literal["PASS", "FAIL", "UNCLEAR"]    # ③ 판정
```

> **Pydantic**은 데이터 형태를 클래스로 선언하고 검증해주는 라이브러리입니다. 이 클래스가 그대로 LLM에게 줄 JSON 스키마로 변환됩니다. `Literal[...]`은 "이 셋 중 하나만"이라는 뜻이고요.

**여기서 필드 순서가 결정적입니다.**

LLM은 앞에서 뒤로 생성합니다. `verdict`를 맨 앞에 두면 **판정을 먼저 뱉고 나서 거기에 맞는 이유를 지어냅니다.** 결론을 내지르고 논리를 갖다 붙이는 것과 같죠. 뒤에 두면 근거를 다 쓴 다음에 판정합니다.

> **한 줄 규칙: `verdict`는 스키마의 맨 마지막 필드.**

인용문(`quote`)을 강제하는 것도 중요합니다. 없는 내용을 지어내기 어려워지고, 나중에 judge가 틀렸을 때 **어느 문장을 보고 그렇게 판단했는지** 추적할 수 있습니다.

## 전체 코드

```python
from openai import OpenAI

client = OpenAI()
RUBRIC = """..."""   # 위의 rubric 전문

def render(case: dict) -> str:
    """케이스의 '상황'을 문자열로."""
    conversation = "\n".join(
        f"{'고객' if m['role'] == 'user' else '콩돌이'}: {m['content']}"
        for m in case["context"]
    )
    return (f"## 고객 정보\n로그인 상태: {case['metadata']['logged_in']}\n\n"
            f"## 대화 맥락\n{conversation}")


def judge(case: dict, response: str) -> Judgment | None:
    """None 이면 판정 실패(거부·파싱 실패). 호출 측에서 UNCLEAR 로 다룬다."""
    completion = client.chat.completions.parse(
        model="gpt-4.1-mini",     # 챗봇과 다른 계열 모델로 (아래 참고)
        temperature=0,             # 재현성
        messages=[
            {"role": "system", "content": RUBRIC},
            {"role": "user", "content":
                f"{render(case)}\n\n## 평가 대상 답변\n콩돌이: {response}"},
        ],
        response_format=Judgment,
    )
    message = completion.choices[0].message
    if message.refusal is not None or message.parsed is None:
        return None
    return message.parsed
```

> **SDK 버전 주의:** 구조화 출력 진입점이 버전에 따라 `client.beta.chat.completions.parse` 였다가 `client.chat.completions.parse` 로 옮겨갔습니다. `AttributeError`가 나면 `beta.`를 붙이거나 떼면 됩니다.

돌려보면 이렇게 나옵니다.

```python
>>> judge(dataset["case-0042"], "주문번호를 알려주시면 확인해 드릴게요!")
Judgment(
  findings=[Finding(quote="주문번호를 알려주시면 확인해 드릴게요!",
                    issue="FAIL 조건 1 — 로그인 고객에게 조회 가능한 정보를 되물음")],
  reasoning="로그인 상태이므로 최근 주문을 직접 조회해 안내할 수 있었다.",
  verdict="FAIL",
)
```

아까 PASS를 주던 judge가 rubric을 제대로 쓰니 FAIL을 줍니다.

데이터셋 전체는 이렇게 돌립니다.

```python
import asyncio

async def _judge_all(cases: dict, responses: dict, concurrency: int):
    sem = asyncio.Semaphore(concurrency)   # 동시 호출 수를 제한하는 신호등

    async def one(cid):
        async with sem:
            return cid, await asyncio.to_thread(judge, cases[cid], responses[cid])

    pairs = await asyncio.gather(*[one(cid) for cid in cases])
    return {cid: (r.verdict if r is not None else "UNCLEAR") for cid, r in pairs}


def judge_all(cases: dict, responses: dict, concurrency: int = 8) -> dict:
    """{case_id: "PASS" | "FAIL" | "UNCLEAR"} 를 돌려준다."""
    return asyncio.run(_judge_all(cases, responses, concurrency))
```

동시 실행은 8~16이 무난하고, 200건이면 1~3분입니다. 비용은 중간급 모델 기준 몇백 원~2천 원 수준이라 하루에 몇 번 돌려도 부담 없습니다.

> **judge 모델은 챗봇과 다른 계열로 쓰세요.** LLM은 자기가 만들었을 법한 답변을 좋게 평가하는 성향이 있습니다. 챗봇이 Claude면 judge는 GPT나 Gemini로. (2편에서 다시 다룹니다.)

## 한 줄 정리

챗봇 답변은 정답이 여럿이라 `assert`로 테스트할 수 없고, 사람이 읽으면 정확하지만 규모가 안 납니다. **judge는 rubric 프롬프트 한 장과 출력 스키마 하나**이며, rubric에는 **FAIL 조건을 번호로 구체적으로 + "평가하지 말 것"** 을 적고, 스키마는 **근거 → 판정** 순서여야 합니다.
