# 0편. 프롤로그 — "이 답변, 좋은 건가요?"

> 시리즈: AI 답변을 채점하는 법 — LLM-as-a-Judge 밑바닥부터
> 이 편에서 배우는 것: LLM 제품 개발이 결국 "방금 바꾼 프롬프트가 정말 나아진 건가?"라는 질문 하나에 막힌다는 것, 왜 기존 자동 지표로는 답할 수 없는지, 그리고 LLM에게 채점을 시키는 방법과 그 방법의 가장 큰 함정.

우리가 운영하는 온라인 원두 쇼핑몰 **"콩마켓"** 에 고객 상담 챗봇 **"콩돌이"** 를 붙였다고 해봅시다. GPT든 Claude든 Gemini든, 시스템 프롬프트를 한 장 써서 붙인 흔한 구성입니다.

```
[시스템 프롬프트 v1]
너는 콩마켓의 고객 상담원이다. 친절하고 간결하게 답하라.
배송·환불·상품 문의를 처리한다.
```

며칠 돌려보니 고객 반응이 영 시원찮습니다. 로그를 열어봤더니 이런 대화가 있었습니다.

```
고객:   어제 주문한 거 아직도 안 왔어요
콩돌이: 주문번호를 알려주시면 확인해 드릴게요!
```

보자마자 아, 하고 이마를 칩니다. 이 고객은 **로그인 상태**라 주문 내역을 이미 조회할 수 있었습니다. 굳이 주문번호를 물어볼 필요가 없었죠. 그래서 프롬프트에 한 줄을 추가합니다.

```
[시스템 프롬프트 v2]
너는 콩마켓의 고객 상담원이다. 친절하고 간결하게 답하라.
배송·환불·상품 문의를 처리한다.
+ 고객이 로그인 상태라면 주문번호를 묻지 말고 최근 주문을 먼저 조회해서 안내하라.
```

배포하고 나니 문득 불안해집니다.

> **이거 정말 좋아진 게 맞나? 혹시 다른 데가 망가진 건 아닐까?**

이 질문에 자신 있게 답할 수 있나요? 대부분은 못 합니다. 그리고 이 시리즈는 정확히 그 질문에 답하는 방법에 관한 것입니다.

## 왜 이게 어려운 문제인가

일반적인 소프트웨어라면 이런 고민을 할 필요가 없습니다. 함수를 고쳤으면 테스트를 돌리면 되니까요.

```python
def add(a, b):
    return a + b

assert add(2, 3) == 5   # 통과 or 실패. 끝.
```

정답이 **하나**이기 때문에 가능한 일입니다. 그런데 챗봇의 답변은 어떨까요?

```
고객: 어제 주문한 거 아직도 안 왔어요

답변 A: "확인해 보니 어제 주문하신 에티오피아 예가체프가 오늘 오전 출고됐어요. 내일 도착 예정입니다!"
답변 B: "앗, 기다리셨겠어요. 방금 확인해보니 오늘 오전에 출고됐고 내일 받아보실 수 있어요."
답변 C: "고객님의 주문은 정상적으로 처리되었으며 배송 중입니다."
```

A와 B는 둘 다 좋습니다. 표현은 완전히 다른데 말이죠. C는... 틀린 말은 아니지만 언제 오는지를 안 알려줬으니 아쉽습니다.

**정답이 하나가 아니고, 좋고 나쁨이 정도의 문제**입니다. `assert`로는 잡을 수 없습니다.

## 옛날 방식이 안 되는 이유

"그럼 정답 문장을 하나 정해두고 얼마나 비슷한지 재면 되지 않나요?"

실제로 오랫동안 그렇게 해왔습니다. **BLEU**나 **ROUGE** 같은 지표가 그것으로, 기계번역이나 요약을 평가할 때 정답 문장과 단어가 얼마나 겹치는지를 셉니다. 그런데 위 예제에 적용해보면 문제가 바로 드러납니다.

정답을 A로 정해두면, B는 같은 뜻인데도 겹치는 단어가 적어 낮은 점수를 받습니다. 반대로 C는 "주문", "배송" 같은 단어가 겹쳐서 점수가 제법 나옵니다. **의미가 아니라 글자를 세기 때문에** 벌어지는 일입니다.

정리하면 이렇습니다.

| 방법 | 왜 안 되나 |
|---|---|
| `assert` 정확히 일치 | 정답이 하나가 아님 |
| BLEU / ROUGE | 단어 겹침만 셈. 다른 표현의 같은 뜻을 놓침 |
| 사람이 직접 읽기 | **정확하지만 느리고 비쌈** |

마지막 줄이 핵심입니다. 사람이 읽으면 정확합니다. 문제는 **규모**입니다. 하루에 대화가 1,000건 쌓이는데 프롬프트를 고칠 때마다 1,000건을 다시 읽을 수는 없습니다.

## 그래서 LLM에게 채점을 시킵니다

발상은 단순합니다. **LLM이 답변을 잘 만든다면, 답변을 평가하는 것도 할 수 있지 않을까?**

```
[채점 지시서]
아래 고객 상담 대화를 평가하라.
고객이 로그인 상태인데 상담원이 주문번호를 되물었다면 FAIL이다.
필요한 정보를 스스로 조회해서 안내했다면 PASS다.

[대화]
고객:   어제 주문한 거 아직도 안 왔어요
콩돌이: 주문번호를 알려주시면 확인해 드릴게요!

→ FAIL. 로그인 고객에게 주문번호를 되물었음.
```

이게 **LLM-as-a-Judge**입니다. 채점하는 LLM을 **judge(심판)** 라고 부르고, 위의 채점 지시서를 **rubric(루브릭, 채점 기준표)** 이라고 부릅니다.

> **용어 정리**
> - **judge**: 채점을 담당하는 LLM. 평가 대상 챗봇과는 별개로 돌아갑니다.
> - **rubric**: judge에게 주는 채점 기준. 사실상 그냥 프롬프트 한 장입니다.
> - **label(라벨)**: 채점 결과. `PASS` / `FAIL` 같은 것.

judge가 생기면 아까의 질문에 답할 수 있게 됩니다.

```
프롬프트 v1 → 대화 200건 재생성 → judge 채점 → 통과율 61%
프롬프트 v2 → 대화 200건 재생성 → judge 채점 → 통과율 74%
```

숫자가 나옵니다. 배포 전에 확인할 수도 있고, CI에 걸어둘 수도 있습니다.

## 그런데 여기서 진짜 문제가 시작됩니다

여기까지 읽고 "오 좋네" 하고 넘어가면 십중팔구 사고가 납니다. 질문 하나만 던져보죠.

> **judge가 제대로 채점하고 있다는 건 누가 보장하나요?**

judge도 LLM입니다. 틀립니다. 그리고 틀리는 방식이 아주 고약합니다.

```
고객:   어제 주문한 거 아직도 안 왔어요
콩돌이: 주문번호를 알려주시면 확인해 드릴게요!

judge: PASS — "정중하게 추가 정보를 요청했음. 적절한 응대."
사람:  FAIL — "로그인했는데 왜 물어봐. 이래서 고객이 짜증나는 것."
```

judge가 PASS를 줬습니다. 그럴듯한 이유까지 붙여서요. 이 judge를 믿고 프롬프트를 계속 튜닝하면 어떻게 될까요? **judge 점수는 계속 오르는데 고객 만족도는 그대로거나 오히려 떨어집니다.** 실제 가치가 아니라 judge의 취향에 맞춰 최적화한 것이니까요.

게다가 judge와 챗봇이 같은 계열 모델이면 이 문제가 더 심해집니다. **LLM은 자기가 쓸 법한 답을 좋아하기 때문입니다.** (5편에서 논문과 함께 자세히 다룹니다.)

그래서 이 시리즈의 진짜 주제는 이렇게 정리됩니다.

> **judge를 만드는 법이 절반, judge를 믿어도 되는지 확인하는 법이 나머지 절반.**
>
> 그리고 실무에서 사고는 대부분 후자를 건너뛰어서 납니다.

## 전체 지도 — 8편

**1단계. 재료 준비**
- **1편. 무엇을 채점할 것인가** — 테스트 케이스와 데이터셋 만들기. 실제 로그에서 평가용 데이터를 뽑는 방법.

**2단계. 사람의 판단을 모으기** — 모든 것의 출발점
- **2편. 사람이 먼저 채점한다** — 라벨 설계(왜 5점 척도가 아니라 PASS/FAIL인지), 몇 개나 필요한지, 채점자는 몇 명이어야 하는지.

**3단계. judge 만들기**
- **3편. LLM judge 만들기** — rubric 작성법, 출력 스키마 설계, "근거를 먼저 쓰게 하라"는 규칙의 이유. 실행 가능한 코드로.

**4단계. judge 검증** — 시리즈의 심장
- **4편. judge를 믿어도 되는가** — 일치율, 우연 보정(Cohen's kappa), PASS/FAIL 각각의 재현율, 홀드아웃 분리.
- **5편. judge의 함정** — 위치 편향, 장황함 편향, 자기편애. 그리고 pointwise vs pairwise.

**5단계. 실전**
- **6편. 프롬프트 A와 B, 어느 쪽이 나은가** — 0편에서 던진 질문에 처음부터 끝까지 답하는 전체 절차.
- **7편. 논문과 오픈소스** — 반드시 읽어야 할 논문 목록과, 직접 만들지 말고 가져다 쓸 도구들.

## 어디에 시간을 쓸지

- **핵심은 2편과 4편입니다.** 사람 라벨을 모으는 법과 judge를 검증하는 법. 이 둘이 전체의 몸통이고, 실무에서 사고가 나는 지점도 여기입니다.
- **3편은 생각보다 쉽습니다.** rubric은 그냥 프롬프트라서, 잘 쓰는 요령 몇 개면 충분합니다.
- **5편은 한 번 읽고 체크리스트로 두세요.** 편향 이름을 외울 필요는 없고, "아 이런 게 있었지" 하고 돌아와 확인하면 됩니다.
- **7편은 먼저 봐도 됩니다.** 이미 만들어진 도구가 많아서, 직접 구현하기 전에 훑어보는 게 시간을 아낍니다.

## 콩돌이 — 앞으로 계속 함께할 예제

개념이 나올 때마다 새 예시를 만들면 머리가 복잡해집니다. 이 시리즈는 **콩마켓의 상담 챗봇 콩돌이** 하나만 붙잡고 끝까지 갑니다.

- **평가 대상:** 콩돌이의 답변 한 턴 (고객 질문에 대한 응답)
- **평가하고 싶은 것:** "이 답변이 고객에게 도움이 됐는가"
- **비교하려는 것:** 프롬프트 v1(현행) vs v2(주문번호 되묻기 금지 조항 추가)
- **가진 것:** 실제 상담 로그 몇천 건

여기서 **200건**을 골라 평가용 데이터셋으로 만들고, 그중 일부에 사람이 직접 라벨을 붙이고, 그 라벨로 judge를 검증한 뒤, 검증된 judge로 v1과 v2를 비교하는 것 — 이게 앞으로 7편에 걸쳐 할 일의 전부입니다.

## 이 시리즈의 최종 목표

목표는 용어를 아는 게 아닙니다. 다 읽고 나면 이렇게 되는 것입니다.

- **promptfoo나 Langfuse 같은 오픈소스 평가 도구를 열었을 때** "아, 이 설정이 그 rubric이고 이 숫자가 그 일치율이구나"라고 알아볼 수 있게
- 그리고 필요하면 **직접 만들 수 있게**

그래서 매 편 끝에 **"도구에서는 어떻게 부르나"** 한 문단을 붙입니다. 방금 배운 개념이 실제 평가 도구의 어느 부품인지 짚어드리겠습니다.

## 도구에서는 어떻게 부르나

평가 도구를 뜯어보면 대개 네 덩어리입니다. (1) **데이터셋** — 무엇을 평가할지 모아둔 것, (2) **실행** — 대상 모델/프롬프트를 돌려 출력을 만드는 부분, (3) **채점기(scorer/evaluator)** — 그 출력에 점수를 매기는 부분, (4) **비교** — 두 실행의 결과를 나란히 보는 화면.

LLM-as-a-judge는 이 중 (3)의 한 종류입니다. 도구마다 이름이 조금씩 달라서, promptfoo에서는 `llm-rubric` assertion, DeepEval에서는 `GEval` 메트릭, Langfuse에서는 `LLM-as-a-judge evaluator`라고 부릅니다. 이름만 다르지 하는 일은 같습니다 — **rubric을 프롬프트로 넣고, 대상 출력을 붙여서, LLM에게 판정을 받아오는 것.**

## 한 줄 정리

LLM 제품은 정답이 하나가 아니라서 `assert`로 테스트할 수 없고, 사람이 읽으면 정확하지만 규모가 안 나옵니다. **LLM-as-a-judge는 사람의 판단을 복제한 자동 채점기**이며, 이 시리즈의 절반은 그 채점기를 만드는 법, 나머지 절반은 **그 채점기가 사람과 같은 판단을 하는지 검증하는 법**입니다.
