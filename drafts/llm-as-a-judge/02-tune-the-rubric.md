# 2편. rubric 튜닝 — judge를 사람 기준에 맞추기

> 시리즈: AI 답변을 채점하는 법 — LLM-as-a-Judge
> 이 편에서 배우는 것: judge가 제대로 채점하는지 재는 법, 일치율이 왜 부풀려지는지, 불일치를 읽고 rubric을 고치는 루프, 그리고 judge가 체계적으로 틀리는 다섯 가지 방식.

1편에서 judge를 만들었습니다. 그런데 이 질문이 남아 있죠.

> **judge가 제대로 채점하고 있다는 건 누가 보장하나?**

judge도 LLM입니다. 틀립니다. 그리고 틀린 judge로 프롬프트를 튜닝하면 **점수는 계속 오르는데 고객 만족도는 그대로거나 오히려 떨어집니다.** 실제 가치가 아니라 judge의 취향에 맞춰 최적화한 것이니까요.

이 편이 시리즈에서 제일 중요합니다. 그리고 실무에서 사고는 대부분 이 편을 건너뛰어서 납니다.

## 정답지를 둘로 나눕니다

1편에서 사람이 100개를 채점해뒀습니다. 이걸 그냥 다 쓰면 안 됩니다.

```
사람 라벨 100개
   ├─ 개발용  60개  ← rubric 고치는 내내, 몇 번이든
   └─ 홀드아웃 40개  ← 각 라운드 맨 마지막에 딱 한 번
```

**왜 나누냐면** — 같은 60개를 보면서 rubric을 다섯 번 고치면, 그 60개에만 잘 맞는 rubric이 됩니다. 시험 문제를 보고 답을 외운 셈이죠. 손대지 않은 40개로 재야 진짜 실력이 나옵니다. 이 40개를 **홀드아웃(holdout)** 이라고 부릅니다.

> **⚠️ judge와 사람이 같은 답변을 채점해야 합니다.** 사람은 운영 로그에 있던 그 답변을 보고 라벨을 붙였습니다. judge에게 새로 생성한 답변을 채점시키면 **다른 물건을 비교하는 셈**입니다.

## 혼동행렬 — 표 하나로 시작

judge에게 홀드아웃 40개를 채점시키고 사람 라벨과 나란히 놓습니다.

|  | judge: PASS | judge: FAIL | 합계 |
|---|---|---|---|
| **사람: PASS** | **10** | 4 | 14 |
| **사람: FAIL** | 3 | **23** | 26 |
| **합계** | 13 | 27 | 40 |

대각선(굵은 숫자)이 맞은 것입니다.

```
일치율 = (10 + 23) / 40 = 82.5%
```

나쁘지 않아 보입니다. **그런데 이 숫자를 믿으면 안 됩니다.**

## 함정 ① 아무렇게나 찍어도 65%

사람 라벨이 PASS 14개, FAIL 26개입니다. FAIL이 65%죠. 어려운 케이스를 일부러 많이 넣었으니까요.

이제 **무조건 FAIL만 외치는 바보 judge**를 만들어 봅시다.

```python
def dumb_judge(case, response):
    return "FAIL"   # 끝
```

일치율은? 사람이 FAIL이라 한 26개를 다 맞히니 **26/40 = 65%** 입니다.

```
바보 judge:  65%
우리 judge:  82.5%
```

**출발선이 이미 65%** 였습니다. 실제로 번 건 17.5%p뿐이죠. 한쪽 라벨이 많을수록 일치율은 저절로 부풀려집니다.

## Cohen's kappa — 우연을 걷어낸 일치율

이걸 해결하는 게 **Cohen's kappa(κ)** 입니다. 아이디어는 단순합니다.

> **"우연히 맞을 만큼은 빼고, 그 이상 얼마나 잘 맞혔나"**

```
        p_o - p_e          p_o = 실제 일치율
  κ =  -----------         p_e = 우연히 일치할 확률
         1 - p_e
```

`p_e`는 둘이 서로 무관하게 라벨을 뿌린다고 가정하고 각자의 비율을 곱해 더합니다.

```
사람 PASS 비율 14/40 = 0.35  ×  judge PASS 비율 13/40 = 0.325  =  0.114
사람 FAIL 비율 26/40 = 0.65  ×  judge FAIL 비율 27/40 = 0.675  =  0.439
                                                        p_e  =  0.553

      0.825 - 0.553
κ =  --------------- = 0.61
      1 - 0.553
```

**82.5%가 0.61이 됐습니다.** 훨씬 겸손한 숫자죠.

| κ | 해석 |
|---|---|
| ~0.40 | 약함 |
| 0.41 ~ 0.60 | 보통 |
| **0.61 ~ 0.80** | **쓸 만한 구간** |
| 0.81 ~ | 거의 완벽 |

우리 judge는 0.61로 **간신히 쓸 만한 구간에 진입**했습니다. 82.5%만 봤다면 "충분하다"고 넘겼을 텐데 말이죠. (이 표는 관례적 경험칙이지 법칙은 아닙니다.)

## 함정 ② PASS와 FAIL을 나눠 보세요

|  | judge: PASS | judge: FAIL |
|---|---|---|
| 사람: PASS (14) | 10 | **4** ← 좋은 답을 나쁘다고 함 |
| 사람: FAIL (26) | **3** ← 나쁜 답을 좋다고 함 | 23 |

```
PASS 재현율 = 10/14 = 71.4%   ← 좋은 답변을 알아보는 능력
FAIL 재현율 = 23/26 = 88.5%   ← 나쁜 답변을 잡아내는 능력
```

**judge가 좋은 답변을 잘 못 알아봅니다.** 전체 82.5%만 보면 이게 안 보입니다.

이게 왜 중요하냐면 — 3편에서 프롬프트 A와 B를 비교할 때 **좋아진 답변을 알아보는 능력**이 결정적이기 때문입니다. 나쁜 것만 잘 잡고 좋은 걸 못 알아보면 개선을 측정할 수 없습니다.

> **재현율(recall)** 은 "사람이 PASS라 한 것 중 judge가 PASS를 준 비율"처럼 **한 줄 안에서만** 따지는 비율입니다. `scikit-learn`도 이 이름을 씁니다.

## 함정 ③ 40개는 생각보다 부정확합니다

```
SE = √(0.825 × 0.175 / 40) = 0.060
95% 신뢰구간 ≈ ±2×SE = ±12%p
```

```
82.5% ± 12%p  →  실제 값은 [70%, 94%] 어딘가
```

**rubric을 고쳐서 82.5% → 86%가 됐다면 개선인지 노이즈인지 알 수 없습니다.** 홀드아웃 40~60개에서는 **5%p 이하 변화는 무시**하는 게 안전합니다. 진짜 개선은 보통 두 자릿수로 움직입니다.

## 계산 코드

```python
from collections import Counter

def evaluate_judge(human_labels: dict, judge_labels: dict):
    """양쪽 다 {case_id: "PASS"|"FAIL"|"UNCLEAR"} 형태."""
    # 사람이 PASS/FAIL 로 확정한 케이스가 평가 대상 전체
    scored = [c for c in human_labels if human_labels[c] in ("PASS", "FAIL")]
    # 그중 judge 도 PASS/FAIL 을 준 것만 일치/불일치를 따질 수 있다
    ids = [c for c in scored if judge_labels.get(c) in ("PASS", "FAIL")]
    n = len(ids)
    if n == 0:
        return None

    matrix = Counter((human_labels[c], judge_labels[c]) for c in ids)
    p_o = (matrix[("PASS", "PASS")] + matrix[("FAIL", "FAIL")]) / n

    human = Counter(human_labels[c] for c in ids)
    judge = Counter(judge_labels[c] for c in ids)
    p_e = sum(human[k] * judge[k] for k in ("PASS", "FAIL")) / (n * n)

    # 둘 다 한 종류 라벨만 썼다면 p_e == 1 이라 kappa 는 0/0 - 정의되지 않는다
    kappa = (p_o - p_e) / (1 - p_e) if p_e < 1 else None
    se = (p_o * (1 - p_o) / n) ** 0.5

    # 재현율 분모는 '사람이 그 라벨을 준 전체'. judge 가 UNCLEAR 로 빠져나간
    # 케이스를 분모에서 빼면, 판단을 회피할수록 점수가 올라간다.
    human_all = Counter(human_labels[c] for c in scored)

    return {
        "n": n,
        "agreement": round(p_o, 3),
        "ci95": round(2 * se, 3),
        "kappa": round(kappa, 3) if kappa is not None else None,
        "pass_recall": round(matrix[("PASS", "PASS")] / max(human_all["PASS"], 1), 3),
        "fail_recall": round(matrix[("FAIL", "FAIL")] / max(human_all["FAIL"], 1), 3),
        "judge_unclear": len(scored) - n,
    }
```

```python
>>> evaluate_judge(human_holdout, judge_labels)
{'n': 40, 'agreement': 0.825, 'ci95': 0.12, 'kappa': 0.609,
 'pass_recall': 0.714, 'fail_recall': 0.885, 'judge_unclear': 0}
```

`judge_unclear`를 꼭 보세요. **judge가 UNCLEAR로 도망친 게 많으면 나머지 숫자가 좋아도 의미가 없습니다.** 20%를 넘으면 rubric의 판정 기준이 흐릿하다는 신호입니다.

> 실무에서는 `scikit-learn`의 `cohen_kappa_score`, `classification_report`를 쓰면 됩니다. 위 코드는 안이 어떻게 생겼는지 보여주려고 푼 것입니다.

## 기준점은 어디인가 — 사람끼리는 얼마나 맞나

κ = 0.61이 좋은 건지 나쁜 건지, 절대 기준으로는 알 수 없습니다. **비교 대상이 필요합니다.**

두 번째 사람에게 같은 케이스 30개만 채점하게 하고, 두 사람 사이의 κ를 같은 함수로 계산합니다.

```
사람 A vs 사람 B   κ = 0.68   ← 기준점
judge vs 사람 A    κ = 0.61   ← 사람 수준에 근접. 훌륭함.
```

**사람끼리도 0.68밖에 안 맞는 문제**에서 judge가 0.61이면, 남은 격차는 대부분 **문제 자체의 애매함**이지 judge의 무능이 아닙니다.

반대 상황도 봅시다.

```
사람 A vs 사람 B   κ = 0.35   ← 사람끼리 안 맞음
judge vs 사람 A    κ = 0.30
```

이때 rubric을 아무리 다듬어도 소용없습니다. 문제는 judge가 아니라 **"무엇이 좋은 답변인가"에 팀이 합의하지 못한 것**입니다. 여기서 할 일은 두 사람이 마주 앉아 불일치 케이스 10개를 놓고 기준을 정하는 것입니다.

> **정답지 제작은 한 사람**이 일관되게 하는 게 낫습니다. 여러 명이 매기면 평균이 흐릿해지거든요. 두 번째 사람은 라벨을 늘리려는 게 아니라 **기준점을 재려는 것**이라 30개면 충분합니다.

## 불일치를 읽고 rubric을 고칩니다

여기서부터는 **개발용 60개**로 작업합니다. 홀드아웃은 읽지 않습니다 — 읽고 고치면 그 순간 오염되니까요.

개발용에서 틀린 게 11개 나왔다고 합시다. 그 11개를 직접 읽고 세 부류로 나눕니다.

**① judge가 틀림 — rubric에 조항이 없었다**

```
고객: 어제 받았는데 봉투가 터져서 왔어요
답변: 불편을 드려 죄송합니다. 바로 재발송해 드릴게요.

사람: PASS
judge: FAIL — "구체적인 배송 날짜를 주지 않음 (조건 2)"
```

재발송 상황에서는 날짜를 모를 수 있는데 조건 2를 과하게 적용했습니다. → **rubric에 예외를 추가**합니다.

**② 사람이 틀림 — 기준 표류의 흔적**

```
고객: 환불 언제 되나요
답변: 영업일 기준 3~5일 소요됩니다.

사람: PASS   ← 케이스 3번. 초반에 채점한 것
judge: FAIL
```

나중에 세운 기준으로는 명백히 FAIL인데 초반에 PASS를 줬습니다. → **사람 라벨을 고칩니다.** judge가 맞았습니다.

**③ 진짜 애매함 — 누가 봐도 반반**

```
고객: ㅋㅋㅋ
답변: 😊 더 도와드릴 일이 있으신가요?
```

사람 둘도 갈립니다. → **넘어갑니다.** 이런 케이스 때문에 사람끼리의 κ도 1.0이 안 되는 겁니다.

### 튜닝 루프

```
┌── 개발용 60개 안에서만 반복 ──────────────┐
│  ① 개발용 채점 → 불일치 읽기               │
│  ② rubric 수정 / 사람 라벨 수정 / 넘어가기 │
│  ③ 재채점 → 나아졌는지 확인 ───────────────┤
└────────────────────────────────────────────┘
         ↓ 만족스러우면 딱 한 번
   ④ 홀드아웃 40개로 최종 측정 → 보고할 숫자
```

> **절대 하면 안 되는 것: 홀드아웃의 불일치를 보고 rubric을 고치는 것.** 답을 보고 시험 문제를 고친 셈이라, 다음 측정부터 부풀려진 숫자가 나옵니다. 홀드아웃은 **읽지 말고 숫자만 받으세요.**

**rubric 튜닝에서 가장 효과가 큰 기법**은 1편에서 사람이 쓴 "이상적 답변" 몇 개를 rubric에 예시로 넣는 것입니다. 명백한 케이스 말고 **경계에 있는 케이스**를 고르세요. 단, **예시로 쓴 케이스는 검증에서 빼야 합니다** — 답을 알려주고 시험 보는 셈이니까요.

## judge가 체계적으로 틀리는 다섯 가지

judge는 무작위로 틀리지 않고 **특정 방향으로 일관되게** 틀립니다. 체크리스트로 두세요.

| 편향 | 증상 | 대책 |
|---|---|---|
| **장황함** | 튜닝할수록 답변이 길어짐. 내용이 같아도 긴 쪽을 선호 | rubric에 "길이는 평가 대상 아님" 명시 + **평균 답변 길이를 따로 감시** |
| **자기편애** | judge와 챗봇이 같은 계열 모델 | 다른 계열로 교체. 여러 judge로 κ를 재보고 고르면 됩니다 |
| **아부** | "개선한 프롬프트의 답변이다"처럼 힌트를 줌 | judge에게 **출처를 절대 알리지 않기**. "v1/v2", "기존/신규" 같은 단어 금지 |
| **점수 몰림** | 1~10점을 주면 7~8점에 뭉침 | 선택지를 **2~4개**로 (PASS/FAIL을 쓴 이유) |
| **위치** | 두 답변을 나란히 보여주면 **먼저 나온 쪽**을 선호 | 순서를 바꿔 두 번 묻고 같을 때만 인정 (3편) |

**장황함 편향**만 예를 들어보죠.

```
A: "오늘 오전 출고됐어요. 내일 도착합니다!"
B: "안녕하세요 고객님, 문의 주셔서 감사합니다. 확인 결과 고객님께서
    주문하신 에티오피아 예가체프 200g 상품은 금일 오전 중 물류센터에서
    출고 처리가 완료되었으며, 택배사 배송 일정에 따라 내일 중 수령하실
    수 있을 것으로 예상됩니다. 추가 문의사항은 언제든 말씀해 주세요."

judge: B가 더 낫습니다 — "더 상세하고 정중함"
실제 고객: A가 낫다. B는 읽기 귀찮다.
```

judge는 "성실해 보이는 것"과 "좋은 것"을 잘 구분하지 못합니다. 이 judge로 튜닝하면 **점점 말이 길어지는 챗봇**이 나옵니다.

## 언제 "됐다"고 할 것인가

```
□ κ가 사람-사람 κ의 80~100% 수준
□ PASS 재현율과 FAIL 재현율이 둘 다 70% 이상
   (한쪽만 높으면 judge가 한쪽으로 기울어 있음)
□ judge_unclear 비율이 10% 이하
```

> **이 숫자들은 법칙이 아니라 출발 기준입니다.** 고객에게 나가는 답변을 거르는 용도라면 높게, 개발 중 방향만 보는 용도라면 낮게 잡으세요.

그리고 **숫자에 집착하지 마세요.** κ 0.61과 0.65의 차이보다, **불일치 11개를 읽고 "아 judge가 이 상황을 이렇게 보는구나"를 이해하는 것**이 훨씬 값집니다. 나중에 judge가 이상한 점수를 낼 때 그 감각이 판단을 도와줍니다.
