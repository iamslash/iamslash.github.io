# 6편. 프롬프트 A와 B, 어느 쪽이 나은가

> 시리즈: AI 답변을 채점하는 법 — LLM-as-a-Judge 밑바닥부터
> 이 편에서 배우는 것: 0편에서 던진 질문에 처음부터 끝까지 답하는 전체 절차. 자를 고정하는 순서, 반복 실행이 필요한 이유, 통과율 두 개를 비교하는 것보다 훨씬 강력한 짝비교, 그리고 사람 눈으로 최종 확인하는 단계.

0편의 질문으로 돌아갑니다.

```
[프롬프트 v1] 너는 콩마켓의 고객 상담원이다. 친절하고 간결하게 답하라.

[프롬프트 v2] 너는 콩마켓의 고객 상담원이다. 친절하고 간결하게 답하라.
             + 고객이 로그인 상태라면 주문번호를 묻지 말고
               최근 주문을 먼저 조회해서 안내하라.
```

**v2가 정말 더 나은가?** 이제 답할 수 있습니다.

## 먼저 짚고 갈 것 — 사람 라벨은 v2를 채점하지 않습니다

가장 많이 하는 착각이라 먼저 못 박겠습니다.

사람이 채점한 건 **예전에 콩돌이가 실제로 했던 답변**입니다. v2를 돌리면 콩돌이가 **새 답변**을 만드는데, 그 새 답변에 대한 사람 라벨은 세상에 존재하지 않습니다.

```
❌ v2의 답변을 사람 라벨과 비교한다   ← 불가능. 라벨이 없음.
✅ 사람 라벨로 judge를 검증하고, 검증된 judge가 v1과 v2를 채점한다
```

역할을 다시 정리하면 이렇습니다.

```
사람 라벨  →  judge가 제대로 채점하는지 검증하는 자[尺]
judge     →  v1과 v2의 새 답변을 채점하는 계량기
```

## 0단계 — 준비물

```
데이터셋 D      200개 케이스 (1편)
사람 라벨       100개 (2편)
    ├─ 개발용    60개
    └─ 홀드아웃  40개
rubric R        pointwise (3편)
rubric P        pairwise (5편)
prompt v1       현행
prompt v2       후보
```

## 1단계 — 자를 먼저 고정합니다. v2는 아직 꺼내지 않습니다

**여기서는 v1도 v2도 실행하지 않습니다.** 사람이 라벨을 붙일 때 봤던 **그 답변 그대로**를 judge에게 채점시켜, 사람과 얼마나 맞는지만 봅니다.

2편에서 저장한 라벨 레코드가 `human[case_id] = {"label": ..., "scored_output": ..., ...}` 형태라고 하면 이렇게 됩니다.

```python
# 사람이 실제로 보고 라벨을 매긴 답변을 그대로 judge에게 준다
judge_labels = judge_all(
    cases={cid: dataset[cid] for cid in holdout_ids},
    responses={cid: human[cid]["scored_output"] for cid in holdout_ids},
)

# evaluate_judge 는 {case_id: 라벨} 형태를 받으므로,
# 라벨 레코드에서 label 문자열만 뽑아낸다 (UNCLEAR 는 걸러낼 필요 없다)
human_holdout = {cid: human[cid]["label"] for cid in holdout_ids}

print(evaluate_judge(human_holdout, judge_labels))
# {'n': 40, 'agreement': 0.825, 'ci95': 0.12, 'kappa': 0.609,
#  'pass_recall': 0.714, 'fail_recall': 0.885, 'judge_unclear': 0}
```

> **주의:** judge에게 넘기는 건 `human[cid]["scored_output"]` — **사람이 봤던 바로 그 답변**입니다. 새로 생성한 답변을 넣으면 사람과 judge가 서로 다른 물건을 채점하게 되어 비교가 성립하지 않습니다. 4편에서 강조한 부분입니다.

**판단:**

```
사람-사람 κ = 0.68   (2편에서 잰 기준점)
judge κ    = 0.61   → 사람 수준의 90%. 통과.
```

미달이면 **개발용 60개로** rubric R을 고치고 다시 옵니다. 여기서만 rubric을 고칠 수 있습니다.

통과했으면:

> ### 🔒 **이 시점부터 rubric R과 P는 동결입니다.**
>
> v1/v2 비교가 끝날 때까지 한 글자도 고치지 않습니다.

> **P는 검증된 게 아니라 그냥 고정한 것입니다.** 1단계에서 사람 라벨로 검증한 것은 pointwise rubric **R뿐**입니다. pairwise rubric P는 "어느 쪽이 나은가"를 묻는 형식이라 사람 라벨(PASS/FAIL)과 직접 대조할 수 없어서, **검증 없이 동결만** 합니다. 그래서 5단계의 pairwise 결과는 **보조 근거**이지 단독 판정 근거가 아닙니다. P까지 검증하고 싶다면 사람에게도 같은 두 답변을 나란히 보여주고 고르게 해서 별도의 정답지를 만들어야 합니다.

**왜 이렇게까지 하나?** 자와 측정 대상을 동시에 움직이면, 점수가 올라도 그게 v2가 좋아진 건지 자가 무뎌진 건지 알 수 없기 때문입니다. 프롬프트 튜닝과 rubric 튜닝은 **방향이 정반대**입니다.

```
rubric 튜닝:   사람(고정) ← judge를 맞춘다
프롬프트 튜닝:  judge(고정) ← 챗봇을 맞춘다
```

## 2단계 — v1과 v2를 똑같은 조건으로, 여러 번 실행

```python
runs_v1 = [generate_all(dataset, prompt_v1) for _ in range(3)]
runs_v2 = [generate_all(dataset, prompt_v2) for _ in range(3)]
```

**왜 3번씩 돌리나?** LLM은 같은 입력에도 매번 조금씩 다른 답을 냅니다. 한 번씩만 돌리면 프롬프트 차이인지 그날의 운인지 구분할 수 없습니다.

3회 돌리면 이런 게 보입니다.

```
        1회차   2회차   3회차
v1      61.0%   60.0%   62.0%    → 흔들림 약 ±1%p
v2      74.0%   71.5%   75.0%    → 흔들림 약 ±1.8%p
```

**흔들림 폭이 두 프롬프트의 차이보다 크면 그 차이는 없는 것입니다.** 위 예에서는 흔들림이 2%p 내외인데 차이가 12%p 이상이니 안전합니다.

**나머지는 전부 동일해야 합니다.** 같은 데이터셋, 같은 모델, 같은 온도, 같은 도구 목록. 프롬프트만 다릅니다. 실무에서 흔한 실수가 **"프롬프트 고치는 김에 모델도 최신으로 바꾸는 것"** 인데, 그러면 무엇 때문에 좋아졌는지 영영 모르게 됩니다.

## 3단계 — 동결된 rubric으로 양쪽 채점 (pointwise)

```python
scores_v1 = [judge_all(dataset, run) for run in runs_v1]
scores_v2 = [judge_all(dataset, run) for run in runs_v2]

print(f"v1 통과율: {mean_pass_rate(scores_v1):.1%}")   # 61.0%
print(f"v2 통과율: {mean_pass_rate(scores_v2):.1%}")   # 73.5%
```

```
v1: 61.0%   (3회 평균)
v2: 73.5%
```

12.5%p 차이. 좋아 보이지만 **여기서 결론 내리면 안 됩니다.** 200개 표본에서 두 비율을 비교하는 건 생각보다 무딘 방법입니다.

## 4단계 — 짝비교. 훨씬 강력합니다

통과율 두 개를 비교하는 대신, **같은 케이스에서 판정이 어떻게 바뀌었는지**를 셉니다.

```python
from collections import Counter

def paired_diff(scores_a: dict, scores_b: dict):
    """같은 회차의 두 채점 결과를 짝지어 비교한다.
    두 dict 모두 judge_all() 의 반환값이므로 키 집합이 같아야 한다."""
    if scores_a.keys() != scores_b.keys():
        raise ValueError("두 채점 결과의 케이스 집합이 다릅니다")

    decided = [
        cid for cid in scores_a
        if scores_a[cid] in ("PASS", "FAIL")
        and scores_b[cid] in ("PASS", "FAIL")
    ]
    table = Counter((scores_a[cid], scores_b[cid]) for cid in decided)
    return {
        "improved":  table[("FAIL", "PASS")],   # v2가 고친 것
        "regressed": table[("PASS", "FAIL")],   # v2가 망친 것
        "unchanged": table[("PASS", "PASS")] + table[("FAIL", "FAIL")],
        # 어느 한쪽이라도 UNCLEAR 면 짝을 지을 수 없어 빠진다.
        "skipped":   len(scores_a) - len(decided),
    }
```

`skipped`를 꼭 보세요. **어느 한쪽이라도 UNCLEAR면 그 케이스는 짝비교에서 사라집니다.** `PASS → UNCLEAR`처럼 통과 개수는 줄었는데 `regressed`에는 안 잡히는 변화가 여기 숨습니다. `skipped`가 0이 아니면 그만큼 판정에서 빠졌다는 뜻이니, 몇 개인지는 알고 넘어가야 합니다.

2단계에서 3회씩 돌렸으니, **회차별로 짝을 지어 3번 계산합니다.** 서로 다른 실행끼리 섞어서 비교하면 안 됩니다 — 같은 조건에서 나온 짝이어야 짝비교의 의미가 있습니다.

```python
>>> for i in range(3):
...     print(paired_diff(scores_v1[i], scores_v2[i]))
{'improved': 34, 'regressed': 8, 'unchanged': 158, 'skipped': 0}
{'improved': 32, 'regressed': 9, 'unchanged': 159, 'skipped': 0}
{'improved': 33, 'regressed': 7, 'unchanged': 160, 'skipped': 0}
```

3단계의 통과율과 맞물리는지 확인해 보면, 1회차는 v1이 122개 통과(61.0%)였고 여기서 34개가 살아나고 8개가 죽었으니 `122 + 34 − 8 = 148`, 즉 74.0%입니다.

> **`skipped`가 0이면** "통과 개수의 변화량 = `improved` − `regressed`"가 **보장됩니다.** 위 예가 그런 경우죠.
>
> 반대로 이 등식이 **안 맞는다면 둘 중 하나**입니다 — 다른 회차를 섞었거나, 빠진 케이스(`skipped`) 안에서 통과 개수가 움직였거나. 그러니 등식이 깨졌을 때는 `skipped`부터 보세요. (`skipped`가 0이 아니어도 등식이 우연히 맞을 수는 있습니다 — 양쪽 다 UNCLEAR라 통과 개수에 영향이 없는 경우처럼요. 그래서 `skipped == 0`은 보장 조건이지 등식 성립의 필요조건은 아닙니다.)

**세 회차가 모두 같은 방향을 가리키면 그게 결론입니다.** 한 회차만 v2 우세이고 나머지가 뒤집힌다면, 그건 프롬프트 차이가 아니라 생성의 흔들림입니다.

아래 설명은 1회차(34 대 8)를 기준으로 하겠습니다.

이 표가 훨씬 많은 걸 말해줍니다.

|  | v2: PASS | v2: FAIL |
|---|---|---|
| **v1: PASS** | 114 | **8** ← 망가진 것 |
| **v1: FAIL** | **34** ← 고쳐진 것 | 44 |

**핵심: 변하지 않은 158개는 판단에 아무 기여를 하지 않습니다.** 두 프롬프트가 똑같이 처리한 케이스니까요. 승부는 **34 대 8**에서 갈립니다.

### 이 차이가 진짜인가 — 간단한 판정법

**"두 프롬프트가 똑같이 좋다면, 34 대 8 같은 결과가 나오기 쉬울까?"** 를 따집니다. 동전 던지기로 생각하면 됩니다. 두 프롬프트의 실력이 같다면 바뀐 42개(34+8)는 양쪽에 반반씩 갈려야 하니, 21 대 21 근처가 나와야 하죠.

> **질문의 방향에 주의하세요.** 우리가 계산할 수 있는 건 **"실력이 같다고 가정했을 때 이런 결과가 나올 확률"** 이지, **"이 차이가 우연일 확률"** 이 아닙니다. 둘은 다릅니다. 앞의 것이 아주 작으면 "실력이 같다"는 가정을 버리는 것이고, 그게 우리가 내리는 결론의 전부입니다.

**주먹구구 규칙:**

```
바뀐 개수 = 34 + 8 = 42
흔들림의 크기 ≈ √42 ≈ 6.5

|34 - 8| = 26  vs  2 × 6.5 = 13

26 > 13  →  차이가 진짜다 ✓
```

> **규칙:** `|고쳐진 수 − 망가진 수| > 2 × √(고쳐진 수 + 망가진 수)` 이면 진짜 차이로 봅니다.

몇 가지 예로 감을 잡아보죠.

| 고쳐짐 | 망가짐 | 기준값 | 판정 |
|---|---|---|---|
| 34 | 8 | 13 | **26 > 13 → 진짜** |
| 20 | 14 | 11.7 | 6 < 11.7 → 노이즈 |
| 12 | 2 | 7.5 | 10 > 7.5 → 진짜(간당간당) |
| 5 | 1 | 4.9 | 4 < 4.9 → 판정 불가, 표본 부족 |

이건 통계학에서 **McNemar 검정**이라고 부르는 것의 간이 버전입니다. 정확히 계산하고 싶으면 이렇게 하면 됩니다.

```python
from statsmodels.stats.contingency_tables import mcnemar

result = mcnemar([[114, 8], [34, 44]], exact=False, correction=True)
print(result.pvalue)   # 0.0001
```

이 `0.0001`은 **"두 프롬프트의 실력이 같다면, 지금만큼 또는 이보다 더 치우친 결과가 나올 확률이 0.01%"** 라는 뜻입니다. "v2가 나을 확률이 99.99%"도 아니고 "이 차이가 우연일 확률"도 아닙니다. 흔한 오해라 한 번 더 짚습니다.

## 5단계 — pairwise로 한 번 더 확인 (선택이지만 권장)

pointwise는 "둘 다 PASS"인 케이스를 구분하지 못합니다. v2가 v1보다 훨씬 좋아졌는데 둘 다 PASS라면 그 개선이 숫자에 안 잡히죠.

그래서 5편의 `compare()`를 씁니다.

```python
from collections import Counter

# 짝비교와 마찬가지로 같은 회차끼리 비교한다 (여기서는 1회차)
results = Counter(
    compare(dataset[cid], runs_v1[0][cid], runs_v2[0][cid])
    for cid in dataset
)
```

pairwise는 케이스당 API 호출이 2번(순서 교환) 필요해서 pointwise보다 비쌉니다. **3회차 전부 돌릴 필요는 없고, 1회차만으로 방향을 확인하는 정도면 충분합니다.** 짝비교에서 이미 3회 일관성을 봤으니까요.

```
{'B': 96, 'A': 41, 'TIE': 61, 'ERROR': 2}
```

v2(B)가 96번, v1(A)가 41번 이겼습니다.

**TIE 61개에는 세 종류가 섞여 있습니다.** 5편의 `compare()`가 "두 순서의 결론이 같을 때만 승자를 인정"하기 때문입니다.

- 두 순서 다 진짜 무승부 (`TIE` / `TIE`)
- 순서를 바꾸니 승자가 뒤집힘 (`A` / `B`)
- 한 번은 승자, 한 번은 무승부 (`A` / `TIE` 같은 불안정한 판정)

셋 다 "승부를 가리지 못했다"로 묶은 것이고, 이게 보수적인 처리입니다. 구분해서 보고 싶다면 `compare()`가 두 회차 결과를 그대로 돌려주게 고치면 됩니다.

**`ERROR` 2개는 판정 자체를 못 받은 것**이니 TIE와 따로 세어야 합니다 — 이 값이 전체의 5%를 넘으면 결과를 믿기 전에 원인부터 보세요.

같은 주먹구구 규칙을 적용합니다.

```
|96 - 41| = 55
2 × √(96+41) = 2 × 11.7 = 23.4
55 > 23.4  →  v2 우세 ✓
```

**두 방법이 같은 방향을 가리키면 확신이 커집니다.** 만약 pointwise는 v2 우세인데 pairwise는 무승부라면, 개선이 "FAIL을 겨우 PASS로 넘긴" 수준이라는 뜻입니다.

## 6단계 — 사람 눈으로 확인. 건너뛰지 마세요

숫자가 다 좋아도 이 단계가 남았습니다. **judge를 속인 게 아닌지 확인하는 마지막 관문**입니다.

**볼 것 두 가지.**

**① 고쳐진 34개 중 10개를 무작위로 읽습니다.**

```
[case-0042] 고객(로그인): 어제 주문한 거 아직도 안 왔어요

v1: 주문번호를 알려주시면 확인해 드릴게요!                    judge FAIL
v2: 확인해보니 어제 주문하신 예가체프가 오늘 오전 출고됐어요.
    내일 도착 예정입니다!                                      judge PASS

→ 사람: 그래, 이게 낫다 ✓
```

10개를 읽고 **"그래 이게 낫다"가 8개 이상**이면 통과입니다. 절반이 애매하면 judge가 후한 판정을 하고 있는 것이니 1단계로 돌아가야 합니다.

**② 망가진 8개는 전부 읽습니다.**

이게 더 중요합니다. 개선하면서 뭔가 하나는 거의 항상 망가집니다.

```
[case-0117] 고객(로그인): 주문한 거 언제 오나요?
                          (최근 주문이 5건이나 있는 고객)

v1: 어떤 주문을 말씀하시는 걸까요? 최근 5건이 진행 중이에요.   judge PASS
v2: 가장 최근 주문하신 케냐 AA는 내일 도착 예정입니다!         judge FAIL

→ v2가 "되묻지 마라"를 너무 곧이곧대로 따라서, 주문이 여러 개일 때도
  임의로 하나를 골라버렸다.
```

**이 8개가 다음 라운드의 재료입니다.** v3에서는 이렇게 고치면 되겠죠.

```
+ 고객이 로그인 상태라면 주문번호를 묻지 말고 최근 주문을 조회해서 안내하라.
+ 단, 진행 중인 주문이 여러 건이면 목록을 보여주고 어느 것인지 확인하라.
```

## 7단계 — 결론

네 조건이 모두 맞으면 **"v2가 더 낫다"** 고 말할 수 있습니다.

```
□ 1단계에서 judge가 검증됐고, 이후 rubric이 동결됐다
□ 반복 실행에서 v2 우세가 일관되고, 짝비교 판정 규칙을 통과했다
□ 고쳐진 케이스를 사람이 읽고 납득했다
□ 망가진 케이스가 감수할 만하고, 다음 라운드 과제로 기록됐다
```

**절대 하면 안 되는 것 하나만 다시 강조합니다.**

> **v2의 결과를 보고 rubric을 고치는 것.**
>
> v2가 FAIL 난 걸 보고 "이 조항이 좀 빡센데" 하며 고치는 순간, 자와 측정 대상을 동시에 움직인 겁니다. 고치고 싶어지면 **1단계로 돌아가 사람 라벨로 다시 검증하고, v1과 v2를 처음부터 다시 돌려야** 합니다.

## 배포한 뒤에 할 일

judge 점수가 올랐다고 고객이 행복해진 건 아닙니다. **judge는 우리 팀의 기준을 복제한 것이지, 고객의 마음을 재는 도구가 아닙니다.**

배포 후 두 가지를 하세요.

**하나, 실제 지표와 대조합니다.** 상담 이관율, 재문의율, 만족도 조사 — 무엇이든 비즈니스 지표 하나와 judge 점수가 같은 방향으로 움직이는지 봅니다. 계속 어긋난다면 rubric이 잘못된 것을 재고 있다는 뜻입니다.

**둘, 새 로그로 라벨을 다시 모읍니다.** 챗봇이 바뀌면 실패 양상도 바뀝니다. v2 시대의 대화 50개를 새로 채점해 데이터셋과 홀드아웃을 갱신하세요. 그러지 않으면 judge는 **v1 시대의 문제만 잡는 낡은 자**가 됩니다.

## 전체 흐름 한 장

```
[1] 저장된 답변 + rubric R → 사람 라벨과 대조 → κ 확인 → 🔒 rubric 동결
    (v1도 v2도 실행하지 않는다)                          │
                                                        │
[2] v1 ×3 ┐                                             │
    v2 ×3 ┘→ 같은 데이터셋 D, 프롬프트만 다르게          │
                                                        ↓
[3] 동결된 R로 양쪽 채점 → 통과율 61.0% vs 73.5%        │
                                                        ↓
[4] 짝비교: 고쳐짐 34 / 망가짐 8 → |26| > 2√42 ✓       │
                                                        ↓
[5] pairwise로 교차 확인: 96 vs 41 ✓                    │
                                                        ↓
[6] 사람이 고쳐진 10개 + 망가진 8개 전부 확인           │
                                                        ↓
[7] v2 채택 → 배포 → 실제 지표 대조 → 새 라벨 수집 ────┘
```

## 도구에서는 어떻게 부르나

- **promptfoo** — 이 절차의 2~3단계에 가장 잘 맞습니다. YAML에 프롬프트 두 개를 적으면 격자로 나란히 돌려서 표로 보여줍니다. `repeat` 옵션으로 반복 실행도 됩니다.
- **Langfuse** — 프롬프트 버전별 `Experiment`를 만들어 같은 데이터셋에 돌리고 결과를 비교합니다. 프롬프트 버전 관리가 붙어 있어 "어느 버전으로 잰 숫자인지"가 자동으로 남습니다.
- **짝비교와 McNemar** — 도구가 거의 지원하지 않습니다. 결과를 CSV로 내려받아 위 `paired_diff()` 코드로 직접 계산하세요.

**도구는 2~3단계(실행과 채점)를 자동화해주고, 1단계(judge 검증)와 4~6단계(판정과 육안 확인)는 대체로 직접 해야 합니다.** 그리고 그 부분이 이 절차에서 가장 중요한 부분이기도 합니다.

## 한 줄 정리

**자를 먼저 검증하고 동결한 다음, 두 프롬프트를 같은 데이터셋에 여러 번 돌려 채점하고, 통과율 대신 짝비교(고쳐진 수 대 망가진 수)로 판정하며, 마지막에 반드시 사람이 눈으로 확인합니다.** 그리고 배포 후에는 실제 지표와 대조하고 새 라벨을 모아 자를 갱신합니다.
