# 4편. judge를 믿어도 되는가

> 시리즈: AI 답변을 채점하는 법 — LLM-as-a-Judge 밑바닥부터
> 이 편에서 배우는 것: 일치율을 계산하는 법과 그 숫자가 왜 부풀려지는지, 우연을 걷어내는 Cohen's kappa, PASS와 FAIL을 각각 따로 봐야 하는 이유, 홀드아웃 분리, 그리고 "이 정도면 됐다"를 언제 선언할 것인가.

이 편이 시리즈의 심장입니다. 3편까지는 누구나 반나절이면 합니다. **실무에서 사고가 나는 건 이 편을 건너뛰기 때문**입니다.

## 무엇을 어떻게 비교하는가

우리가 가진 것은 이렇습니다.

```
사람 라벨   100개   (2편에서 만듦)
   ├─ 개발용  60개  ← rubric 고칠 때 쓴 것. few-shot 예시도 여기서 뽑음
   └─ 홀드아웃 40개  ← judge에게 한 번도 안 보여준 것
```

**두 묶음은 쓰임이 완전히 다릅니다.** 먼저 이걸 못 박고 갑니다.

| | 개발용 60개 | 홀드아웃 40개 |
|---|---|---|
| 언제 쓰나 | 개선하는 내내, 몇 번이든 | **각 라운드의 맨 마지막에 딱 한 번** |
| 무엇에 쓰나 | 불일치를 읽고 rubric 고치기 | 최종 점수 측정 |
| few-shot 예시로 뽑아도 되나 | 된다 | **절대 안 된다** |

앞으로 나올 계산 방법은 두 묶음에 똑같이 적용합니다. **다만 "숫자를 보고 rubric을 고치는" 행위는 개발용에서만** 하고, 홀드아웃은 다 끝난 뒤 성적표를 받는 용도입니다. 이 구분이 이 편의 핵심이고, 뒤에서 다시 강조합니다.

아래 예시는 **홀드아웃 40개로 낸 최종 성적표**입니다.

> **⚠️ 반드시 지킬 것: judge와 사람이 같은 답변을 채점해야 합니다.**
>
> 사람은 운영 로그에 있던 그 답변을 보고 라벨을 붙였습니다. judge에게 새로 생성한 답변을 채점시키면 **다른 물건을 비교하는 셈**이 됩니다. 2편에서 `scored_output` 필드를 저장하라고 한 이유가 이것입니다. 그 문자열을 그대로 judge에게 넘기세요.

## 혼동행렬 — 표 하나로 시작합니다

40개를 채점한 결과를 2×2 표로 정리합니다. 이걸 **혼동행렬(confusion matrix)** 이라고 부릅니다.

|  | judge: PASS | judge: FAIL | 합계 |
|---|---|---|---|
| **사람: PASS** | **10** | 4 | 14 |
| **사람: FAIL** | 3 | **23** | 26 |
| **합계** | 13 | 27 | 40 |

대각선(굵은 숫자)이 일치한 것, 나머지가 불일치입니다.

```
일치율 = (10 + 23) / 40 = 33/40 = 82.5%
```

82.5%. 나쁘지 않아 보입니다. **그런데 이 숫자를 그대로 믿으면 안 됩니다.**

## 함정 하나 — 아무렇게나 찍어도 65%

이 데이터에서 사람 라벨은 PASS 14개, FAIL 26개입니다. FAIL이 65%죠. 2편에서 어려운 케이스를 많이 넣었기 때문입니다.

이제 **아무 생각 없이 무조건 FAIL만 외치는 바보 judge**를 만들어 봅시다.

```python
def dumb_judge(case, response):
    return "FAIL"   # 끝
```

이 judge의 일치율은 얼마일까요? 사람이 FAIL이라 한 26개를 전부 맞히니까 **26/40 = 65%** 입니다.

```
바보 judge:  65%
우리 judge:  82.5%
```

우리 judge가 대단해 보였는데, **출발선이 이미 65%** 였습니다. 실제로 벌어들인 건 17.5%p뿐이죠.

이게 **클래스 불균형(class imbalance)** 문제입니다. 한쪽 라벨이 많을수록 일치율은 저절로 부풀려집니다. 그래서 이 숫자를 그대로 보고하면 안 됩니다.

## Cohen's kappa — 우연을 걷어낸 일치율

이 문제를 해결하려고 만든 게 **Cohen's kappa(κ)** 입니다. 아이디어는 단순합니다.

> **"우연히 맞을 만큼은 빼고, 그 이상 얼마나 잘 맞혔나"**

공식은 이렇습니다.

```
        p_o - p_e
  κ =  -----------
         1 - p_e

  p_o = 실제 일치율 (observed)
  p_e = 우연히 일치할 확률 (expected by chance)
```

`p_e`를 어떻게 구할까요. 사람과 judge가 서로 무관하게 라벨을 뿌린다고 가정하고, 각자의 비율을 곱해서 더합니다.

```
사람이 PASS 줄 확률 = 14/40 = 0.35
judge가 PASS 줄 확률 = 13/40 = 0.325
→ 둘 다 우연히 PASS일 확률 = 0.35 × 0.325 = 0.114

사람이 FAIL 줄 확률 = 26/40 = 0.65
judge가 FAIL 줄 확률 = 27/40 = 0.675
→ 둘 다 우연히 FAIL일 확률 = 0.65 × 0.675 = 0.439

p_e = 0.114 + 0.439 = 0.553
```

이제 대입합니다.

```
      0.825 - 0.553     0.272
κ =  --------------- = ------- = 0.61
      1 - 0.553         0.447
```

**κ = 0.61.** 82.5%가 0.61로 바뀌었습니다. 훨씬 겸손한 숫자죠.

### κ를 어떻게 읽나

관례적으로 쓰이는 해석표입니다. (엄밀한 법칙이 아니라 경험칙입니다.)

| κ | 해석 |
|---|---|
| ~0.20 | 거의 우연 수준 |
| 0.21 ~ 0.40 | 약함 |
| 0.41 ~ 0.60 | 보통 |
| **0.61 ~ 0.80** | **상당히 일치 — 실무에서 쓸 만한 구간** |
| 0.81 ~ 1.00 | 거의 완벽 |

우리 judge는 0.61로 **간신히 쓸 만한 구간에 진입**했습니다. 82.5%라는 숫자만 봤다면 "충분하다"고 판단했을 텐데, 실제로는 아슬아슬합니다.

## 함정 둘 — PASS와 FAIL을 나눠 보세요

혼동행렬을 다시 봅시다.

|  | judge: PASS | judge: FAIL |
|---|---|---|
| 사람: PASS (14개) | 10 | **4** ← 좋은 답변을 나쁘다고 함 |
| 사람: FAIL (26개) | **3** ← 나쁜 답변을 좋다고 함 | 23 |

각 줄에서 얼마나 맞혔는지 따로 계산합니다.

```
PASS 재현율 = 10/14 = 71.4%   ← 좋은 답변을 알아보는 능력
FAIL 재현율 = 23/26 = 88.5%   ← 나쁜 답변을 잡아내는 능력
```

**재현율(recall)** 은 "사람이 PASS라고 한 것 중 judge가 PASS를 준 비율"처럼 **한 줄 안에서만** 따지는 비율입니다. 전체 정답률(accuracy)과는 다르고, `scikit-learn`도 이 이름을 씁니다.

**judge가 좋은 답변을 잘 못 알아봅니다.** 14개 중 4개를 억울하게 FAIL 처리했죠.

전체 일치율 82.5%만 보면 이게 안 보입니다. **불균형한 데이터에서는 다수 클래스의 성적이 전체 숫자를 지배**하기 때문입니다.

이게 왜 중요한가 하면 — 6편에서 프롬프트 A와 B를 비교할 때, **좋아진 답변을 알아보는 능력**이 결정적이기 때문입니다. 나쁜 걸 잡아내기만 잘하고 좋은 걸 못 알아보는 judge로는 개선을 측정할 수 없습니다.

> **보고할 때는 세 숫자를 함께 쓰세요: κ, PASS 재현율, FAIL 재현율.**

## 함정 셋 — 40개는 생각보다 부정확합니다

82.5%라는 숫자가 얼마나 흔들릴까요? 표준오차를 계산해봅니다.

```
SE = √(p(1-p)/n) = √(0.825 × 0.175 / 40) = √0.0036 = 0.060
```

95% 신뢰구간은 대략 ±2×SE이니 **±12%p**입니다.

> 이건 가장 단순한 계산법(Wald 방식)입니다. 비율이 0이나 1에 아주 가깝거나 n이 30 미만이면 실제보다 좁게 나오니, **정확한 값이 아니라 자릿수 감각을 잡는 용도**로 쓰세요.

```
82.5% ± 12%p  →  실제 값은 [70%, 94%] 어딘가
```

폭이 꽤 넓습니다. **rubric을 고쳐서 82.5% → 86%가 됐다면, 그건 개선인지 노이즈인지 알 수 없습니다.**

홀드아웃을 키우면 좁아집니다.

| 홀드아웃 크기 | 95% 신뢰구간 폭 |
|---|---|
| 40 | 약 ±12%p |
| 100 | 약 ±8%p |
| 200 | 약 ±5%p |

그래서 2편에서 "100~150개 라벨"이라고 한 것입니다. 그중 40~60을 홀드아웃으로 떼면 위 표의 중간쯤이 됩니다.

**실무 감각(경험칙):** 홀드아웃 40~60개에서는 **5%p 이하의 변화는 무시**하는 편이 안전합니다. 위 신뢰구간 폭에서 나온 어림이지 정해진 규칙은 아닙니다. 진짜 개선은 보통 두 자릿수로 움직입니다.

## 계산 코드

위의 모든 걸 한 번에 계산합니다.

```python
from collections import Counter

def evaluate_judge(human_labels: dict, judge_labels: dict):
    """
    human_labels: {case_id: "PASS"|"FAIL"|"UNCLEAR"}
    judge_labels: {case_id: "PASS"|"FAIL"|"UNCLEAR"}

    양쪽 다 UNCLEAR 를 담을 수 있다. 사람이 UNCLEAR 를 준 케이스는
    정답이 없으므로 평가 대상(scored)에서 통째로 빠지고,
    judge 만 UNCLEAR 인 경우는 judge_unclear 로 따로 센다.
    """
    # 사람이 PASS/FAIL 로 확정한 케이스 전체가 평가 대상
    scored = [cid for cid in human_labels if human_labels[cid] in ("PASS", "FAIL")]
    # 그중 judge 도 PASS/FAIL 을 준 것만 일치/불일치를 따질 수 있다
    ids = [cid for cid in scored if judge_labels.get(cid) in ("PASS", "FAIL")]
    n = len(ids)
    if n == 0:
        return None

    matrix = Counter((human_labels[c], judge_labels[c]) for c in ids)
    agree = matrix[("PASS", "PASS")] + matrix[("FAIL", "FAIL")]
    p_o = agree / n

    human = Counter(human_labels[c] for c in ids)
    judge = Counter(judge_labels[c] for c in ids)
    p_e = sum(human[k] * judge[k] for k in ("PASS", "FAIL")) / (n * n)

    # 두 채점자가 각각 한 종류 라벨만 썼다면 p_e == 1 이 되고 kappa 는 0/0 -
    # 정의되지 않는다. 1.0(완벽)으로 뭉개면 안 된다.
    kappa = (p_o - p_e) / (1 - p_e) if p_e < 1 else None
    se = (p_o * (1 - p_o) / n) ** 0.5

    # 재현율의 분모는 '사람이 그 라벨을 준 전체'다. judge 가 UNCLEAR 로
    # 빠져나간 케이스를 분모에서 빼면 재현율이 부풀려진다.
    human_all = Counter(human_labels[c] for c in scored)

    return {
        "n": n,
        "agreement": round(p_o, 3),
        "ci95": round(2 * se, 3),
        "kappa": round(kappa, 3) if kappa is not None else None,
        "pass_recall": round(matrix[("PASS", "PASS")] / max(human_all["PASS"], 1), 3),
        "fail_recall": round(matrix[("FAIL", "FAIL")] / max(human_all["FAIL"], 1), 3),
        "judge_unclear": len(scored) - n,
    }
```

```python
>>> evaluate_judge(human, judge_out)
{'n': 40, 'agreement': 0.825, 'ci95': 0.12, 'kappa': 0.609,
 'pass_recall': 0.714, 'fail_recall': 0.885, 'judge_unclear': 0}
```

> **재현율의 분모에 UNCLEAR도 포함되는 이유**
>
> judge가 UNCLEAR를 준 케이스를 분모에서 빼면, **판단을 회피할수록 재현율이 올라갑니다.** 모르겠으면 UNCLEAR를 외치는 judge가 최고 점수를 받게 되죠. 그래서 분모는 `human_all` — **사람이 그 라벨을 준 전체**로 잡습니다. 회피는 실패로 계산됩니다.

> **`pass_accuracy`가 아니라 `pass_recall`인 이유**
>
> "사람이 PASS라 한 것 중 judge가 맞힌 비율"은 통계에서 **재현율(recall)** 이라고 부릅니다. `scikit-learn`의 `classification_report`를 돌리면 이 이름으로 나오니, 미리 맞춰두는 게 나중에 헷갈리지 않습니다. (accuracy는 전체 정답률 — 위의 `agreement`가 그것입니다.)

`judge_unclear`를 꼭 확인하세요. **judge가 UNCLEAR로 도망친 케이스가 많으면 나머지 숫자가 좋아도 의미가 없습니다.** 20%를 넘으면 rubric의 판정 기준이 흐릿하다는 신호입니다.

## 기준점은 어디인가 — 사람끼리는 얼마나 맞나

κ = 0.61이 좋은 건지 나쁜 건지, 절대 기준으로는 알 수 없습니다. **비교 대상이 있어야 합니다.**

2편에서 두 번째 사람이 30개를 겹쳐 채점했죠. 그 두 사람 사이의 κ를 같은 함수로 계산합니다.

```
사람 A vs 사람 B   κ = 0.68   ← 기준점
judge vs 사람 A    κ = 0.61   ← 사람 수준에 근접
```

**이러면 훌륭한 judge입니다.** 사람끼리도 0.68밖에 안 맞는 문제에서 judge가 0.61이면, 남은 격차는 대부분 **문제 자체의 애매함**이지 judge의 무능이 아닙니다.

반대 상황도 봅시다.

```
사람 A vs 사람 B   κ = 0.35   ← 사람끼리 안 맞음
judge vs 사람 A    κ = 0.30
```

이때 rubric을 아무리 다듬어도 소용없습니다. **문제는 judge가 아니라 "무엇이 좋은 답변인가"에 팀이 합의하지 못한 것**입니다. 여기서 할 일은 rubric 튜닝이 아니라 **두 사람이 마주 앉아 불일치 케이스 10개를 놓고 기준을 정하는 것**입니다.

> **자가 흔들리면 그 자로 잰 모든 숫자가 무의미합니다.** 이 점검을 먼저 하세요.

## 불일치 케이스를 읽는 법

여기서부터는 **개발용 60개**로 작업합니다. 같은 방식으로 채점해서 틀린 게 11개 나왔다고 합시다. 그 11개를 직접 읽는 것이 실제 작업입니다.

> **왜 홀드아웃이 아니라 개발용인가?** 불일치를 읽는 목적은 rubric을 고치기 위해서입니다. 홀드아웃을 보고 고치면 그 순간 홀드아웃이 오염됩니다(이 편 마지막에서 다시 설명합니다). **홀드아웃은 읽지 말고, 숫자만 받으세요.**

각 케이스를 세 부류로 나눕니다.

**① judge가 틀림 — rubric에 조항이 없었다**

```
고객: 어제 받았는데 봉투가 터져서 왔어요
답변: 불편을 드려 죄송합니다. 바로 재발송해 드릴게요.

사람: PASS
judge: FAIL — "구체적인 배송 날짜를 주지 않음 (조건 2)"
```

judge가 조건 2를 과하게 적용했습니다. 재발송 상황에서는 날짜를 모를 수 있는데 말이죠. → **rubric에 예외를 추가**합니다.

**② 사람이 틀림 — 기준 표류의 흔적**

```
고객: 환불 언제 되나요
답변: 영업일 기준 3~5일 소요됩니다.

사람: PASS   ← 케이스 3번. 초반에 채점한 것
judge: FAIL
```

2편의 criteria drift입니다. 나중에 세운 기준으로는 명백히 FAIL인데, 초반에 PASS를 줬습니다. → **사람 라벨을 고칩니다.** judge가 맞았습니다.

**③ 진짜 애매함 — 누가 봐도 반반**

```
고객: ㅋㅋㅋ
답변: 😊 더 도와드릴 일이 있으신가요?
```

이건 사람 둘도 갈립니다. → **건드리지 말고 넘어갑니다.** 이런 케이스 때문에 사람끼리의 κ도 1.0이 안 되는 것입니다.

**11개를 분류해보면 대개 ①이 절반, ②가 몇 개, ③이 나머지**입니다.

```
│  ② 부류별로 처리                             │
│     (rubric 수정 / 사람 라벨 수정 / 넘어가기)│
│        ↓                                     │
│  ③ 개발용으로 재채점 → 나아졌는지 확인       │
│        ↓                                     │
│     만족스럽지 않으면 ①로 ───────────────────┤
└──────────────────────────────────────────────┘
         ↓ 만족스러우면 딱 한 번
   ④ 홀드아웃 40개로 최종 측정 → 이게 보고할 숫자
```

**여기서 절대 하면 안 되는 것:**

> **홀드아웃 40개의 불일치를 보고 rubric을 고치는 것.**

그 순간 홀드아웃은 더 이상 홀드아웃이 아닙니다. 답을 보고 시험 문제를 고친 셈이라, 다음 측정부터는 부풀려진 숫자가 나옵니다.

rubric 수정은 **개발용 60개**로만 하세요. 홀드아웃은 **각 라운드의 맨 마지막에 딱 한 번** 재는 자입니다.

> **홀드아웃을 너무 자주 쓰는 것도 문제입니다.** 열 번 스무 번 반복해서 재면 결국 홀드아웃에도 맞춰집니다. 라운드를 몇 번 돌 계획이라면, 라벨을 더 모아서 **새 홀드아웃을 준비**하는 게 안전합니다.

## 언제 "됐다"고 할 것인가

세 조건이 다 맞으면 judge를 실전에 투입할 수 있습니다.

```
□ κ가 사람-사람 κ의 80~100% 수준에 도달
□ PASS 재현율과 FAIL 재현율이 둘 다 70% 이상
   (한쪽만 높으면 그 judge는 한쪽으로 기울어 있음)
□ judge_unclear 비율이 10% 이하
```

> **이 숫자들은 법칙이 아니라 출발 기준입니다.** 어디에도 "κ 0.61 이상이면 통과"라고 정해둔 곳은 없습니다. 위 세 줄은 **이 시리즈가 제안하는 시작점**이고, 몇 라운드 돌려보면 여러분의 제품에 맞는 선이 생깁니다. 고객에게 나가는 답변을 거르는 용도라면 기준을 높게, 개발 중 방향만 보는 용도라면 낮게 잡으면 됩니다.

**숫자에 집착하지 마세요.** κ 0.61과 0.65의 차이보다, **개발용 불일치 11개를 읽고 "아 judge가 이 상황을 이렇게 보는구나"를 이해하는 것**이 훨씬 값집니다. 나중에 judge가 이상한 점수를 낼 때 그 감각이 판단을 도와줍니다.

## 도구에서는 어떻게 부르나

이 단계는 도구 지원이 가장 약한 영역입니다. 대부분의 평가 도구가 사람 라벨과 judge 라벨을 각각 저장은 하지만, **둘을 대조해서 κ를 계산해주는 기능은 흔치 않습니다.**

- **Langfuse / LangSmith** — 사람 점수와 judge 점수를 같은 trace에 붙일 수 있어 데이터는 모입니다. 대조 분석은 보통 직접 SQL이나 노트북으로 합니다.
- **scikit-learn** — `cohen_kappa_score`, `confusion_matrix`, `classification_report`가 위 코드를 대체합니다. 실무에서는 이걸 쓰세요.

```python
from sklearn.metrics import cohen_kappa_score, classification_report

print(cohen_kappa_score(human_list, judge_list))
print(classification_report(human_list, judge_list))
```

**"judge 검증은 직접 노트북으로 한다"** 가 현재의 표준에 가깝습니다. 어렵지 않고, 위 코드 30줄이면 됩니다.

## 한 줄 정리

judge를 사람 라벨과 대조하되, **일치율은 클래스 불균형 때문에 부풀려지므로 Cohen's kappa로 우연을 걷어내고**, PASS·FAIL 재현율을 **따로** 보며, **사람끼리의 일치율을 기준점 삼아** 판단합니다. **불일치를 읽고 rubric을 고치는 일은 개발용 데이터에서만** 하고, **홀드아웃은 각 라운드의 마지막에 한 번만** 재세요.
