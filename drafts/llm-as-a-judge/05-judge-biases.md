# 5편. judge의 함정 — 편향과 pairwise

> 시리즈: AI 답변을 채점하는 법 — LLM-as-a-Judge 밑바닥부터
> 이 편에서 배우는 것: LLM judge가 체계적으로 틀리는 다섯 가지 방식(위치·장황함·자기편애·아부·점수 몰림), 각각의 완화 대책, 그리고 두 답변을 직접 비교하는 pairwise 방식이 언제 pointwise보다 나은가.

4편에서 judge를 검증하는 법을 배웠습니다. 그런데 **judge는 무작위로 틀리지 않고, 특정 방향으로 일관되게 틀립니다.** 이런 걸 **편향(bias)** 이라고 부르고, 미리 알면 대부분 막을 수 있습니다.

이 편은 외우기보다 **체크리스트로 두고 필요할 때 돌아오는 용도**로 쓰세요.

## 편향 ① 위치 편향 (position bias)

두 답변을 나란히 놓고 "어느 쪽이 나은가"를 물으면, **judge는 먼저 제시된 쪽을 더 좋아합니다.**

```
[질문 1]
답변 1: (v1이 만든 답)
답변 2: (v2가 만든 답)
→ judge: "답변 1이 낫습니다"

[질문 2]  ← 순서만 바꿈
답변 1: (v2가 만든 답)
답변 2: (v1이 만든 답)
→ judge: "답변 1이 낫습니다"     ← 또 앞에 있는 걸 골랐다!
```

같은 두 답변인데 **순서만 바꿨더니 승자가 뒤집혔습니다.** 이건 판단이 아니라 자리 때문입니다.

Wang 등이 2023년 *"Large Language Models are not Fair Evaluators"* 에서 이 현상을 체계적으로 보고했고, MT-Bench 논문(Zheng et al., 2023)도 같은 문제를 다룹니다.

**대책: 순서를 바꿔 두 번 묻고, 두 번 다 같은 답이 나올 때만 인정합니다.**

```
A 먼저 → A 승
B 먼저 → A 승     → A의 승리로 인정 ✓

A 먼저 → A 승
B 먼저 → B 승     → 무승부 처리 (판정 불가) ✗
```

호출이 두 배가 되지만, 이걸 안 하면 pairwise 결과는 믿을 수 없습니다. 뒤에 코드로 정리합니다.

> pointwise(답변 하나만 놓고 PASS/FAIL)에서는 이 편향이 없습니다. 비교할 상대가 없으니까요.

## 편향 ② 장황함 편향 (verbosity bias)

**judge는 긴 답변을 좋아합니다.** 내용이 같아도요.

```
답변 A: "오늘 오전 출고됐어요. 내일 도착합니다!"

답변 B: "안녕하세요 고객님, 문의 주셔서 감사합니다. 확인 결과
        고객님께서 주문하신 에티오피아 예가체프 200g 상품은
        금일 오전 중 물류센터에서 출고 처리가 완료되었으며,
        택배사 배송 일정에 따라 내일 중 수령하실 수 있을 것으로
        예상됩니다. 추가로 궁금하신 점이 있으시면 언제든지
        문의해 주시기 바랍니다. 감사합니다."

judge: B가 더 낫습니다 — "더 상세하고 정중함"
실제 고객: A가 낫다. B는 읽기 귀찮다.
```

judge는 "성실해 보이는 것"과 "좋은 것"을 잘 구분하지 못합니다. 챗봇 프롬프트를 이 judge로 튜닝하면 **점점 말이 길어지는 챗봇**이 나옵니다.

**대책 두 가지.**

첫째, **rubric에 명시적으로 못 박습니다.** 3편에서 "평가하지 말 것"에 길이를 넣은 이유입니다.

```
## 평가하지 말 것
- 답변 길이는 평가 대상이 아니다. 짧아도 필요한 정보가 있으면 PASS.
- 정중한 인사말의 유무는 평가 대상이 아니다.
```

둘째, **길이를 따로 재서 감시합니다.** judge 점수와 별개로 평균 답변 길이를 기록해두면, 프롬프트를 튜닝하면서 길이가 슬금슬금 늘어나는 걸 잡을 수 있습니다.

```python
metrics = {
    "pass_rate": 0.74,
    "avg_response_chars": 187,   # ← 이것도 같이 봅니다
}
```

## 편향 ③ 자기편애 (self-preference)

**LLM은 자기가 만들었을 법한 답변을 더 좋게 평가합니다.**

Panickssery 등이 2024년 *"LLM Evaluators Recognize and Favor Their Own Generations"* 에서 보인 결과입니다. 모델은 자기 출력을 어느 정도 알아보고, 그것에 더 높은 점수를 줍니다. Zheng 등의 MT-Bench 논문에서는 이를 **self-enhancement bias**라고 부릅니다.

콩마켓 상황으로 옮기면 이렇습니다.

```
콩돌이   = Gemini 기반
judge   = Gemini 기반

→ judge는 Gemini스러운 답변에 후한 점수를 준다
→ 프롬프트를 튜닝할수록 "Gemini가 좋아하는 답"에 수렴
→ 고객 만족도와는 무관하게 점수만 오른다
```

**대책: judge 모델과 챗봇 모델을 다른 계열로 두세요.** 3편에서 말한 원칙이 여기 근거가 있습니다. 같은 회사 모델을 써야 한다면 최소한 다른 크기·다른 세대를 쓰세요.

**확인 방법:** 4편의 검증을 **judge 모델을 바꿔가며** 해보면 됩니다. 사람 라벨과의 κ가 모델마다 얼마나 다른지 보면, 어느 judge가 우리 팀 기준에 가까운지 바로 나옵니다. 라벨 100개가 있으면 이 실험은 몇 분이면 끝납니다.

## 편향 ④ 아부 (sycophancy)

**judge에게 힌트를 주면 그쪽으로 기웁니다.**

```
❌ "아래는 우리 팀이 새로 개선한 프롬프트의 답변이다. 평가하라."
❌ "이전 버전보다 나아졌는지 평가하라."
❌ "전문가가 작성한 모범 답안이다. 문제가 있는지 확인하라."
```

첫 번째는 "개선한"이라는 단어 때문에 후해집니다. 두 번째는 "나아졌는지"라고 물었으니 나아졌다고 답할 확률이 올라갑니다. 세 번째는 "전문가"라는 권위에 눌립니다.

**대책: judge에게 답변의 출처를 절대 알리지 마세요.**

```
✅ "아래 고객 상담 답변을 rubric에 따라 평가하라."
```

A/B 비교를 할 때도 마찬가지입니다. `답변 1`, `답변 2`처럼 **중립적인 이름**을 쓰고, "v1", "v2", "기존", "신규" 같은 단어를 넣지 마세요. 실험자 자신이 무의식적으로 힌트를 흘리는 경우가 의외로 많습니다.

## 편향 ⑤ 점수 몰림

0편과 2편에서 언급한 이야기의 근거입니다. judge에게 1~10점을 매기라고 하면 이런 분포가 나옵니다.

```
1점  ▏
2점  ▏
3점  ▎
4점  ▍
5점  ██
6점  ████
7점  ████████████
8점  ██████████████████
9점  ████
10점 ▎
```

**7~8점에 몰립니다.** 극단을 피하는 성향 때문인데, 결과적으로 우리가 구분하고 싶은 좋고 나쁨의 차이가 좁은 구간에 눌려버립니다.

**대책: 선택지를 줄이세요.** PASS/FAIL 이진, 넓어야 3~4단계. 3편에서 이진 판정을 쓴 이유입니다.

굳이 점수가 필요하면 **판정을 먼저 받고 그 안에서 점수를 받는 2단계**로 하세요. "FAIL 중에서 얼마나 나쁜가(0.0~0.3)"처럼 범위를 묶어주면 몰림이 줄어듭니다.

## pointwise vs pairwise — 언제 무엇을

지금까지의 judge는 전부 **pointwise**였습니다. 답변 하나를 놓고 PASS/FAIL을 매기는 방식이죠. 다른 방식이 하나 더 있습니다.

**pairwise**는 두 답변을 나란히 놓고 "어느 쪽이 나은가"를 묻습니다.

```
[pointwise]
답변 A → PASS
답변 B → PASS        → 둘 다 통과. 어느 쪽이 나은지는 모름.

[pairwise]
답변 A vs 답변 B → "B가 낫다"   → 미세한 차이도 잡힘
```

### 어떻게 다른가

| | pointwise | pairwise |
|---|---|---|
| 묻는 것 | "이거 괜찮나?" | "둘 중 어느 쪽?" |
| 강점 | 절대 기준. 시간이 지나도 비교 가능 | 미세한 차이 감지에 강함 |
| 약점 | 둘 다 PASS면 구분 불가 | 위치 편향. 절대 품질은 모름 |
| 호출 수 | 케이스당 1회 | 케이스당 2회(순서 바꿔서) |
| 어울리는 용도 | **회귀 검사, 배포 게이트** | **A/B 승부 판정** |

**중요한 차이 하나:** pairwise는 **절대 품질을 말해주지 않습니다.** "B가 A보다 낫다"는 알아도, B가 고객에게 내보낼 만한 수준인지는 모릅니다. 둘 다 형편없어도 승자는 나오니까요.

> **실무 권장: 둘 다 쓰세요.**
> - **pointwise**로 "고객에게 나가도 되는 수준인가"를 지키고 (배포 게이트)
> - **pairwise**로 "A와 B 중 뭐가 나은가"를 판정합니다 (개선 판단)

6편에서 이 조합을 실제 절차로 씁니다.

### pairwise judge 코드 — 순서 바꾸기 포함

```python
from typing import Literal
from pydantic import BaseModel

# 3편에서 만든 것들을 그대로 씁니다.
#   client — openai.OpenAI() 인스턴스
#   render(case) — 케이스의 '상황'을 문자열로 만드는 함수
from judge_kit import client, render

class Comparison(BaseModel):
    reasoning: str
    winner: Literal["FIRST", "SECOND", "TIE"]   # 마지막 필드 (3편 규칙)


PAIRWISE_RUBRIC = """당신은 콩마켓의 고객 상담 품질 검수자다.
같은 상황에 대한 두 개의 답변을 비교한다.

## 판단 기준 (우선순위 순)
1. 고객이 물은 것에 실제로 답했는가
2. 조회 가능한 정보를 되묻지 않았는가
3. 구체적인 날짜/조치를 제시했는가

## 판단하지 말 것
- 길이. 짧은 쪽이 필요한 정보를 담았다면 그쪽이 낫다.
- 말투, 이모지, 인사말.
- 당신의 문체 취향.

우열을 가릴 수 없으면 TIE.
"""


def _ask(case, first: str, second: str) -> str | None:
    """FIRST | SECOND | TIE 중 하나. 판정 실패면 None."""
    completion = client.chat.completions.parse(
        model="gpt-4.1-mini",
        temperature=0,
        messages=[
            {"role": "system", "content": PAIRWISE_RUBRIC},
            {"role": "user", "content":
                f"## 상황\n{render(case)}\n\n"
                f"## 답변 1\n{first}\n\n"
                f"## 답변 2\n{second}"},
        ],
        response_format=Comparison,
    )
    parsed = completion.choices[0].message.parsed
    return parsed.winner if parsed is not None else None   # 실패는 None


def compare(case, resp_a: str, resp_b: str) -> str:
    """위치 편향을 제거한 비교. 'A' | 'B' | 'TIE' | 'ERROR' 를 반환."""
    r1 = _ask(case, resp_a, resp_b)   # 1회차: A가 앞
    r2 = _ask(case, resp_b, resp_a)   # 2회차: B가 앞

    # 판정 실패(모델 거부·파싱 실패)를 무승부와 섞지 않는다.
    # 섞으면 "우열이 없었다"와 "물어보지 못했다"가 구별되지 않는다.
    if r1 is None or r2 is None:
        return "ERROR"

    v1 = {"FIRST": "A", "SECOND": "B", "TIE": "TIE"}[r1]
    v2 = {"FIRST": "B", "SECOND": "A", "TIE": "TIE"}[r2]   # 자리를 바꿨으니 해석도 뒤집는다

    return v1 if v1 == v2 else "TIE"   # 두 번 다 같을 때만 승자 인정
```

마지막 줄이 핵심입니다. **두 순서에서 결론이 다르면 무승부로 처리**합니다. 이렇게 하면 위치 편향으로 생긴 가짜 승리가 걸러집니다.

그리고 그 위의 `ERROR` 분기도 그냥 넘기지 마세요. 실패를 `TIE`로 뭉개면 **judge가 절반을 판정 못 해도 "우열이 없었다"로 보입니다.** 실패는 실패로 세야 그 비율이 높을 때 알아챌 수 있습니다.

실제로 돌려보면 **10~25% 정도가 "순서에 따라 뒤집히는" 케이스**로 나옵니다. 그 비율이 지나치게 높다면(30% 이상) 두 답변의 품질이 실제로 비슷하거나 rubric의 기준이 모호하다는 신호입니다.

## 편향 체크리스트

작업하다 이 편으로 돌아왔을 때 볼 요약입니다.

| 편향 | 증상 | 대책 |
|---|---|---|
| **위치** | 순서 바꾸면 승자가 뒤집힘 | 두 순서로 묻고 일치할 때만 인정 |
| **장황함** | 튜닝할수록 답변이 길어짐 | rubric에 "길이는 평가 대상 아님" 명시 + 평균 길이 감시 |
| **자기편애** | judge와 챗봇이 같은 모델 | 다른 계열 모델 사용, 여러 judge로 κ 비교 |
| **아부** | 출처/의도를 알려줌 | "답변 1/2" 중립 표기, 버전명 노출 금지 |
| **점수 몰림** | 7~8점에 결과가 뭉침 | 선택지를 2~4개로 축소 |

여기에 4편의 체크를 더하면 됩니다.

```
□ κ를 계산했는가 (일치율만 보지 않았는가)
□ PASS/FAIL 재현율을 따로 봤는가
□ 홀드아웃을 rubric 수정에 쓰지 않았는가
□ 사람-사람 일치율(기준점)을 알고 있는가
```

## 도구에서는 어떻게 부르나

- **promptfoo** — `select-best` assertion이 pairwise 계열입니다. 여러 프롬프트를 한 번에 비교하는 격자 실행이 기본 기능이라, A/B 비교에 가장 손이 덜 갑니다.
- **FastChat의 `llm_judge`** — MT-Bench 논문의 참조 구현. **position bias를 순서 교환으로 처리하는 코드가 그대로 들어 있어서**, 직접 구현하기 전에 한 번 읽어보면 좋습니다.
- **autoevals** — `Battle` 스코어러가 두 출력 비교용입니다.
- **Chatbot Arena** — 사람이 직접 pairwise 투표를 하는 서비스. 방법론의 원형을 볼 수 있습니다.

pointwise judge는 어느 도구에나 있지만, **순서 교환까지 챙겨주는 pairwise는 도구마다 지원이 다릅니다.** 없다면 위 `compare()` 함수처럼 직접 감싸세요. 20줄이면 됩니다.

## 한 줄 정리

LLM judge는 **먼저 나온 답을, 긴 답을, 자기가 쓸 법한 답을** 좋아하고 **힌트를 주면 그쪽으로 기울며 점수는 중간에 몰립니다.** 각각 순서 교환·rubric 명시·다른 계열 모델·출처 은닉·선택지 축소로 막을 수 있고, **A/B 승부 판정에는 pairwise가, 배포 게이트에는 pointwise가** 어울립니다.
