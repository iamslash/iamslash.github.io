# 3편. 프롬프트 A와 B, 어느 쪽이 나은가

> 시리즈: AI 답변을 채점하는 법 — LLM-as-a-Judge
> 이 편에서 배우는 것: 1편에서 던진 질문에 끝까지 답하는 절차. rubric을 동결해야 하는 이유, 통과율 비교보다 강력한 짝비교, 사람 눈으로 하는 최종 확인, 그리고 더 볼 논문과 도구.

1편의 질문으로 돌아갑니다.

```
[v1] 너는 콩마켓의 고객 상담원이다. 친절하고 간결하게 답하라.

[v2] 너는 콩마켓의 고객 상담원이다. 친절하고 간결하게 답하라.
     + 로그인한 고객이면 주문번호를 묻지 말고 최근 주문을 조회해서 안내하라.
```

**v2가 정말 더 나은가?**

## 먼저 — 사람 라벨은 v2를 채점하지 않습니다

가장 흔한 착각이라 먼저 못 박겠습니다.

사람이 채점한 건 **예전에 콩돌이가 실제로 했던 답변**입니다. v2를 돌리면 콩돌이가 **새 답변**을 만드는데, 그 새 답변에 대한 사람 라벨은 세상에 없습니다.

```
❌ v2의 답변을 사람 라벨과 비교한다        ← 불가능. 라벨이 없음.
✅ 사람 라벨로 judge를 검증하고,
   검증된 judge가 v1과 v2를 채점한다
```

역할이 이렇게 나뉩니다.

```
사람 라벨  →  judge가 제대로 채점하는지 재는 자[尺]   (2편)
judge     →  v1과 v2의 새 답변을 채점하는 계량기      (이번 편)
```

## 1단계 — 자를 고정합니다

2편의 튜닝이 끝났다면 이 상태일 겁니다.

```
사람-사람 κ = 0.68   (기준점)
judge κ    = 0.61   → 사람 수준의 90%. 통과.
```

여기서 선언합니다.

> ### 🔒 **이 시점부터 rubric은 동결입니다.**
> v1/v2 비교가 끝날 때까지 한 글자도 고치지 않습니다.

**왜 이렇게까지 하나?** 자와 재는 대상을 동시에 움직이면, 점수가 올라도 그게 v2가 좋아진 건지 자가 무뎌진 건지 알 수 없기 때문입니다. 두 튜닝은 **방향이 정반대**입니다.

```
rubric 튜닝:   사람(고정)  ← judge를 맞춘다      (2편)
프롬프트 튜닝:  judge(고정) ← 챗봇을 맞춘다      (이번 편)
```

## 2단계 — 같은 조건으로, 여러 번

```python
runs_v1 = [generate_all(dataset, prompt_v1) for _ in range(3)]
runs_v2 = [generate_all(dataset, prompt_v2) for _ in range(3)]
```

**왜 3번씩 돌리나?** LLM은 같은 입력에도 매번 조금씩 다른 답을 냅니다. 한 번씩만 돌리면 프롬프트 차이인지 그날의 운인지 구분할 수 없습니다.

```
        1회차   2회차   3회차
v1      61.0%   60.0%   62.0%    → 흔들림 약 ±1%p
v2      74.0%   71.5%   75.0%    → 흔들림 약 ±1.8%p
```

**흔들림 폭이 두 프롬프트의 차이보다 크면 그 차이는 없는 것입니다.** 위 예에서는 흔들림이 2%p 내외인데 차이가 12%p 이상이니 안전합니다.

**나머지는 전부 동일해야 합니다.** 같은 데이터셋, 같은 모델, 같은 온도. 프롬프트만 다릅니다. 흔한 실수가 **"프롬프트 고치는 김에 모델도 최신으로 바꾸는 것"** 인데, 그러면 무엇 때문에 좋아졌는지 영영 모르게 됩니다.

## 3단계 — 동결된 rubric으로 양쪽 채점

```python
scores_v1 = [judge_all(dataset, run) for run in runs_v1]
scores_v2 = [judge_all(dataset, run) for run in runs_v2]
# v1: 61.0%   v2: 73.5%   (3회 평균)
```

12.5%p 차이. 좋아 보이지만 **여기서 결론 내리면 안 됩니다.** 200개 표본에서 두 비율을 비교하는 건 생각보다 무딘 방법입니다.

## 4단계 — 짝비교. 훨씬 강력합니다

통과율 두 개를 비교하는 대신, **같은 케이스에서 판정이 어떻게 바뀌었는지**를 셉니다.

```python
from collections import Counter

def paired_diff(scores_a: dict, scores_b: dict):
    """같은 회차의 두 채점 결과를 짝지어 비교한다."""
    if scores_a.keys() != scores_b.keys():
        raise ValueError("두 채점 결과의 케이스 집합이 다릅니다")

    decided = [c for c in scores_a
               if scores_a[c] in ("PASS", "FAIL")
               and scores_b[c] in ("PASS", "FAIL")]
    t = Counter((scores_a[c], scores_b[c]) for c in decided)
    return {
        "improved":  t[("FAIL", "PASS")],   # v2가 고친 것
        "regressed": t[("PASS", "FAIL")],   # v2가 망친 것
        "unchanged": t[("PASS", "PASS")] + t[("FAIL", "FAIL")],
        "skipped":   len(scores_a) - len(decided),   # 한쪽이라도 UNCLEAR
    }
```

```python
>>> for i in range(3):
...     print(paired_diff(scores_v1[i], scores_v2[i]))
{'improved': 34, 'regressed': 8, 'unchanged': 158, 'skipped': 0}
{'improved': 32, 'regressed': 9, 'unchanged': 159, 'skipped': 0}
{'improved': 33, 'regressed': 7, 'unchanged': 160, 'skipped': 0}
```

1회차를 표로 펼치면 이렇습니다.

|  | v2: PASS | v2: FAIL |
|---|---|---|
| **v1: PASS** | 114 | **8** ← 망가진 것 |
| **v1: FAIL** | **34** ← 고쳐진 것 | 44 |

**핵심: 변하지 않은 158개는 판단에 아무 기여를 하지 않습니다.** 두 프롬프트가 똑같이 처리한 케이스니까요. 승부는 **34 대 8**에서 갈립니다.

> `skipped`가 0이면 "통과 개수 변화 = `improved` − `regressed`"가 보장됩니다. 실제로 1회차는 v1이 122개 통과(61.0%)였고 `122 + 34 − 8 = 148`, 즉 74.0%죠. **이 등식이 안 맞으면** 다른 회차를 섞었거나, UNCLEAR가 낀 케이스에서 통과 개수가 움직인 것입니다.

### 이 차이가 진짜인가 — 주먹구구

**"두 프롬프트가 똑같이 좋다면, 34 대 8 같은 결과가 나오기 쉬울까?"** 를 따집니다. 실력이 같다면 바뀐 42개(34+8)는 반반씩 갈려야 하니 21 대 21 근처가 나와야 합니다.

```
바뀐 개수 = 34 + 8 = 42
흔들림 크기 ≈ √42 ≈ 6.5

|34 - 8| = 26   vs   2 × 6.5 = 13
26 > 13  →  진짜 차이 ✓
```

> **규칙:** `|고쳐진 수 − 망가진 수| > 2 × √(고쳐진 수 + 망가진 수)` 이면 진짜로 봅니다.

| 고쳐짐 | 망가짐 | 기준값 | 판정 |
|---|---|---|---|
| 34 | 8 | 13 | **진짜** |
| 20 | 14 | 11.7 | 노이즈 |
| 12 | 2 | 7.5 | 진짜(간당간당) |
| 5 | 1 | 4.9 | 판정 불가, 표본 부족 |

통계학에서 **McNemar 검정**이라고 부르는 것의 간이 버전입니다. 정확히 계산하려면:

```python
from statsmodels.stats.contingency_tables import mcnemar
print(mcnemar([[114, 8], [34, 44]], exact=False, correction=True).pvalue)  # 0.0001
```

> 이 `0.0001`은 **"두 프롬프트의 실력이 같다면, 지금만큼 또는 이보다 더 치우친 결과가 나올 확률이 0.01%"** 라는 뜻입니다. "v2가 나을 확률 99.99%"도, "이 차이가 우연일 확률"도 아닙니다. 흔한 오해입니다.

**세 회차가 모두 같은 방향을 가리키면 그게 결론입니다.** 한 회차만 v2 우세이고 나머지가 뒤집힌다면 그건 프롬프트 차이가 아니라 생성의 흔들림입니다.

## 5단계 — 사람 눈으로 확인. 건너뛰지 마세요

숫자가 다 좋아도 이 단계가 남았습니다. **judge를 속인 게 아닌지 확인하는 마지막 관문**입니다.

**① 고쳐진 34개 중 10개를 읽습니다.**

```
[case-0042] 고객(로그인): 어제 주문한 거 아직도 안 왔어요

v1: 주문번호를 알려주시면 확인해 드릴게요!                  judge FAIL
v2: 확인해보니 어제 주문하신 예가체프가 오늘 오전 출고됐어요.
    내일 도착 예정입니다!                                    judge PASS

→ 사람: 그래, 이게 낫다 ✓
```

**"그래 이게 낫다"가 8개 이상**이면 통과입니다. 절반이 애매하면 judge가 후한 판정을 하고 있는 것이니 2편으로 돌아가야 합니다.

**② 망가진 8개는 전부 읽습니다.** 이게 더 중요합니다.

```
[case-0117] 고객(로그인): 주문한 거 언제 오나요?
                          (최근 주문이 5건이나 있는 고객)

v1: 어떤 주문을 말씀하시는 걸까요? 최근 5건이 진행 중이에요.  judge PASS
v2: 가장 최근 주문하신 케냐 AA는 내일 도착 예정입니다!        judge FAIL

→ v2가 "되묻지 마라"를 곧이곧대로 따라서, 주문이 여러 개일 때도
  임의로 하나를 골라버렸다.
```

**이 8개가 다음 라운드의 재료입니다.** v3에서는 이렇게 고치면 되겠죠.

```
+ 로그인한 고객이면 주문번호를 묻지 말고 최근 주문을 조회해서 안내하라.
+ 단, 진행 중인 주문이 여러 건이면 목록을 보여주고 어느 것인지 확인하라.
```

## 6단계 — 결론

```
□ judge가 2편에서 검증됐고, 이후 rubric이 동결됐다
□ 3회 반복에서 v2 우세가 일관되고, 짝비교 판정 규칙을 통과했다
□ 고쳐진 케이스를 사람이 읽고 납득했다
□ 망가진 케이스가 감수할 만하고, 다음 라운드 과제로 기록됐다
```

넷이 다 맞으면 **"v2가 더 낫다"** 고 말할 수 있습니다.

> **절대 하면 안 되는 것: v2의 결과를 보고 rubric을 고치는 것.** v2가 FAIL 난 걸 보고 "이 조항이 좀 빡센데" 하며 고치는 순간, 자와 대상을 동시에 움직인 겁니다. 고치고 싶어지면 **2편으로 돌아가 사람 라벨로 다시 검증하고, v1과 v2를 처음부터 다시** 돌려야 합니다.

## 배포한 뒤에

judge 점수가 올랐다고 고객이 행복해진 건 아닙니다. **judge는 우리 팀의 기준을 복제한 것이지 고객의 마음을 재는 도구가 아닙니다.**

**하나, 실제 지표와 대조합니다.** 상담 이관율, 재문의율, 만족도 — 무엇이든 비즈니스 지표 하나와 judge 점수가 같은 방향으로 움직이는지 보세요. 계속 어긋난다면 rubric이 잘못된 걸 재고 있는 겁니다.

**둘, 새 로그로 라벨을 다시 모읍니다.** 챗봇이 바뀌면 실패 양상도 바뀝니다. v2 시대의 대화 50개를 새로 채점해 데이터셋과 홀드아웃을 갱신하지 않으면, judge는 **v1 시대의 문제만 잡는 낡은 자**가 됩니다.

## 전체 흐름 한 장

```
[1편] 사람이 100개 채점 → rubric 작성 → judge 완성
          ↓
[2편] 개발용 60개로 rubric 튜닝 (불일치 읽기 → 수정 → 반복)
      홀드아웃 40개로 최종 측정 → κ 0.61 → 🔒 동결
          ↓
[3편] v1 ×3, v2 ×3 실행 → 동결된 judge로 채점
          ↓
      짝비교: 고쳐짐 34 / 망가짐 8 → |26| > 2√42 ✓
          ↓
      사람이 고쳐진 10개 + 망가진 8개 확인
          ↓
      v2 채택 → 배포 → 실제 지표 대조 → 새 라벨 수집 ──┐
          ↑                                            │
          └────────────────────────────────────────────┘
```

## 논문 — 이 셋이면 충분합니다

**① "Judging LLM-as-a-Judge with MT-Bench and Chatbot Arena"**
Zheng et al., NeurIPS 2023 — [arXiv:2306.05685](https://arxiv.org/abs/2306.05685)

이 분야의 기준 문헌입니다. **"judge가 옳다는 근거 = 사람과의 일치율"** 이라는 검증 방식을 정립했고(2편 전체가 이 아이디어), 강한 judge가 사람끼리의 일치율에 준하는 수준에 도달함을 보였습니다. **position·verbosity·self-enhancement bias**를 문서화한 것도 여기입니다. 시간이 없으면 편향을 다루는 절만 읽어도 본전입니다.

**② "Who Validates the Validators?"**
Shankar et al., UIST 2024 — [arXiv:2404.12272](https://arxiv.org/abs/2404.12272)

**실무자에게 가장 직접적으로 유용합니다.** 사람이 채점하며 LLM 평가자를 정렬시키는 과정을 사용자 연구로 관찰했고, **criteria drift** — 채점하다 보면 자기 기준이 계속 바뀐다는 현상 — 를 발견했습니다. 1편에서 "기준을 메모하면서 채점하라"고 한 근거입니다.

> **"평가 기준은 미리 정하는 게 아니라 데이터를 보면서 발견하는 것"** — 이 한 문장이 정수입니다.

**③ "G-Eval"**
Liu et al., EMNLP 2023 — [arXiv:2303.16634](https://arxiv.org/abs/2303.16634)

평가 절차를 chain-of-thought로 먼저 쓰게 한 뒤 점수를 매기면 사람 판단과 더 잘 맞는다는 것을 보였습니다. 1편의 "근거 먼저, 판정 나중"이 같은 방향입니다. (다만 이 논문이 JSON 필드 순서를 실험한 건 아닙니다. 필드 순서 규칙은 자기회귀 생성이라는 성질에서 나온 것이고, 이 논문은 방향을 뒷받침하는 근거입니다.)

**더 갈 곳** — 자기편애 편향은 Panickssery et al. 2024([arXiv:2404.13076](https://arxiv.org/abs/2404.13076)), 위치 편향은 Wang et al.([arXiv:2305.17926](https://arxiv.org/abs/2305.17926), ACL 2024). 전체 지형은 Gu et al.의 서베이([arXiv:2411.15594](https://arxiv.org/abs/2411.15594)). Cohen's kappa는 Cohen(1960) 원논문이 짧고, 2편의 해석표는 Landis & Koch(1977)에서 온 경험칙입니다.

## 오픈소스 — 직접 만들기 전에

**promptfoo** — [github.com/promptfoo/promptfoo](https://github.com/promptfoo/promptfoo)
**처음이라면 여기서 시작하세요.** CLI + YAML이라 30분이면 첫 실행이 됩니다. 이 편의 2~3단계를 그대로 해줍니다.

```yaml
prompts:
  - file://prompts/v1.txt
  - file://prompts/v2.txt      # 두 프롬프트를 나란히
providers:
  - openai:gpt-4.1-mini
tests:
  - vars: { conversation: "어제 주문한 거 아직도 안 왔어요", logged_in: true }
    assert:
      - type: llm-rubric
        value: "로그인 고객에게 주문번호를 되물으면 실패다."
```

**Langfuse** — [github.com/langfuse/langfuse](https://github.com/langfuse/langfuse)
**이 시리즈 전체를 한 제품에 담은 것에 가장 가깝습니다.** 데이터셋 + 사람 annotation 큐 + judge + 프롬프트 버전별 실험 비교가 다 있고 자체 호스팅됩니다. "조직에 평가 체계를 세우자" 단계라면 이걸 먼저 보세요.

**DeepEval** — [github.com/confident-ai/deepeval](https://github.com/confident-ai/deepeval)
pytest처럼 쓰는 평가 라이브러리. **CI에 회귀 검사를 붙이고 싶을 때** 가장 자연스럽습니다. G-Eval 구현이 들어 있습니다.

**scikit-learn / statsmodels** — 2편의 κ와 이 편의 McNemar. 실무에서는 직접 짜지 말고 `cohen_kappa_score`, `classification_report`, `mcnemar`를 쓰세요.

> RAG 시스템이라면 **Ragas**([github.com/explodinggradients/ragas](https://github.com/explodinggradients/ragas))의 faithfulness 같은 전용 지표를 먼저 보는 게 낫습니다. MT-Bench 논문의 실제 코드를 보고 싶다면 **FastChat의 `llm_judge`** 디렉터리에 위치 편향 처리까지 들어 있습니다.

## 마지막 한마디

새 기법을 많이 아는 것보다 **두 가지가 훨씬 중요합니다.**

**하나, 데이터를 직접 보는 것.** 로그 50개를 읽으면 rubric에 뭘 써야 할지 알게 됩니다. 안 읽고 상상으로 쓴 rubric은 현실에 없는 문제를 잡습니다. 이 시리즈에서 딱 하나만 가져가신다면 이것입니다.

**둘, 자를 검증하는 것.** judge를 만드는 데 하루, 검증하는 데 하루를 쓰면 그 judge는 몇 달을 씁니다. 검증을 건너뛰고 만든 judge는 **틀린 방향으로 몇 달을 달리게** 만듭니다.

화려한 기법은 특정 상황용 20%이고, 실전 가치의 **80%는 "사람이 직접 본 라벨 100개 + 그걸로 검증한 judge"** 에서 나옵니다.
