# 0편. 프롤로그 — 내 백엔드에는 문이 네 개다

> 시리즈: 내 스택 안전하게 만들기 — Vercel · Cloud Run · Supabase · Cloudflare
> 이 편에서 배우는 것: 보안 도구를 고르기 **전에** 해야 할 일. 내 시스템에 문이 몇 개인지 세는 것.

이런 스택을 만들었다고 해봅시다. 요즘 흔한 구성입니다.

```
브라우저
   ↓
Next.js  @ Vercel        (SSR + edge + serverless 라우트)
   ↓
NestJS   @ GCP Cloud Run  ← API · WebSocket · MCP · Webhook
   ↑
Supabase                  (Google 로그인 → JWT 발급)
```

배포하고 나면 이런 생각이 듭니다.

> **"Cloudflare 깔면 되겠지?"**

이 시리즈는 그 생각이 **왜 절반만 맞는지**에서 출발합니다.

## 먼저 문을 세어봅시다

"백엔드를 보호한다"고 뭉뚱그리면 설계가 어긋납니다. 위 그림의 Cloud Run 하나에 **성격이 다른 입구가 넷** 있기 때문입니다.

| 문 | 누가 두드리나 | 무엇으로 신원을 확인하나 |
|---|---|---|
| **REST API** | 내 프론트엔드 | Supabase JWT |
| **WebSocket** | 내 프론트엔드 | 연결할 때 JWT 한 번 |
| **MCP** (AI 도구 연결 규약) | AI 클라이언트 | 토큰 또는 OAuth |
| **Webhook** | **텔레그램 같은 외부 서비스** | **공유 시크릿 / 서명** |

문마다 **부르는 쪽이 다르고, 신원 확인 방법이 다르고, 막는 방법도 다릅니다.**

### 네 번째 문이 모든 걸 바꿉니다

앞의 셋은 "내 사용자" 또는 "내가 허락한 클라이언트"입니다. 로그인을 요구할 수 있죠.

> **한 가지 미리 짚어둡니다.** 위 그림은 브라우저 → Vercel → Cloud Run 으로 그렸지만, **WebSocket 은 그 경로를 타지 않습니다.** 여러분의 WS 서버는 NestJS 쪽에 있으니 브라우저가 `api.내도메인.com` 으로 **직접** 붙습니다. (Vercel 도 요즘은 WebSocket 을 지원하지만, 그건 Vercel 에서 WS 서버를 돌릴 때 얘기입니다.) 5편에서 다룹니다.

**웹훅은 아닙니다.** 텔레그램은 여러분의 로그인 화면을 못 봅니다. 계정도 없고, 토큰도 없습니다. 그냥 URL을 때립니다. 그리고 **때리게 놔둬야 합니다** — 안 그러면 봇이 동작을 안 하니까요.

> **그래서 "전부 잠그면 된다"는 설계가 성립하지 않습니다.** 인터넷 전체에 열어둘 수밖에 없는 문이 하나 있고, 그 문은 **다른 방식으로** 지켜야 합니다.

## 두 번째로 셀 것 — 누가 인증을 담당하는가

여기서 흔한 혼동이 하나 나옵니다.

Cloudflare에는 **Access**라는 제품이 있습니다. 도메인 앞에 서서 "당신 누구세요"를 먼저 묻고, 통과한 요청만 뒤로 보냅니다. 이름만 들으면 딱 필요한 물건 같죠.

**그런데 여러분 사용자에게 쓰면 안 됩니다.**

```
[Access를 서비스 앞에 걸면]

사용자 → Cloudflare Access에 Google 로그인   ← 1번째
       → Supabase에 Google 로그인            ← 2번째
       → 겨우 앱 진입
```

**로그인을 두 번** 하게 됩니다. 게다가 Access는 **좌석 단위 과금**이라 사용자가 늘면 비용이 그대로 따라 늘어납니다. 일반 사용자용으로 설계된 물건이 아닙니다.

> **한 줄로 정리하면 이렇습니다.**
> **Access는 여러분의 *사용자*를 위한 게 아니라 여러분의 *팀*을 위한 것입니다.**

그럼 사용자 인증은 누가 하나요? **이미 하고 계십니다** — Supabase가 Google 로그인을 처리하고 JWT를 발급하죠. 그게 인증 담당입니다.

Access가 필요한 곳은 따로 있습니다.

| 대상 | 인증 담당 |
|---|---|
| 일반 사용자 | **Supabase + Google OAuth** |
| 관리자 페이지 · 스테이징 · 내부 도구 | **Cloudflare Access** |

> 좌석 과금이라고 했지만 **무료 티어가 50 명까지** 있습니다. 위 표의 아래 칸(팀 내부용)이라면 소규모에서는 사실상 공짜입니다.

## 세 번째로 셀 것 — 뒷문이 열려 있나

이게 제일 중요합니다.

Cloud Run에 배포하면 이런 주소가 자동으로 생깁니다.

```
https://<서비스명>-<프로젝트번호>.<리전>.run.app
```

여러분은 `api.내도메인.com`을 쓰겠지만, **저 주소도 살아 있습니다.** 그리고 여기가 핵심입니다.

```
[정상 경로]
공격자 → api.내도메인.com → Cloudflare(WAF·레이트리밋) → Cloud Run
                              ↑ 여기서 걸러짐

[우회 경로]
공격자 → my-backend-abcd1234-uc.a.run.app → Cloud Run
         ↑ Cloudflare를 아예 안 거침
```

**앞문에 자물쇠를 아무리 달아도 뒷문이 열려 있으면 소용없습니다.**

그리고 저 주소는 **규칙적으로 만들어집니다.** 서비스명·프로젝트번호·리전을 알면 조합할 수 있습니다. 거기에 로그, 에러 메시지, 브라우저 히스토리, 실수로 커밋된 설정 파일까지 더하면 — **"주소를 모르니 괜찮겠지"는 보안이 아닙니다.**

## 그래서 이 시리즈가 답할 질문

세 가지입니다.

1. **뒷문을 어떻게 닫나** — Cloud Run 직접 호출 막기
2. **문마다 어떻게 다르게 지키나** — 특히 잠글 수 없는 웹훅
3. **진짜 인증 경계는 어디인가** — Cloudflare인가, 내 코드인가

세 번째부터 답을 미리 말하면 이렇습니다.

> **진짜 인증 경계는 NestJS의 JWT 검증입니다.** Cloudflare는 그 앞에 세우는 방어층이지 대체재가 아닙니다.

이 구분을 못 하면 **"Cloudflare 깔았으니 안전하다"** 는 착각에 빠집니다. Cloudflare가 막아주는 건 대량 스캔, 봇, DDoS 같은 것들입니다. **"이 요청이 정말 그 사용자인가"** 는 여전히 여러분 코드가 판단합니다.

## 비용 이야기를 미리 하면

"가장 적은 노력, 가장 저렴한 가격"이 목표라면 좋은 소식이 있습니다. **소규모에서는 대부분 무료 티어로 됩니다.**

다만 갈림길이 있습니다. 뒷문을 닫는 방법이 **최소 세 가지**이고, 비용과 확실성이 다릅니다.

| | Cloudflare + 앱 검증 | **기본 URL 끄기** | GCLB + Cloud Armor |
|---|---|---|---|
| `*.run.app` | **여전히 열림**. 앱이 걸러냄 | **꺼짐** | 꺼짐 |
| 월 고정비 | 없음 | **없음** | 로드밸런서 + 정책 비용 |
| WAF·레이트리밋 | Cloudflare 가 | 없음 | Cloud Armor 가 |
| 설정 | DNS 정도 | 플래그 하나 + 도메인 연결 | NEG · 백엔드 서비스 · 인증서 · 룰 |

가운데 칸이 덜 알려져 있습니다. Cloud Run 은 **기본 URL 자체를 끌 수 있습니다.**

```bash
gcloud run services update <서비스> --region <리전> --no-default-url
```

```
--[no-]default-url
   Toggles the default url for a run service. This is enabled by default
   if not specified.
```

**공짜입니다.** 다만 끄고 나면 들어올 다른 길이 있어야 합니다 — 로드밸런서나 Cloud Run 의 도메인 매핑이죠.

> 그래서 **"원본을 진짜로 닫으려면 Cloud Armor 뿐"이라는 말은 정확하지 않습니다.** Cloud Armor 의 값어치는 *닫는 것*이 아니라 **WAF·레이트리밋** 쪽입니다. 누군가 Cloud Armor 를 권했다면 그 부분에서 옳습니다. 4편에서 셋을 정면 비교합니다.

> **정확한 금액은 이 글에 적지 않겠습니다.** 클라우드 가격은 자주 바뀌고, 리전과 트래픽에 따라 달라집니다. **쓰기 직전에 공식 가격 계산기로 확인하세요.** 이 시리즈는 "무엇이 유료이고 무엇이 무료인지"의 구조만 다룹니다.

## 해결책은 세 갈래로 나뉩니다

문을 다 셌으면, 이제 **누가 그 문을 닫느냐**를 봐야 합니다. 해결책은 성격이 다른 셋으로 갈립니다.

| 갈래 | 무엇으로 | 예 |
|---|---|---|
| **① 엣지** | Cloudflare · Cloud Armor | L7 레이트리밋 · DoS 흡수 · WAF 시그니처 · IP 허용목록 |
| **② 코드** | 내 애플리케이션 | **권한 검사(IDOR)** · 인젝션 · fail-open · 조회 범위 필터 · 사용자별 throttle |
| **③ 설정·콘솔** | 인프라·정책 | `ingress` 잠금 · 시크릿 보관과 회전 · 캐시 설정 · 배포 권한 |

**이 순서가 중요합니다. ③이 ①의 전제입니다.**

```
③ 뒷문 잠금 ──(선행)──> ① 엣지가 비로소 의미를 가짐
```

`*.run.app` 이 열려 있으면 공격자는 앞단을 안 거치고 바로 갑니다. **Cloudflare도 Cloud Armor도 평가할 기회조차 없습니다.** 뒷문을 열어둔 채 앞에 WAF를 세우면 보안이 아니라 **착각**이 늘어납니다.

### 엣지가 못 하는 일 두 가지

**첫째, 권한 오류를 못 잡습니다.** 로그인한 사용자가 남의 주문 번호를 넣어 조회하면, WAF에게는 **완벽히 정상인 요청**입니다. 페이로드가 멀쩡하니까요. 그런데 실제 침해에서 가장 흔한 게 이 부류입니다. **진짜 구멍은 코드가 닫고, 엣지는 그 위에 얹는 층**입니다.

**둘째, 레이트리밋도 절반은 코드입니다.** 엣지의 제한은 보통 **IP 기준**인데, 유효한 토큰 하나로 프록시를 갈아타며 남의 ID를 훑는 공격에는 약합니다. 이건 **사용자 기준**(JWT `sub`) 제한이라야 잡히고, 그건 앱에서 해야 합니다.

### 그래서 이 시리즈가 다루는 것

**②와 ③입니다.** 각 편 끝의 체크리스트 57개를 갈래별로 세면 이렇습니다.

| ① 엣지 | ② 코드 | ③ 설정·콘솔 |
|---|---|---|
| 3개 | **36개** | 18개 |

**①은 57개 중 3개**입니다. 이 시리즈에서 Cloudflare와 Cloud Armor는 *해법*보다 **"이것만으로는 왜 부족한가"의 대조군**으로 더 자주 등장합니다.

> **이 시리즈의 목적은 이 구성에서 열려 있는 문을 하나도 남기지 않고 닫는 것**입니다.
>
> **"완벽한 보안"을 약속하지는 않겠습니다.** 그런 건 없고, 그렇게 파는 제품은 더더욱 믿을 게 못 됩니다. 대신 약속할 수 있는 건 이겁니다 — **문을 빠짐없이 세고, 각각을 무엇으로 닫는지 보이고, 닫히지 않는 것은 닫히지 않는다고 말하는 것.** 그래서 매 편 끝에 "확인 못 한 것"을 답니다.

**다루지 않는 것도 밝혀둡니다.** 뚫린 뒤를 다루는 **④ 탐지·대응**(감사 로그, 토큰 즉시 무효화, 이상 징후 알림)은 이 시리즈 범위 밖입니다. 중요하지 않아서가 아니라 별도 주제라서입니다. 다만 **대부분의 팀에 이게 비어 있다**는 것만 기억해 두세요.

## 이 시리즈에서 볼 것

| 편 | 주제 |
|---|---|
| 1편 | **JWT가 뭔가** — 생초보용 |
| 2편 | **진짜 인증 경계** — Supabase JWT 검증하기 |
| 3편 | **웹훅 문** — 잠글 수 없는 문 지키기 |
| 4편 | 뒷문 — Cloud Run 직접 호출 막기 (Cloudflare vs Cloud Armor) |
| 5편 | 긴 연결 문 — WebSocket과 MCP |
| 6편 | 나가는 문 — Cloud Run → PlanetScale |

**2·3·4편이 중심**입니다. 나머지를 다 해도 이 셋이 없으면 뚫립니다.

## 정리

- **도구를 고르기 전에 문을 세세요.** 이 스택엔 API · WebSocket · MCP · Webhook 넷이 있습니다.
- **웹훅은 잠글 수 없습니다.** 그래서 "전부 잠근다"는 설계는 성립하지 않습니다.
- **Cloudflare Access는 사용자용이 아닙니다.** 팀용입니다. 사용자 인증은 Supabase가 이미 하고 있습니다.
- **`*.run.app` 뒷문이 열려 있습니다.** 앞문만 막으면 우회당합니다.
- **진짜 인증 경계는 여러분의 JWT 검증 코드**입니다. Cloudflare는 그 앞의 방어층입니다.
- **해결책은 ①엣지 · ②코드 · ③설정 세 갈래**이고, 이 시리즈는 **②와 ③**을 다룹니다. ③이 안 되면 ①은 값이 0입니다.

다음 편은 **JWT**입니다. 위에서 "진짜 인증 경계는 여러분의 JWT 검증 코드"라고 했는데, 그 JWT가 무엇인지부터 짚고 갑니다. 처음 보시는 분 기준으로 씁니다.
