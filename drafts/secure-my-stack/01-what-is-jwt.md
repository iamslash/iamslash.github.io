# 1편. JWT가 뭔가 — 생초보용

> 시리즈: 내 스택 안전하게 만들기
> 이 편에서 배우는 것: 서버가 "너 누구야"를 매번 어떻게 아는지, JWT의 세 조각, **JWT는 암호화된 게 아니라는 것**, 그리고 위조가 왜 안 되는지.

이 시리즈의 나머지 편은 전부 이 한 문자열 위에 서 있습니다. 그래서 먼저 짚고 갑니다. **JWT를 처음 보시는 분을 기준으로** 씁니다.

## 문제부터 — 서버는 여러분을 기억하지 못합니다

웹의 기본 규칙이 하나 있습니다.

> **HTTP 요청은 서로를 모릅니다.**

로그인 요청과 그다음 "내 글 목록 줘" 요청은 **완전히 남남**입니다. 서버 입장에서는 매번 처음 보는 손님이죠.

```
요청 1: "로그인할게요"        → 서버: "확인했습니다"
요청 2: "내 글 목록 주세요"    → 서버: "...누구세요?"
```

그럼 로그인이 무슨 의미일까요? **매 요청마다 "나 아까 그 사람이야"를 증명할 방법**이 필요합니다.

## 옛날 방식 — 서버가 명단을 들고 있기

전통적인 방법은 이렇습니다.

```
로그인 성공 → 서버가 임의의 문자열(세션 ID)을 만들어 준다
            → 서버는 "abc123 = 홍길동" 을 자기 메모리/DB 에 적어둔다
            → 브라우저는 abc123 만 들고 다닌다
매 요청     → abc123 을 보냄 → 서버가 명단을 뒤져서 홍길동임을 확인
```

잘 동작합니다. 다만 **서버가 명단을 계속 들고 있어야** 합니다. 서버가 여러 대면 명단을 공유해야 하고, 서버리스처럼 떴다 사라지는 환경이면 더 곤란해집니다.

## JWT 방식 — 도장 찍힌 쪽지를 들려 보내기

**놀이공원 손목밴드**를 떠올리면 정확합니다.

```
입구에서 신분증 확인   →  손목밴드를 채워줍니다     ← 로그인 (딱 한 번)
놀이기구 탈 때마다     →  밴드만 보여주면 됩니다     ← 매 요청
```

밴드에는 이런 성질이 있습니다.

| 손목밴드 | JWT |
|---|---|
| 이름·유효기간이 **눈에 보이게 인쇄**돼 있다 | **누구나 읽을 수 있다** |
| 홀로그램이 있어 **못 만든다** | **서명이 있어 위조 불가** |
| 오늘 자정까지만 유효 | **만료 시각이 들어 있다** |
| 직원이 명단을 안 봐도 된다 | **서버가 기억할 필요 없다** |

마지막 줄이 핵심입니다. **JWT는 필요한 정보를 자기 안에 담고 다닙니다.** 그래서 서버가 명단을 유지하지 않아도 됩니다. Cloud Run처럼 인스턴스가 떴다 사라지는 환경에 잘 맞는 이유죠.

**다만 비유가 깨지는 곳이 하나 있습니다.** 손목밴드는 내 손목에 채워져 있지만, JWT는 **종이 티켓에 가깝습니다.**

> **가진 사람이 곧 그 사람입니다.** 누가 내 토큰을 훔치면 서버는 그 사람을 나로 취급합니다. 서명은 **위조**를 막을 뿐 **도난**은 못 막습니다.

그래서 두 가지가 따라옵니다.

- **토큰을 어디에 보관하느냐가 중요합니다** (7편)
- **수명을 짧게 잡습니다.** 서버가 명단을 안 들고 있으니 **만료 전에 강제로 무효화할 수도 없기 때문**입니다

> **JWT** = JSON Web Token. "JSON으로 된 웹 토큰"이고, 보통 **"조트"** 라고 읽습니다.

## 생긴 모양 — 점으로 나뉜 세 조각

실제 JWT는 이렇게 생겼습니다.

```
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJpc3MiOiJodHRwczovL2FiY2RlZmdo...Q.b2rG5vxvZJp8pz0VvBRGKuHtmCUtlCw13NMnC1jyQkw
```

암호처럼 보이지만 아닙니다. **점(`.`) 두 개로 나뉜 세 덩어리**입니다.

```
헤더 . 페이로드 . 서명
```

| 조각 | 무엇 |
|---|---|
| **헤더** | 어떤 방식으로 서명했는지 |
| **페이로드** | 실제 내용 — 누구인지, 언제 만료되는지 |
| **서명** | 위조 방지용 도장 |

## 직접 열어봅시다

**여기가 가장 중요한 부분입니다.** 아래를 직접 실행해보세요.

```bash

print('[페이로드]'); print(json.dumps(json.loads(d(t[1])), indent=2, ensure_ascii=False))
print('[서명]', t[2][:20], '... (읽을 수 없음)')
```

## 🚨 여기서 가장 중요한 사실

방금 무슨 일이 있었는지 보세요.

> **비밀키도 없이, 아무 권한도 없이, 내용을 전부 읽었습니다.**

**JWT는 암호화된 게 아닙니다.** 그냥 **Base64로 인코딩**돼 있을 뿐입니다. Base64는 암호가 아니라 **글자를 다른 글자로 바꿔 적는 방식**입니다. 누구나 되돌릴 수 있습니다.

초보자가 가장 많이 하는 착각이 이겁니다.

```
❌ "JWT에 넣었으니 안전하겠지"
✅ "JWT 내용은 전 세계가 읽을 수 있다"
```

**그러니 절대 넣으면 안 되는 것들**이 있습니다.

- 비밀번호
- 주민번호·카드번호 같은 민감 정보
- 내부 API 키
- 남에게 보이면 안 되는 모든 것

JWT에는 **"이 사람이 누구인지 식별할 정보"** 만 넣습니다. 위 예시에 이메일과 사용자 ID만 있는 이유입니다.

## 그럼 위조하면 되지 않나요?

좋은 질문입니다. 내용을 읽을 수 있다면, 고쳐서 다시 붙이면 되지 않을까요?

```
페이로드의 "role": "authenticated" 를
           "role": "admin" 으로 바꿔서 보내면?
```

**안 됩니다. 세 번째 조각인 서명 때문입니다.**

서명은 이렇게 만들어집니다.

```
서명 = 어떤_계산(헤더 + 페이로드, 비밀키)
```

**비밀키는 발급한 쪽(여기서는 Supabase)만 갖고 있습니다.** 여러분이 페이로드를 고치면 계산 결과가 달라지고, 서버가 다시 계산해보면 **서명이 안 맞습니다.** 그래서 거부됩니다.

```
공격자: 페이로드를 admin 으로 고침
      → 하지만 새 서명을 만들 수 없음 (비밀키가 없으니까)
      → 옛 서명을 그대로 붙임
서버:  다시 계산 → 안 맞음 → 거부 ✅
```

손목밴드의 홀로그램과 같습니다. **읽는 건 누구나, 만드는 건 발급자만.**

> **단, 이건 서버가 서명을 *실제로 검증할 때만* 성립합니다.** 검증을 안 하고 디코드만 하면 위조가 그대로 통과합니다. **이게 실무에서 가장 흔한 사고**이고, 2편의 주제입니다.

## 페이로드에 들어가는 표준 항목들

이름이 짧아서 처음엔 낯선데, 정해진 약속입니다.

| 이름 | 읽는 법 | 뜻 | 예시 |
|---|---|---|---|
| `iss` | issuer | **누가 발급했나** | `https://abcdefgh.supabase.co/auth/v1` |
| `sub` | subject | **누구에 대한 토큰인가** (사용자 ID) | `9f8b1c2d-...` |
| `aud` | audience | **누가 쓰라고 만든 건가** | `authenticated` |
| `exp` | expiration | **언제 만료되나** | `1787000000` |
| `iat` | issued at | **언제 발급됐나** | `1786996400` |

`exp`와 `iat`의 숫자는 **1970년 1월 1일부터 흐른 초**입니다. 사람이 읽으려면 변환해야 합니다.

```bash
python3 -c "import datetime; print(datetime.datetime.fromtimestamp(1787000000))"
```

> **`sub`를 기억해두세요.** 이 시리즈에서 반복해서 나옵니다. **"이 요청을 보낸 사람이 누구인가"의 정답은 언제나 검증된 JWT의 `sub`** 이고, 클라이언트가 보낸 다른 값이 아닙니다.

## 서명 방식 두 가지

헤더의 `alg`가 서명 방식입니다. 크게 두 종류입니다.

### 대칭키 (HS256)

**하나의 비밀키로 만들고 검증합니다.**

```
Supabase ──(비밀키로 서명)──> JWT
NestJS   ──(같은 비밀키로 검증)
```

간단하지만, **검증하려면 서명할 수 있는 키를 가져야** 합니다. 즉 검증만 하고 싶은 쪽도 **토큰을 위조할 능력**을 갖게 됩니다.

### 비대칭키 (RS256, ES256)

**만드는 키와 검증하는 키가 다릅니다.**

```
Supabase ──(개인키로 서명)──> JWT
NestJS   ──(공개키로 검증)       ← 공개키로는 서명을 만들 수 없다
```

공개키는 이름 그대로 **공개돼도 됩니다.** 발급자가 인터넷에 올려두고, 검증하는 쪽이 받아 갑니다. 그 목록을 **JWKS**(JSON Web Key Set)라고 부릅니다.

> **가능하면 비대칭키를 쓰세요.** NestJS는 검증만 하면 되는데, 대칭키를 쓰면 **위조 능력까지** 갖게 됩니다. 백엔드가 뚫렸을 때 피해 범위가 달라집니다. 2편에서 어느 쪽을 쓰고 있는지 확인하는 법을 다룹니다.

## 이 구성에서는 이렇게 흐릅니다

전체 그림을 두 장으로 나눠 보겠습니다. **로그인은 한 번**이고, **검증은 매 요청**이라 성격이 다릅니다.

> **BFF** = Backend For Frontend. 브라우저와 백엔드 사이에 두는 얇은 서버 계층으로, 여기서는 Next.js 의 서버 라우트가 그 역할을 합니다.

### 그림 1 — 로그인 (딱 한 번)

```
  브라우저            Vercel BFF          Supabase            Google
     │                    │                   │                  │
 ①   │ "Google로 로그인"  │                   │                  │
     ├───────────────────>│                   │                  │
 ②   │                    │   인증 시작       │                  │
     │                    ├──────────────────>│                  │
 ③   │        Google 로그인 화면으로 리다이렉트                    │
     │<───────────────────────────────────────┴─────────────────>│
 ④   │                  계정 선택 + 동의                          │
     │                    │                   │                  │
 ⑤   │                    │                   │<── 인가 코드 ────┤
     │                    │                   │                  │
 ⑥   │                    │      코드 교환 → auth.users 에 기록   │
     │                    │                   │                  │
 ⑦   │                    │<══ ★ Supabase JWT │   ← Google 토큰 아님
     │                    │                   │                  │
 ⑧   │<── httpOnly 쿠키 ──┤                   │                  │
     │  (브라우저 JS 는    │                   │                  │
     │   읽을 수 없음)     │                   │            여기서 Google 퇴장
```

**⑦이 이 그림의 핵심입니다.** 이후에 쓰는 건 **Google 토큰이 아니라 Supabase가 만든 JWT**입니다. Google은 ③~⑤에서만 일하고 사라집니다.

**⑧도 중요합니다.** 브라우저가 BFF를 거치는 구성이라면 토큰을 **`httpOnly` 쿠키**에 넣을 수 있습니다. 브라우저 JS가 읽을 수 없다는 뜻이고, **XSS로 토큰이 새는 경로가 막힙니다.** 7편에서 자세히 다룹니다.

### 그림 2 — 그 뒤 모든 요청

```
  브라우저          Vercel BFF        NestJS @ Cloud Run     PlanetScale
     │                  │                     │                   │
 ①   │ fetch('/api/…')  │                     │                   │
     ├─ 쿠키 자동 첨부 ─>│                     │                   │
     │                  │                     │                   │
 ②   │                  │ Authorization:      │                   │
     │                  │   Bearer <JWT>      │                   │
     │                  ├────────────────────>│                   │
     │                  │                     │                   │
 ③   │                  │            ┌────────┴────────┐          │
     │                  │            │ 서명 검증        │          │
     │                  │            │ (JWKS 공개키)    │          │
 ④   │                  │            │ exp 만료 확인    │          │
     │                  │            │ iss 발급자 확인  │          │
     │                  │            │ aud 대상 확인    │          │
     │                  │            └────────┬────────┘          │
     │                  │                     │                   │
 ⑤   │                  │            sub 로 사용자 특정            │
     │                  │            → RBAC 역할 판정              │
     │                  │                     │                   │
 ⑥   │                  │                     ├─── 쿼리 ─────────>│
     │                  │                     │<── 결과 ──────────┤
 ⑦   │<─────────────────┴─────────────────────┤                   │
```

**③~⑤가 2편의 전부**입니다. 그리고 이 구성에서는 **이 다섯 줄이 인가의 전부**이기도 합니다 — 뒤에 RLS 같은 방어선이 없으니까요.

### 공개키는 어디서 오나

③의 JWKS 공개키는 여기 있습니다.

```
https://<프로젝트>.supabase.co/auth/v1/.well-known/jwks.json
```

**매 요청마다 받아오면 안 됩니다.** 캐시해두고 주기적으로 갱신하는 게 정석이고, 검증 라이브러리가 대개 알아서 해줍니다 — 2편에서 확인합니다.

## 자주 하는 오해 정리

| 오해 | 사실 |
|---|---|
| "JWT는 암호화돼 있다" | **아니다.** 누구나 읽는다 |
| "JWT에 넣으면 안전하다" | 반대다. 넣으면 공개된다 |
| "긴 문자열이라 못 고친다" | 고칠 수 있다. **서명 때문에 안 통할 뿐** |
| "받은 JWT를 디코드하면 검증한 것" | **아니다.** 디코드 ≠ 검증. 가장 흔한 사고 |
| "만료됐는지는 알아서 걸러진다" | **검증을 호출해야** 걸러진다 |
| "Google 토큰을 검증하면 된다" | 검증할 건 **Supabase JWT** 다 |
| "서명이 있으니 도난당해도 괜찮다" | **아니다.** 가진 사람이 곧 그 사람이다 |

## 정리

- HTTP는 요청끼리 서로를 모릅니다. 그래서 **매번 신원을 증명**해야 합니다.
- JWT는 **서명된 쪽지**입니다. 서버가 명단을 안 들고 있어도 됩니다.
- **점 두 개로 나뉜 세 조각** — 헤더·페이로드·서명.
- **암호화가 아니라 인코딩입니다.** 누구나 읽습니다. 민감 정보를 넣지 마세요.
- **위조가 안 되는 건 서명 때문**입니다. 단 **서버가 실제로 검증할 때만**.
- 사용자 ID는 **검증된 JWT의 `sub`** 에서 꺼냅니다.
- 검증만 하는 쪽이라면 **비대칭키(JWKS)** 가 안전합니다.

다음 편에서는 이걸 **NestJS에서 제대로 검증하는 법**을 봅니다. 이 구성에는 RLS 같은 마지막 방어선이 없어서, **이 검증이 인가의 전부**입니다. 틀리면 뒤가 없습니다.

## 확인 못 한 것

- **위 토큰은 설명을 위해 만든 가짜**입니다. 실제 Supabase 프로젝트에서 발급된 것이 아니고 서명도 의미가 없습니다. 구조를 보여주는 용도입니다.
- **클레임 구성은 프로젝트 설정과 버전에 따라 다릅니다.** 여기 없는 클레임이 있을 수 있고, 있는 게 없을 수도 있습니다. 본인 토큰을 직접 디코드해서 확인하세요.
- 위 출력은 **python3** 기준입니다.
