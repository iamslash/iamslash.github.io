# 5편. 긴 연결 문 — WebSocket과 MCP

> 시리즈: 내 스택 안전하게 만들기
> 이 편에서 배우는 것: **브라우저 WebSocket 은 헤더를 붙일 수 없다**는 제약과 그 우회법들, 핸드셰이크 이후 토큰이 만료되면 생기는 일, Cloud Run 의 연결 수명, 그리고 admin 전용 MCP 를 Access 로 막을 때 빠지기 쉬운 함정.

지금까지 다룬 문은 전부 **한 번 왔다 가는** 요청이었습니다. 이번 편의 둘은 **오래 붙어 있습니다.**

## 먼저 — 이 연결은 어디로 가나

여러분의 WebSocket 서버는 NestJS 쪽, 즉 Cloud Run 에 있습니다. 그래서 경로가 이렇습니다.

```
브라우저 ──wss──> Cloudflare ──> Cloud Run (NestJS)
              ↑ Vercel 을 거치지 않는다
```

Vercel 도 요즘은 WebSocket 을 지원합니다(Fluid compute 필요). **다만 그건 Vercel 위에서 WS 서버를 돌릴 때 얘기**고, 이 구성에서는 브라우저가 `api.내도메인.com` 으로 직접 붙습니다.

> **"그럼 Vercel 로 중계하면 되지 않나?"** 자연스러운 질문인데, 권하지 않습니다.
>
> Vercel 문서가 말하는 WebSocket 지원은 *"Vercel Functions can serve WebSocket connections"* — **Vercel 위에서 WS 서버를 돌리는 것**입니다. [문서] **외부 오리진으로 `wss` 를 중계한다는 내용은 문서에 없습니다.** rewrite 로 중계되는지는 오래 논란이었고, 중계가 실제로 일어난다고 확인된 유일한 공식 문서가 **Next.js 의 SSRF 보안 권고**입니다 — 거기서 *"upgrade requests are only proxied when routing has explicitly marked them as safe external rewrites"* 로 **조이는** 수정이 들어갔습니다. **문서화되지 않은 동작 위에 구조를 세우지 마세요.**
>
> 그리고 애초에 **풀려던 문제가 이미 4편에서 풀립니다.** "WS 때문에 Cloud Run 주소가 드러난다"고 걱정하기 쉬운데, 드러나는 건 `api.내도메인.com` 이지 `run.app` 이 아닙니다. **뒷문은 `--no-default-url` 로 닫고, 공개 API 도메인은 원래 공개되라고 만든 주소입니다.**
>
> 굳이 진입점을 하나로 모으고 싶다면 중계가 아니라 **Vercel 에서 WS 서버를 직접 돌리는** 방법이 있는데, 대가가 큽니다 — 연결이 열려 있는 **내내 함수 사용량으로 과금**되고, 인스턴스가 고정되지 않아 **외부 저장소가 필요**하며(이 편 뒤쪽 문제와 동일), 무엇보다 **검증 코드를 NestJS 와 Vercel 양쪽에 이중으로** 두게 됩니다.

핸드셰이크 자체는 평범한 HTTP `GET` 이라 Cloudflare 도 잘 중계하고 시크릿 헤더도 붙습니다. WebSocket 은 **모든 Cloudflare 요금제에서 지원**됩니다. [문서]

> **다만 Cloudflare 의 검사는 핸드셰이크까지입니다.** [문서]
>
> *"once a connection has been established, the WAF does not perform any further inspections."*
>
> **WAF 도 레이트리밋도 업그레이드 이후엔 안 돕니다.** 연결이 열린 뒤 쏟아지는 메시지는 **여러분이 직접** 막아야 합니다. 앞단도 내 코드도 **긴 연결에는 약합니다 — 다만 이유가 다릅니다.** (Cloudflare 는 핸드셰이크까지는 보고 그 뒤로 손을 떼지만, 곧 볼 전역 가드는 **핸드셰이크조차 안 봅니다.**)

**그리고 함정이 하나 더 있습니다.**

### 🚨 전역 가드는 WebSocket 에 돌지 않습니다

2편·4편에서 `APP_GUARD` 로 전역 가드를 걸었죠. WS 에도 적용될까요? 직접 확인했습니다. [관찰]

```
① HTTP 요청 후 : ["GUARD_RAN"]         ← 전역 가드가 돈다
② WS 연결 후   : ["handleConnection"]   ← 가드가 안 돈다
③ WS 메시지 후 : ["messageHandler"]     ← 메시지에도 안 돈다
```

**전역 등록(`APP_GUARD`)은 HTTP 라우트에만 돕니다.** WS 업그레이드는 그 파이프라인을 아예 안 지나갑니다.

> **지금까지 쌓은 방어가 이 문 앞에서 통째로 사라집니다.** 원본 시크릿 검증도, JWT 검증도요. **`handleConnection` 안에서 직접 해야 합니다.**

```ts
handleConnection(client: Socket) {
  const req = client.request                       // 핸드셰이크 요청
  if (!secretOk(req.headers['x-origin-secret'])) return client.disconnect(true)
  // ... JWT 검증도 여기서
}
```

> **4편의 가드를 게이트웨이에 옮겨 붙이지 마세요.** 게이트웨이에 `@UseGuards()` 를 직접 달면 **메시지 핸들러에는 돕니다** — 전역 등록과 다릅니다. 그래서 더 위험한데, 그 가드는 `ctx.switchToHttp().getRequest()` 를 씁니다. **WS 컨텍스트에서 그건 요청이 아니라 소켓**이라 `req.headers` 에서 터집니다.

## 🚨 문제는 여기서 시작합니다

브라우저의 WebSocket API 를 보세요.

```js
new WebSocket('wss://api.내도메인.com/ws')
```

**헤더를 붙일 자리가 없습니다.** 브라우저 `WebSocket` 생성자는 인자가 **`url` 과 `protocols` 둘뿐**이라, 2편에서 쓰던 `Authorization: Bearer <JWT>` 를 넣을 자리가 없습니다. [문서] 우회가 아니라 설계로 풀어야 합니다.

## 토큰을 전달하는 네 가지 방법

| 방법 | 장점 | 함정 |
|---|---|---|
| **① 쿠키** | 브라우저가 알아서 보냄 | **도메인 범위 + CSRF** |
| ② 쿼리 파라미터 | 간단 | **각종 로그에 그대로 남음** |
| ③ 연결 후 첫 메시지 | 헤더 제약 없음 | 인증 전 상태를 직접 관리해야 함 |
| ④ `Sec-WebSocket-Protocol` | 헤더처럼 씀 | 서버가 서브프로토콜을 되돌려줘야 함 |

> **BFF 를 쓰는 구성에서는 ②③④ 가 애초에 어렵습니다.** 토큰이 `httpOnly` 쿠키에 있어 **브라우저 JS 가 값을 못 읽기** 때문입니다. ③·④ 를 쓰려면 BFF 에 "일회용 WS 티켓 발급 라우트"를 따로 만들어야 합니다. **①이 가장 자연스럽습니다.**

### ① 쿠키 — 이 구성에 가장 잘 맞습니다

BFF 를 쓰면 토큰이 `httpOnly` 쿠키에 있습니다(1편·7편). 핸드셰이크는 HTTP 요청이라 **쿠키가 자동으로 실립니다.**

**단, 도메인 범위가 맞아야 합니다.**

```
쿠키를 app.내도메인.com 에만 걸면  →  api.내도메인.com 으로 안 감  ✗
쿠키를 .내도메인.com 에 걸면       →  둘 다 감                      ✓
```

프론트가 `app.내도메인.com`, API 가 `api.내도메인.com` 이라면 **상위 도메인에 쿠키를 걸어야** WS 핸드셰이크에 실립니다.

> **범위를 넓히면 대가가 있습니다.** `.내도메인.com` 에 걸면 **모든 서브도메인**이 그 쿠키를 받습니다. 하나가 뚫리면 세션이 샙니다. 그리고 NestJS 에 **쿠키를 읽는 인증 경로**를 새로 만들어야 합니다 — 2편의 가드는 `Authorization` 헤더만 봅니다.

### 🚨 쿠키를 쓰면 CSRF 가 열립니다

**WebSocket 핸드셰이크에는 CORS 가 적용되지 않습니다.** [추론] 브라우저가 교차 출처 WS 연결 자체를 막지 않기 때문에, 아무 사이트나 이렇게 할 수 있습니다.

```js
// evil.com 페이지에서
new WebSocket('wss://api.내도메인.com/ws')   // ← 쿠키가 자동으로 실린다
```

로그인한 사용자가 그 페이지를 열면 **공격자 페이지가 그 사용자로서 소켓을 엽니다.** `Authorization` 헤더였다면 불가능합니다 — 외부 페이지는 헤더를 못 붙이니까요.

> **4편의 원본 시크릿도 여기선 못 막습니다.** `evil.com` 이 보낸 핸드셰이크도 Cloudflare 를 거치므로 **똑같이 시크릿 헤더가 붙습니다.**

막는 방법은 둘이고, **둘 다 하세요.**

**① `SameSite=Lax`** — `app.` 과 `api.` 는 같은 등록 도메인이라 정상 핸드셰이크는 통과하고, `evil.com` 발 요청에는 쿠키가 안 실립니다.

**② `Origin` 헤더 검증** — 브라우저는 WS 업그레이드에 `Origin` 을 **항상** 보냅니다. RFC 6455 원문입니다. [문서]

> *"The request MUST include a header field with the name |Origin| if the request is coming from a browser client."*

**서버가 그걸 검사하는 게 CSWSH 의 표준 방어입니다.** 브라우저는 막아주지 않으니 여러분이 봐야 합니다.

```ts
const origin = client.request.headers.origin
if (origin !== 'https://app.내도메인.com') return client.disconnect(true)
```

### ② 쿼리 파라미터 — 피하세요

```
wss://api.내도메인.com/ws?token=eyJhbGci...    ← 이러지 마세요
```

**URL 은 로그에 남습니다.** Cloudflare·Cloud Run·프록시의 액세스 로그, 개발자 도구의 네트워크 기록, 에러 추적 도구 — 어디에 찍힐지 모릅니다. 1편에서 본 대로 **토큰은 가진 사람이 곧 그 사람**이니, 로그에 남은 토큰은 만료 전까지 그대로 유효합니다.

### ③ 연결 후 첫 메시지 — 쓸 거면 규칙을 지키세요

연결은 열어두고 첫 메시지로 토큰을 받는 방식입니다. 흔하지만 **직접 관리할 게 생깁니다.**

```ts
// 1. 인증 전 소켓은 '미인증' 상태로 표시하고
// 2. 인증 메시지 외의 모든 메시지를 거부하고
// 3. 몇 초 안에 인증 안 하면 끊고
// 4. 인증 성공을 클라이언트에게 알리고
// 5. 인증 전에는 메시지 크기·빈도를 제한한다
```

**3 번**이 없으면 인증 안 한 연결이 무한정 쌓입니다. **4 번**이 없으면 클라이언트가 인증 직후 데이터를 보내버리고, 그게 2 번에 걸려 조용히 사라집니다.

## 핸드셰이크만 검증하고 끝내면

가장 흔한 실수입니다.

```
연결 시점: JWT 검증 ✓
그 뒤 한 시간: 아무 검사 없음
```

2편에서 봤듯 액세스 토큰은 보통 **한 시간**짜리입니다. 그런데 WebSocket 은 그보다 오래 붙어 있을 수 있죠. 그럼 **만료된 신원으로 계속 대화**하게 됩니다.

로그아웃도 마찬가지입니다. 사용자가 로그아웃해도 **이미 열린 소켓은 살아 있습니다.**

**두 가지 중 하나를 고르세요.**

```
A. 토큰 만료 시각에 맞춰 서버가 연결을 끊는다
   → 클라이언트가 ★ BFF 로 세션을 갱신한 뒤 다시 붙는다

B. 주기적으로 클라이언트에게 새 토큰을 요구한다
```

**A 를 권하지만 ★ 를 빠뜨리면 안 됩니다.**

> **끊고 바로 재연결하면 무한 루프입니다.** 토큰은 `httpOnly` 쿠키에 있고 갱신하는 건 **BFF** 인데, WS 경로는 BFF 를 안 거칩니다. 그냥 재연결하면 **같은 만료 토큰**으로 붙었다가 다시 거부됩니다. 재연결 **전에 BFF 의 세션 갱신 라우트를 한 번 호출**하세요.

**B 는 그대로는 안 됩니다.** 클라이언트 JS 가 `httpOnly` 쿠키를 못 읽으니, 위에서 말한 **BFF 티켓 라우트**가 있어야 가능합니다.

> **두 가지를 더 챙기세요.**
> - **백오프에 지터를 넣으세요.** 비슷한 시각에 발급된 토큰은 비슷한 시각에 만료되고, **전원이 동시에 재연결**합니다.
> - **로그아웃은 만료를 기다리면 안 됩니다.** 위 방식만으로는 로그아웃 후에도 최대 한 시간 소켓이 삽니다. 즉시 끊으려면 **외부 저장소로 끊기 신호**를 뿌려야 합니다.

## Cloud Run 의 연결 수명

보안 이전에 구조 문제가 있습니다. 공식 문서 기준입니다. [문서]

**연결은 요청 타임아웃에 걸립니다.**

> *"WebSockets streams are HTTP requests, which are still subject to the request timeout configured for your Cloud Run service."*

**기본값이 5 분입니다.** 아무것도 안 바꾸면 5 분마다 끊기고, 이유를 모른 채 재연결만 반복하게 됩니다.

> *"They are subject to request timeouts (currently up to 60 minutes and defaults to 5 minutes)."*

최대 60 분까지 늘릴 수 있고, **현재 상한이 60 분**입니다.

**재연결은 필수입니다.**

> *"WebSockets clients connecting to Cloud Run should handle reconnecting to the server if the request times out or the server disconnects."*

**세션 어피니티는 보장이 아닙니다.**

> *"session affinity on Cloud Run provides best effort affinity, new WebSockets requests could still potentially connect to different instances, due to built-in load balancing."*

즉 **같은 사용자의 재연결이 다른 인스턴스로 갈 수 있습니다.** 인스턴스 메모리에 상태를 두면 깨집니다. 구글은 Redis 같은 외부 저장소를 권합니다.

> **비용을 정확히 말하면** — 열려 있는 WS 는 **처리 중인 요청**이라, 붙어 있는 동안 인스턴스가 유휴로 회수되지 않고 그만큼 과금됩니다. 연결을 끊는 건 스케일 투 제로가 아니라 **타임아웃·재배포·인스턴스 교체**입니다. `min-instances` 는 연결을 길게 유지해주는 게 아니라 **재연결이 빨리 붙도록 워밍**해줍니다. 어느 쪽이든 공짜가 아니니 **WebSocket 이 정말 필요한지** 재검토할 가치가 있습니다.

### 하트비트도 필요합니다

중간 장비들은 **조용한 연결을 끊습니다.** 한쪽만 끊긴 반열림 상태는 양쪽 다 모르고요. 주기적인 핑/퐁으로 확인하고 응답이 없으면 재연결하세요. 대부분의 WS 라이브러리에 있으니 **켜져 있는지만 확인**하면 됩니다.

## MCP — Access 가 제 몫을 하는 자리

0편에서 **Cloudflare Access 는 사용자용이 아니라 팀용**이라고 했습니다. 관리자 페이지·스테이징과 함께 **admin 전용 MCP** 가 그 자리입니다.

```
mcp.내도메인.com  →  Cloudflare Access (Google 로그인, 내 이메일만 허용)
                      → 통과한 요청만 Cloud Run 으로
```

**OAuth 를 직접 구현할 필요가 없습니다.** Access 가 앞에서 신원을 확인하고 통과한 요청만 뒤로 보냅니다. 무료 티어가 50 석이라 알려져 있어 소규모면 사람이 들어오는 비용은 없습니다. **다만 아래 함정을 먼저 읽으세요 — 프로그램이 들어오는 길은 별도입니다.**

설정은 대략 이렇습니다.

1. Zero Trust 대시보드에서 애플리케이션 추가
2. 도메인을 `mcp.내도메인.com` 으로 지정
3. 정책: 이메일이 내 주소와 일치
4. IdP 로 Google 연결

### 🚨 여기까지만 하면 나도 못 들어갑니다

위 설정은 **브라우저 로그인**을 전제합니다. 그런데 **MCP 클라이언트는 브라우저가 아닙니다.** Google 로그인 페이지로 리다이렉트를 받아도 **렌더링할 수 없습니다.**

즉 이메일 정책만 걸면 **공격자와 함께 나도 막힙니다.**

프로그래밍 클라이언트가 들어오는 길이 따로 있습니다. [문서]

- **서비스 토큰** — `CF-Access-Client-Id` 와 `CF-Access-Client-Secret` 헤더로 보냅니다. 공식 문서 원문 — *"add a **Service Auth policy**. This policy type accepts service token credentials instead of requiring an identity provider login."* **이메일 정책으로는 통과 못 하니 정책을 따로** 만들어야 하고, 클라이언트가 커스텀 헤더를 보낼 수 있어야 합니다. (무료 티어에서 되는지는 확인 못 했습니다.)
- **`cloudflared` 로컬 프록시** — 한 번 브라우저로 로그인해두고 로컬 포트로 접속합니다.

> **설정 절차는 여기까지만 하겠습니다.** 메뉴 이름과 절차는 자주 바뀌고 저는 이 구성을 직접 세워보지 못했습니다. **"Access 를 걸면 끝"이 아니라 "클라이언트가 들어올 길도 같이 설계해야 한다"** 는 것만 기억하세요.

### 🚨 그리고 Access 만으로는 부족합니다

Access 는 **Cloudflare 를 거쳐 들어오는 호스트**만 지킵니다. 그런데 4편에서 봤듯 `run.app` 주소는 살아 있죠.

```
정상: mcp.내도메인.com → Cloudflare Access → Cloud Run
우회: <서비스>-<번호>.<리전>.run.app → Cloud Run     ← Access 를 안 거침
```

**그리고 MCP 서버는 툴을 실행합니다.** 이 우회는 "API 하나가 열리는" 정도가 아니라 **인증 없는 툴 실행**입니다. [추론]

> **0편에서 한 말 그대로입니다** — Cloudflare 는 앞에 세우는 방어층이지 대체재가 아닙니다. **4편의 뒷문 닫기를 먼저 해야 Access 가 의미를 갖습니다.**

### MCP 가 공개라면

이야기가 완전히 달라집니다. 인증이 약하면 **남이 여러분 툴을 실행합니다.**

공개해야 한다면 MCP 스펙의 OAuth 를 제대로 붙여야 하고, 이 시리즈의 범위를 넘습니다. **admin 전용으로 두시는 게 훨씬 안전하고 훨씬 쉽습니다.**

## 체크리스트

- [ ] **`handleConnection` 에서 원본 시크릿과 JWT 를 직접 검증**한다 (전역 가드는 안 돈다)
- [ ] **`Origin` 헤더를 검증**한다 (쿠키를 쓴다면 필수)
- [ ] 쿠키에 **`SameSite=Lax`, `Secure`** 가 걸려 있다
- [ ] WS 토큰 전달 방식이 **쿼리 파라미터가 아니다**
- [ ] 쿠키를 쓴다면 **상위 도메인**에 걸려 있어 `api.` 로도 전송된다
- [ ] 첫 메시지 인증이라면 **미인증 타임아웃**이 있다
- [ ] **토큰 만료 시각에 연결을 끊는다** (또는 갱신을 요구한다)
- [ ] 재연결 **전에 BFF 로 세션을 갱신**한다
- [ ] 재연결 백오프에 **지터**가 있다
- [ ] **하트비트**가 켜져 있다
- [ ] 연결 상태를 **인스턴스 메모리에 두지 않는다**
- [ ] **요청 타임아웃을 늘렸다** (기본 5 분)
- [ ] **HTTP/2 end-to-end 를 끄고** 있다 (WebSocket 요구사항)
- [ ] `min-instances` 를 **의식적으로 정했다**
- [ ] MCP 가 **Access 뒤에** 있다
- [ ] **MCP 도 4편의 뒷문이 닫혀 있다** (Access 만으로는 `run.app` 우회를 못 막는다)
- [ ] MCP 클라이언트가 **들어올 길**(서비스 토큰 등)을 마련했다

## 확인 못 한 것

- **Cloudflare Access 무료 티어 50 석.** 여러 곳에서 그렇게 전하지만 **공식 요금 문서에서 직접 확인하지는 못했습니다.** 쓰기 전에 직접 확인하세요. 서비스 토큰이 무료 티어에서 되는지도 못 찾았습니다.
- **Cloudflare 의 WebSocket 유휴 타임아웃.** 흔히 도는 숫자가 있지만 **공식 문서에 없습니다.** 그래서 이 글에는 적지 않았습니다.
- **가드 실험은 로컬 NestJS 앱** 기준입니다. Cloud Run 에 올려서 같은 결과인지는 확인 못 했습니다.
- **`--vpc-egress` 나 앞단 구성**이 WS 핸드셰이크에 주는 영향은 다루지 않았습니다.

## 정리

- **전역 가드는 WS 에 돌지 않습니다.** 실측으로 확인했습니다. `handleConnection` 에서 직접 검증하세요.
- **브라우저 WebSocket 은 헤더를 못 붙입니다.** `Authorization` 을 쓸 수 없습니다.
- 토큰은 **쿠키로** 보내는 게 맞지만 **CSRF 가 열립니다.** `SameSite=Lax` 와 **`Origin` 검증**을 둘 다 하세요.
- **쿼리 파라미터는 피하세요.** 로그에 남습니다.
- **핸드셰이크만 검증하면 만료된 신원이 한 시간 삽니다.** 만료 시각에 끊되 **재연결 전에 BFF 로 갱신**하게 하세요.
- Cloud Run 요청 타임아웃은 **기본 5 분, 최대 60 분**이고 어피니티는 **best effort** 입니다. **재연결 로직은 선택이 아닙니다.**
- **admin 전용 MCP 는 Access 가 맞습니다.** 단 **4편의 뒷문이 닫혀 있어야** Access 가 의미를 갖고, **브라우저가 아닌 클라이언트가 들어올 길**(서비스 토큰 등)도 같이 설계해야 합니다.
