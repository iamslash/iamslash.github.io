# 0편. 프롤로그 — 멀티에이전트는 병렬화가 아니다

> 시리즈: Claude Code 멀티에이전트 (builtin 기준)
> 이 편에서 배우는 것: 에이전트를 늘리는 진짜 이유, 그 대가로 무엇을 사는지, 그리고 이 시즌의 모든 주장을 직접 확인하는 법.

시즌 1의 마지막 편에서 서브에이전트를 **25 줄**로 만들었습니다.

```python
def tool_agent(args):
    sub = [{"role": "user", "content": args["prompt"]}]   # ← 부모 messages 를 안 준다
    run_turn(sub, max_turns=10)                            # ← 같은 루프 코드를 그대로 재사용
    ...
```

격리의 정체는 대단한 장치가 아니라 **새 리스트 하나**였습니다.

그럼 이제 질문이 바뀝니다.

> **이걸 열 개 돌리려면 무엇이 필요할까요? 그리고 열 개를 돌리면 정말 좋아질까요?**

## 흔한 오해부터

에이전트를 여러 개 쓰는 이유를 물으면 대부분 이렇게 답합니다.

> "빨라지니까요. 병렬로 도니까."

**틀렸습니다.** 정확히는, 그게 주된 이유가 아닙니다. 그리고 이 오해가 멀티에이전트를 잘못 쓰게 만드는 가장 큰 원인입니다.

실측으로 시작하겠습니다.

## 262 건의 실측

제 머신에 쌓인 트랜스크립트에서 **동기 서브에이전트 호출**을 전부 찾아, 두 가지를 쟀습니다.

- 자식이 태운 토큰
- 부모에게 실제로 돌아온 `tool_result` 의 크기

```bash
cd ~/.claude/projects && python3 - <<'PY'
import json,glob
tok=0; ret=0; n=0; big=[]
for p in glob.glob('*/*.jsonl'):
    try:
        for l in open(p,errors='ignore'):
            if 'totalTokens' not in l: continue
            try: d=json.loads(l)
            except Exception: continue
            t=d.get('toolUseResult')
            if not isinstance(t,dict) or not t.get('totalTokens'): continue
            c=(d.get('message') or {}).get('content'); size=0
            if isinstance(c,list):
                for b in c:
                    if isinstance(b,dict) and b.get('type')=='tool_result':
                        cc=b.get('content')
                        size += len((cc if isinstance(cc,str) else json.dumps(cc,ensure_ascii=False)).encode('utf-8'))
            n+=1; tok+=t['totalTokens']; ret+=size
            big.append((t['totalTokens'], size, t.get('agentType')))
    except Exception: pass
big.sort(reverse=True)
print(f"동기 Agent 호출 {n}건")
print(f"  자식 컨텍스트 최종 크기 합 : {tok:,} 토큰")
print(f"  부모가 받은 바이트         : {ret:,}  (≈ {ret/4:,.0f} 토큰)")
print(f"  → 약 1/{tok/max(ret/4,1):.0f}")
print("가장 큰 3건:")
for t_,s_,a_ in big[:3]: print(f"  {t_:>9,} 토큰 → {s_:>5,} 바이트   [{a_}]")
PY
```

제 머신 결과입니다. [관찰]

```
동기 Agent 호출 262건
  자식 컨텍스트 최종 크기 합 : 17,382,294 토큰
  부모가 받은 바이트         : 108,364  (≈ 27,091 토큰)
  → 약 1/642
가장 큰 3건:
    212,626 토큰 →   356 바이트   [general-purpose]
    190,158 토큰 →   358 바이트   [general-purpose]
    187,649 토큰 → 7,220 바이트   [general-purpose]
```

> **자식들의 컨텍스트가 도합 1,738 만 토큰까지 부풀었고, 그중 부모 컨텍스트에 들어온 건 10 만 바이트입니다.**
> 가장 극단적인 한 건은 **컨텍스트가 212,626 토큰까지 갔는데 356 바이트를 돌려줬습니다.**

**여기서 `totalTokens` 가 무엇인지 정확히 짚고 가겠습니다.** 이건 "자식이 태운 요금"이 아닙니다. 자식의 **마지막 API 호출의 usage 합**입니다 — 262 건 전부에서 정확히 일치하는 것을 확인했습니다. [관찰]

```
cache_read       17,328,585  (99.69%)
cache_creation       36,855  ( 0.21%)
output               16,000  ( 0.09%)
input                   854  ( 0.00%)
```

**99.7% 가 캐시 읽기입니다.** 즉 이 숫자는 **자식이 마지막 순간에 들고 있던 컨텍스트의 크기**이지, 청구액이 아닙니다. (실제 누적 지출은 매 턴이 쌓이므로 이보다 크고, 대신 캐시 읽기는 기본 입력보다 훨씬 쌉니다.)

**그런데 이 시즌의 논지에는 이쪽이 더 정확합니다.** 우리가 알고 싶은 건 비용이 아니라 **컨텍스트**니까요. 자식의 컨텍스트가 21 만 토큰까지 부풀었고, 부모 컨텍스트에는 356 바이트(≈89 토큰)만 들어왔다 — **컨텍스트 대 컨텍스트** 비교입니다.

바이트를 토큰으로 환산한 건 대략치입니다(영문 4 바이트 ≈ 1 토큰 가정). 자릿수만 보세요 — 합산하면 **약 1/642** 입니다. 참고로 **건별 중앙값은 약 1/915** 로, 전형적인 경우가 오히려 더 극단적입니다. [관찰]

## 그래서 진짜 이유는 이것입니다

시즌 1 의 0편에서 세운 명제를 기억하시나요?

> **LLM API 는 상태가 없다. 매 턴 전부를 다시 보낸다.**

여기서 전부 따라 나옵니다. 파일 마흔 개를 열어본 흔적이 대화 이력에 남으면, 그 마흔 개가 **이후 모든 요청에 따라다닙니다.** 답은 세 줄인데 말이죠.

서브에이전트는 그 탐색을 **다른 방에서** 하게 하고 **결론만** 받아옵니다.

```
[혼자 할 때]                      [나눠서 할 때]
messages: 40개 파일 내용 전부      messages: "인증은 auth/ 에 있습니다" 한 줄
        ↓ 이후 매 요청에 재전송            ↓ 이후 매 요청에 재전송
        비용이 계속 붙는다                  거의 안 붙는다
```

> **이 시즌을 관통하는 명제입니다.**
> **멀티에이전트는 병렬화가 아니라 컨텍스트 분할이다.**

속도는 부수 효과입니다. 그리고 **반대로 가는 경우도 있습니다** — 조율 비용 때문에 오히려 느려질 수 있습니다. [추론] 6편에서 실측으로 확인합니다.

## 공짜가 아닙니다

컨텍스트를 아끼는 대신 무엇을 지불할까요? 미리 목록만 보면 이렇습니다.

- **브리핑 비용** — 자식은 부모 대화를 못 봅니다. 필요한 걸 전부 다시 써줘야 합니다.
- **대기 시간** — 부모가 자식을 기다리는 동안 노는 시간이 생깁니다. (6편에서 실측합니다)
- **토큰 증폭** — 자식들의 컨텍스트 합이 부모보다 훨씬 커집니다. [추론]
- **재현 불가** — 같은 위임이 매번 다르게 흘러갑니다. [추론]
- **디버깅 난이도** — 부모 트랜스크립트에는 결론만 있어서, 원인은 자식 파일을 열어야 나옵니다.
- **신뢰 문제** — 자식이 웹페이지를 읽고 온다면, 그 내용을 그대로 믿어도 될까요?

마지막 항목이 특히 중요합니다. 1편에서 바로 다룹니다.

## 이 시즌에서 볼 것

| 편 | 주제 |
|---|---|
| 1편 | 위임의 해부 — 브리핑이 전부다, 그리고 자식의 대답을 왜 못 믿나 |
| 2편 | 격리의 스펙트럼 — `fork`, `observer`, 에이전트 메모리 |
| 3편 | Workflow ① — 결정적 오케스트레이션의 계약 |
| 4편 | Workflow ② — `pipeline` vs `parallel`, 그리고 재개 캐시 |
| 5편 | worktree 격리와 교차 세션 메시징 |
| 6편 | 한계와 안티패턴 — **언제 멀티에이전트가 손해인가** |

**6편이 이 시즌의 목적지**입니다. 멀티에이전트 이야기는 대개 응원가인데, 저는 "이럴 땐 쓰지 마세요"를 실측으로 쓰고 싶었습니다.

## 관찰 도구 — 시즌 1 에 세 개를 더합니다

시즌 1 에서 쓰던 세 가지는 그대로입니다.

1. 세션 트랜스크립트 `~/.claude/projects/*/*.jsonl` + `jq`
2. `claude --debug api`
3. 로컬 싱크 프록시 (가짜 API 키로 요청 바디 캡처)

여기에 멀티에이전트 전용으로 세 개를 더합니다.

### 4. 자식의 트랜스크립트

```bash
ls ~/.claude/projects/*/*/subagents/ 2>/dev/null | head
```

자식은 **자기만의 JSONL** 을 남깁니다. 부모 기록에는 결론만 있으므로, **무슨 일이 있었는지 알려면 여기를 봐야 합니다.**

### 5. 워크플로 저널

```bash
find ~/.claude/projects -name journal.jsonl | head
```

Workflow 를 쓰면 `journal.jsonl` 이 생깁니다. 어떤 에이전트가 언제 시작하고 끝났는지가 한 줄씩 쌓여서, **실행 순서를 그대로 재구성할 수 있습니다.** 3·4편의 주 무기입니다.

### 6. 세션 명부

```bash
ls ~/.claude/sessions/
```

지금 돌고 있는 Claude Code 프로세스들의 명부입니다. 세션끼리 메시지를 주고받는 통로가 여기서 시작합니다. 5편에서 씁니다.

> 시즌 1 의 부록(`~/.claude` 안내 지도)에서 이 세 경로를 이미 지나쳤습니다. **이번 시즌은 그 디렉터리들이 주인공입니다.**

## 이 시즌의 규칙

시즌 1 과 같습니다. 다만 **버전 표기에 한 가지 주의**가 생겼습니다.

이 시즌을 조사하는 동안 제 머신이 **2.1.243 → 2.1.245 → 2.1.246** 으로 자동 업데이트됐습니다. 그리고 2.1.246 부터는 JS 소스 일부가 **바이트코드로 컴파일**되어 `strings` 추출이 예전만큼 듣지 않습니다.

그래서 이렇게 나눕니다.

- **코드 인용은 2.1.243** — 평문 JS 가 남아 있는 마지막 버전
- **동작 실험은 2.1.246** — 지금 실제로 도는 바이너리

```bash
claude --version
ls -la ~/.local/share/claude/versions/     # 옛 버전이 파일로 남아 있습니다
```

증거 라벨도 그대로입니다.

- **[관찰]** — 직접 실행해서 본 것
- **[문서]** — 공식 문서에 있는 것
- **[추론]** — 정황으로 미루어 짐작한 것

그리고 각 편 말미의 **"확인 못 한 것"** 도 유지합니다. 이번 시즌엔 그게 꽤 됩니다 — 기능 게이트에 막혀 못 본 것들이 있습니다.

## 정리

- 멀티에이전트의 진짜 이득은 **속도가 아니라 컨텍스트 분할**입니다.
- 실측: 동기 호출 **262 건에서 자식 컨텍스트 합이 1,738 만 토큰**까지 갔고, 부모에게 돌아온 건 **10 만 바이트(합산 약 1/642, 건별 중앙값 약 1/915)** 였습니다.
- 대가는 브리핑 비용, 대기 시간, 토큰 증폭, 재현 불가, 디버깅 난이도, 그리고 **신뢰 문제**입니다.
- 관찰 도구가 셋 늘었습니다 — **자식 트랜스크립트 · 워크플로 저널 · 세션 명부**.

다음 편에서는 **위임 그 자체**를 봅니다. 자식에게 무엇을 주고 무엇을 받는지, 브리핑을 잘못 쓰면 어떻게 되는지, 그리고 **자식이 돌려준 텍스트를 왜 그대로 믿으면 안 되는지**.
