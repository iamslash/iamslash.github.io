# 4편. Workflow ② — pipeline vs parallel, 그리고 재개 캐시

> 시리즈: Claude Code 멀티에이전트 (builtin 기준)
> 이 편에서 배우는 것: `journal.jsonl` 읽는 법, **`pipeline` 에 배리어가 없다는 직접 증거**, 재개가 **0 토큰·10ms** 로 도는 것, 그리고 그 캐시가 언제 깨지는지.

3편 끝에서 하네스가 이렇게 시켰습니다.

> *"결과가 이상하면 진단하기 전에 `journal.jsonl` 부터 읽어라."*

이번 편은 그 파일을 여는 편입니다.

## 저널의 구조

한 줄이 하나의 사건입니다. `started` 아니면 `result` 뿐입니다.

```bash
W=$(dirname $(find ~/.claude/projects -name journal.jsonl | head -1))
python3 -c "
import json
for i,l in enumerate(open('$W/journal.jsonl'),1):
    if not l.strip(): continue
    d=json.loads(l)
    print(f\"{i:2d} {d.get('type'):8s} {str(d.get('agentId'))[:18]:18s} {str(d.get('key'))[:22]:22s} {str(d.get('result'))[:34]}\")"
```

3편의 프로브(항목 2 개 × 단계 2 개)를 돌린 뒤의 앞 8 줄입니다. [관찰]

```
 1 started  ae1a13e5535bb388f  v2:7b62fc1d5379a243111 None
 2 started  a9b596131044770f1  v2:4ca2ef7100e3e7a29e0 None
 3 result   a9b596131044770f1  v2:4ca2ef7100e3e7a29e0 {'value': 'beta'}
 4 started  a9d275ffb02d2424e  v2:8b9139f3d3c432a49ea None
 5 result   ae1a13e5535bb388f  v2:7b62fc1d5379a243111 {'value': 'alpha'}
 6 started  a72e586ab2140f57b  v2:5f0682beb0bceeeb711 None
 7 result   a9d275ffb02d2424e  v2:8b9139f3d3c432a49ea {'value': 'beta-1'}
 8 result   a72e586ab2140f57b  v2:5f0682beb0bceeeb711 {'value': 'alpha-0'}
```

- **`key`** 는 `v2:<64자리 hex>` 형태입니다. sha256 으로 보입니다. [추론] 이게 **재개 캐시의 키**입니다.
- `result` 줄에 자식의 반환값이 그대로 들어갑니다.
- **캐시로 재생된 실행은 저널에 아무것도 추가하지 않습니다.** 제가 6 회를 돌렸는데 저널은 16 줄에서 멈춰 있습니다. [관찰]

## 증거 — `pipeline` 에는 배리어가 없다

위 8 줄을 값으로 치환해서 다시 보세요.

```
 1 started  alpha  (Stage1)
 2 started  beta   (Stage1)
 3 result   beta   (Stage1)   ← beta 가 1단계를 먼저 끝냈다
 4 started  beta   (Stage2)   ← ★ alpha 를 기다리지 않고 즉시 2단계 진입
 5 result   alpha  (Stage1)   ← alpha 는 이제야 1단계 완료
 6 started  alpha  (Stage2)
 7 result   beta   (Stage2)
 8 result   alpha  (Stage2)
```

**4 번 줄이 5 번 줄보다 먼저입니다.**

`beta` 는 `alpha` 가 1 단계를 끝내기도 전에 2 단계에 들어갔습니다. `parallel` 이었다면 **불가능한 순서**입니다.

### 그림으로

```
parallel:   [A1  A2  A3] ──전부 끝날 때까지 대기──> [B1  B2  B3]
             ↑ A2가 느리면 A1·A3의 B단계가 놀고 있음

pipeline:    A1 ──> B1
             A2 ──────────> B2
             A3 ──> B3
             ↑ 각 항목이 독립적으로 끝까지 간다
```

**`parallel` 은 배리어(barrier)입니다.** 모든 항목이 그 단계를 끝내야 다음으로 갑니다. **`pipeline` 은 아닙니다.** 항목마다 자기 속도로 끝까지 갑니다.

### 그럼 언제 `parallel` 을 쓰나

배리어가 필요할 때만입니다. **다음 단계가 이전 단계의 결과 *전부* 를 봐야 할 때**죠.

| 상황 | 선택 |
|---|---|
| 항목별로 독립 처리 | **`pipeline`** — 기본으로 이걸 쓰세요 |
| 전체 결과를 모아 중복 제거한 뒤 진행 | `parallel` |
| 결과가 0 개면 다음 단계를 통째로 건너뛰어야 함 | `parallel` |
| 다음 단계 프롬프트가 "다른 결과들과 비교"를 요구 | `parallel` |
| "일단 flatten/filter 부터 해야 해서" | **`pipeline`** — 변환은 단계 안에서 하면 됩니다 |

마지막 줄이 흔한 함정입니다. 중간에 리스트를 손봐야 한다는 이유로 배리어를 쓰면, **느린 항목 하나 때문에 나머지가 전부 대기**합니다.

## 재개 캐시 — 0 토큰, 10 밀리초

같은 워크플로를 **6 회** 돌리면서 매번 조금씩 바꿔봤습니다. [관찰]

| # | 무엇을 바꿨나 | agent_count | 실제 실행 | 토큰 | 소요 |
|---|---|---|---|---|---|
| 1 | 최초 실행 | 4 | **4** | 99,579 | 10,083ms |
| 2 | `parallel` 단계 추가 | 6 | **4** | 99,586 | 7,652ms |
| 3 | **무편집 재개** | 6 | **0** | **0** | **8ms** |
| 4 | 파일 **맨 끝에** 주석 1 줄 추가 | 6 | **0** | **0** | **10ms** |
| 5 | 원본 스크립트로 되돌림 | 4 | **0** | **0** | **7ms** |
| 6 | `meta.phases` 에만 항목 추가 | 4 | **0** | **0** | **5ms** |

**3~6 번을 보세요. 0 토큰, 한 자릿수 밀리초입니다.**

### 어떻게 부르나

`Workflow` 는 여러분이 터미널에 치는 명령이 아니라 **모델이 호출하는 툴**입니다. 그래서 사용법은 "이렇게 시킨다"가 됩니다.

```
워크플로로 돌려줘. 스크립트는 이거야:
(여기에 export const meta = {...} 부터 스크립트 전문)
```

3편에서 봤듯 **명시적으로 요청해야** 부릅니다. 그러면 결과에 `runId` 와 **스크립트 사본 경로**가 같이 옵니다. 고쳐서 다시 돌릴 땐 그 파일을 편집하고 이렇게 시킵니다.

```
저 스크립트 파일 그대로, runId wf_3a32cfa1-107 로 재개해줘
```

모델이 내부적으로 부르는 형태는 이렇습니다.

```
Workflow({ scriptPath: "<스크립트 사본 경로>",
           resumeFromRunId: "wf_3a32cfa1-107" })
```

### 무엇이 캐시를 깨지 않나

통제 실험으로 확인한 것들입니다. [관찰]

**1) 파일 전체 해시가 아닙니다.** 파일 **맨 끝에** 주석을 한 줄 덧붙여도 100% 히트했습니다(4 번).

```bash
printf '\n// cache-probe\n' >> "$SCRIPT"     # EOF 에 한 줄 append
```

**2) `meta` 는 캐시 키에 없습니다.** `meta.phases` 에만 항목을 추가해도 히트했습니다(6 번).

**3) 편집했다가 되돌려도 히트합니다.** 원본으로 복원했더니 4 개 전부 히트했습니다(5 번).

> 단, 이걸 **"원래 키가 되살아났다"고 읽으면 안 됩니다.** 캐시 재생은 저널에 아무것도 안 남기므로(위에서 본 성질), **어느 키가 쓰였는지 확인할 방법이 없습니다.** 2 회차에서 새로 만들어진 Stage2 키도 캐시에 남아 있으니, 5 번의 "0 회 실행"은 둘 중 무엇으로도 설명됩니다. **관찰된 건 "다시 안 돌았다"뿐입니다.** [관찰]

즉 캐시 키는 **각 `agent()` 호출의 프롬프트와 옵션**을 중심으로 만들어집니다.

### 그런데 하나가 깨졌습니다

2 번을 다시 보세요. `parallel` 단계를 새로 추가했더니 `agent_count` 가 6 인데 **실제 실행이 4** 였습니다. 새 에이전트 2 개가 도는 건 당연한데, **왜 4 개일까요?**

저널 9~12 줄이 답입니다. [관찰]

```
 9 started  a098ae8919a746653  v2:1dc7c2a9... None
10 started  a25f4caa7061be171  v2:352f0e4c... None
11 result   a25f4caa7061be171  v2:352f0e4c... {'value': 'alpha-0'}
12 result   a098ae8919a746653  v2:1dc7c2a9... {'value': 'beta-1'}
```

`alpha-0` 과 `beta-1` — **Stage 2 의 결과입니다.** 프롬프트도 옵션도 안 바꿨는데 **새 키로 다시 실행됐습니다.**

- 1 회차 Stage2 키: `v2:8b9139f3…` (beta-1), `v2:5f0682be…` (alpha-0)
- 2 회차 Stage2 키: `v2:1dc7c2a9…` (beta-1), `v2:352f0e4c…` (alpha-0)

**원인은 특정하지 못했습니다.** [확인 못 함]

확실히 배제된 건 둘입니다 — **파일 전체 해시가 아니고**(4 번), **`meta` 도 아닙니다**(6 번). 둘 다 바꿔도 히트했으니까요.

> **4 번 실험의 한계를 짚어둡니다.** 제가 넣은 주석은 **파일 맨 끝**이라 어떤 `agent()` 호출의 위치도 밀지 않습니다. 그래서 **아래 가설(위치가 키에 들어간다)을 검증하지 못합니다.** 배제한 건 "파일 해시"뿐이고, 위치 가설은 **손도 못 댄 상태**입니다. 제대로 하려면 첫 `agent()` **앞에** 줄을 넣어봤어야 했습니다.

남은 가설은 **캐시 키에 실행 순서상의 위치가 들어간다**는 것입니다. 첫 재개 때 Stage1 이 즉시 캐시 재생되면서 Stage2 호출의 발행 순서가 1 회차와 달라졌을 수 있습니다. [추론] **검증하지 못했으니 가설로만 받아주세요** — 캐시 키를 만드는 함수를 번들에서 찾지 못했습니다.

### 실용적 결론

> **스크립트를 안 건드리면 재개는 사실상 공짜입니다.** 0 토큰, 10ms 이내.
>
> **하지만 단계를 새로 추가하면 앞 단계까지 다시 돌 수 있습니다.** 비싼 워크플로를 고칠 때는 "새 단계만 돌겠지"라고 가정하지 마세요.

이 성질 때문에 워크플로를 개발하는 방식이 달라집니다.

1. **작게 시작하세요.** 사소한 작업으로 뼈대를 먼저 맞춥니다. 제 프로브가 "이 단어를 그대로 반환하라" 수준이었던 이유입니다.
2. **뼈대가 맞으면 프롬프트를 채웁니다.** 이때부터 재개가 이득을 봅니다.
3. **뒤에서부터 고치세요.** 앞 단계를 건드리면 그 뒤가 다시 돌 가능성이 큽니다. [추론] — 위의 미해결 현상 때문에 확언할 수는 없지만, 안전한 쪽으로 작업하는 게 낫습니다.

## 저널로 디버깅하기

3편에서 본 안내를 다시 보면 이유가 분명합니다.

```
If the result above is empty or unexpected, Read this file BEFORE diagnosing.
```

워크플로가 이상한 결과를 냈을 때, 부모에게 오는 건 **최종 반환값 하나**입니다. 중간에 어느 에이전트가 빈 결과를 냈는지는 안 보입니다. 저널에는 **에이전트별 반환값이 그대로** 있습니다.

빈 결과를 찾는 한 줄입니다.

```bash
python3 -c "
import json
for l in open('$W/journal.jsonl'):
    if not l.strip(): continue
    d=json.loads(l)
    if d.get('type')=='result' and not d.get('result'):
        print('빈 결과:', d.get('agentId'))"
```

제 프로브에서는 아무것도 안 나옵니다 — 8 개 다 정상 반환했으니까요. **출력이 비어 있으면 좋은 것입니다.**

3편에서 본 `agents_empty_result` 필드와 짝을 이룹니다. **빈 결과가 흔하다는 걸 하네스가 알고 있어서** 세는 필드까지 만들어둔 것이죠.

그리고 저널로 **실행 순서를 재구성**할 수 있습니다. 위에서 `pipeline` 의 배리어 없음을 증명한 방식 그대로입니다. 병목이 어디인지, 무엇이 무엇을 기다렸는지가 다 보입니다.

## 정리

- **`journal.jsonl` 이 워크플로의 블랙박스 기록**입니다. `started`/`result` 두 종류뿐이고, `key` 가 캐시 키입니다.
- **`pipeline` 에는 배리어가 없습니다.** 저널에서 `started(beta-Stage2)` 가 `result(alpha-Stage1)` 보다 먼저 나온 것이 직접 증거입니다.
- **`parallel` 은 배리어**입니다. 다음 단계가 이전 결과 **전부** 를 봐야 할 때만 쓰세요.
- **재개는 사실상 공짜입니다** — 0 토큰, 5~10ms. 4 회 재현했습니다.
- 캐시 키는 파일 해시도 `meta` 도 아닙니다. **각 `agent()` 호출의 프롬프트·옵션** 중심입니다.
- **단, 단계를 추가하면 앞 단계까지 다시 돌 수 있습니다.** 원인은 확인하지 못했습니다.
- **캐시 재생은 저널에 기록을 남기지 않습니다.** 6 회를 돌려도 16 줄 그대로였습니다.

## 확인 못 한 것

1. **단계 추가가 이전 단계 캐시를 깨뜨린 원인.** 두 가지를 배제했지만 진짜 이유는 못 찾았습니다. 캐시 키 생성 함수를 번들에서 특정하지 못했습니다.
2. **동시 실행 상한**(`min(16, CPU-2)`)에 실제로 부딪혀보지 않았습니다. 제 프로브는 최대 2 개 동시 실행이었습니다.
3. **`budget`** 은 값만 확인했습니다(예산 지시가 없으면 `null`). 예산 기반 적응형 팬아웃은 돌려보지 않았습니다.
4. 캐시가 **세션을 넘어서도** 유효한지 확인하지 못했습니다. 문서상 `resumeFromRunId` 는 **같은 세션 안에서만** 동작한다고 돼 있습니다. [문서]

다음 편에서는 **파일을 건드리는** 병렬 작업을 봅니다. 에이전트 다섯이 같은 저장소를 동시에 고치면 어떻게 되는지, git worktree 격리가 그걸 어떻게 푸는지, 그리고 **변경이 자동으로 돌아오지 않는다는** 것을.
