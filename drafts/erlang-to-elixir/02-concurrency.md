# 동시성: 수백만 프로세스와 BEAM 스케줄러

이 글은 "대용량 메시지 처리 도구: Erlang 에서 Elixir 까지" 시리즈의 두 번째 글이다. 앞 글에서는 통신 산업의 요구가 어떻게 Erlang 을 낳았고, WhatsApp·Discord·Ericsson 이 왜 이 런타임 위에서 성공했는지, 그리고 이 시리즈를 관통할 세 축(동시성·격리성·감독성)과 스코어카드를 소개했다. 이번 글은 그 첫 축인 **동시성**을 파고든다. BEAM 이 어떻게 수백만 개의 프로세스를 동시에 돌리는지, 그 아래의 스케줄러는 무엇을 다르게 하는지, 그리고 Go·Java·C++ 와 나란히 놓았을 때 진짜로 무엇이 다르고 무엇이 같은지를 정직하게 따진다.

미리 결론을 던져 두겠다. 동시성 하나만 놓고 보면 BEAM 은 더 이상 독보적이지 않다. Go 고루틴과 Java 가상 스레드(Loom)는 사용 편의성에서 BEAM 과 막상막하다. 이 글은 그 사실을 숨기지 않는다. BEAM 을 정당화하는 진짜 이유는 다음 글(격리성·감독성)에서 드러난다. 그러니 이 글은 "동시성은 필요조건이지 충분조건이 아니다"라는 이야기이기도 하다.

## BEAM 경량 프로세스: OS 스레드가 아니다

Erlang 을 처음 보는 사람이 가장 먼저 오해하는 지점이 바로 "프로세스"라는 단어다. Erlang 의 프로세스는 OS 프로세스도 아니고 OS 스레드도 아니다. 이것은 **BEAM 가상 머신 안에서만 존재하는 경량 실행 단위**다. `fork()` 나 `pthread_create()` 같은 커널 호출은 일어나지 않는다. 프로세스를 하나 만드는 것은 그저 BEAM 힙 위에 작은 자료구조를 하나 얹는 일에 가깝다.

가벼움의 규모가 핵심이다. 생성 직후의 Erlang 프로세스는 현대 64-bit BEAM 기준 대략 수 KB 규모의 메모리로 시작한다(공식 예시 기준 약 327 워드 ≈ 2.6 KiB, 초기 힙은 233 워드이며, 정확한 값은 OTP 버전과 아키텍처에 따라 달라진다). 반면 OS 스레드는 보통 스택으로만 수백 KB~수 MB 를 예약한다. 이 두세 자릿수 차이가 "수천 개"와 "수백만 개"를 가른다. WhatsApp 이 서버 한 대에서 200 만 개가 넘는 동시 연결을 처리했다는 유명한 사례는 마법이 아니라, 연결 하나당 프로세스 하나라는 설계가 이 비용 구조 위에서 자연스럽게 성립했기 때문이다. 다만 경량이라고 공짜는 아니다. 프로세스 100 만 개면 프로세스 기준선만으로도 메모리가 수 GB 에 이를 수 있고, 각자의 상태와 메일박스는 여기에 별도로 얹힌다. OS 스레드보다 훨씬 가벼울 뿐 비용이 없는 게 아니므로, 규모를 잡을 때는 실제 workload 를 측정해야 한다.

두 번째 핵심은 **share-nothing 메시지 패싱**이다. Erlang 의 값은 불변(immutable)이고, 각 프로세스는 자기만의 가변 힙을 따로 가진다. 다른 프로세스와 소통하는 유일한 통로는 메시지를 보내는 것이고, 메시지는 상대의 메일박스(mailbox, 프로세스마다 하나씩 있는 받은 편지함으로, 기본적으로 크기 제한이 없어 수신이 느리면 계속 쌓여 메모리가 늘어난다)로 복사되어 들어간다. 이렇게 보통의 값은 서로 공유되지 않으므로, 일반적인 값을 두고 두 프로세스가 경쟁하는 data race 는 생기지 않는다. 다만 "메모리를 전혀 공유하지 않는다"는 절대적 표현은 정확하지 않다. 큰 ref-counted 바이너리는 실제 저장소(backing storage)를 여러 프로세스가 공유할 수 있고, ETS·`:atomics`·`:counters` 는 아예 명시적으로 공유되는 가변 시설이다. 이들에 원자적(atomic) 연산이 제공되더라도, 여러 연산을 하나로 묶은 로직에는 여전히 race 가 생길 수 있다. 이 share-nothing 성질은 이번 글의 주제인 동시성보다 다음 글의 주제인 격리성에서 더 크게 빛나지만, 동시성을 안전하게 확장하는 토대이기도 하다.

## BEAM 스케줄러: 아무도 CPU 를 독점하지 못한다

프로세스가 아무리 가벼워도, 그것들을 CPU 위에 어떻게 얹느냐가 나쁘면 소용없다. 여기서 BEAM 스케줄러가 등장한다.

BEAM 은 기본적으로 **사용 가능한 논리 프로세서(logical processor) 수에 맞춰 일반(normal) 스케줄러 스레드를 online 상태로** 띄우며, 이 개수는 설정으로 바꿀 수 있다. 8 코어 머신이면 대개 8 개의 스케줄러가 각자 실행 큐를 들고 수백만 개의 프로세스를 나눠 돌린다. 스케줄러들끼리는 부하가 한쪽에 몰리지 않도록 프로세스를 훔쳐 가며(work stealing) 균형을 맞춘다. 즉 개발자가 스레드 풀 크기를 튜닝하거나 작업을 코어에 수동으로 배분할 필요가 없다. 여기에 더해, 오래 걸리는 네이티브 CPU 연산이나 블로킹 I/O 를 위해서는 이 일반 스케줄러와 분리된 별도의 dirty scheduler 를 둔다.

가장 중요한 특징은 **선점형(preemptive) 스케줄링**이다. 많은 언어의 협력형 async 런타임(예: 명시적 `await` 지점이 있어야 양보하는 모델)과 달리, BEAM 은 프로세스에게 "이제 그만 양보해라"라고 강제할 수 있다. 그 구현이 바로 **reduction 카운트**다. reduction 은 함수·BIF 호출 등을 대략적인 작업량으로 세는 VM 내부 단위이고, 각 프로세스는 실행되면서 이 카운트를 소모한다. 정해진 예산(OTP 19.2 이후 일반 프로세스는 보통 최대 4000 reduction)을 다 쓰면, 그 프로세스가 무한 루프를 돌든 무거운 계산을 하든 상관없이 스케줄러가 강제로 실행권을 회수하고 다음 프로세스에게 넘긴다. 다만 이 선점은 순수 BEAM 코드나 협조적으로 설계된 BIF 에 해당하는 이야기다. 오래 실행되는 일반 NIF(native 로 짠 함수)는 중간에 스스로 양보하지 않아 스케줄러를 막을 수 있으므로, 작업을 잘게 쪼개거나 dirty scheduler 에 태워야 한다.

이 한 문장의 함의가 크다. **어떤 프로세스도 CPU 를 독점할 수 없다.** 하나의 프로세스가 폭주해도 다른 수백만 개는 계속 공평하게 돌아간다. 그래서 BEAM 시스템은 부하가 걸려도 응답 시간(latency)이 예측 가능하게 유지된다. "한 요청이 오래 걸려도 다른 요청들이 굶지 않는다"는 성질은 메시지 게이트웨이 같은 다중 접속 시스템에서 결정적이다.

지연이 낮은 두 번째 이유는 **GC 모델**에 있다. 프로세스마다 힙이 분리되어 있으므로, 가비지 컬렉션도 프로세스 단위로 일어난다. 한 프로세스가 GC 를 해도 그 프로세스만 잠깐 멈출 뿐, 일반적인 힙 GC 가 시스템 전체를 함께 얼리는 일은 피한다. JVM 이 전통적으로 씨름해 온 "GC 가 돌면 전 애플리케이션이 수십~수백 ms 멈춘다"는 식의 전역 정지는 BEAM 의 프로세스별 GC 에서는 구조적으로 잘 생기지 않는다. 다만 이것이 BEAM 전체에 어떤 pause 도 없다거나 지연이 보장된다는 뜻은 아니다. 힙이나 메일박스가 커진 프로세스, 과부하 상태, 오래 실행되는 NIF 는 여전히 지연을 키운다. 그래도 각 힙이 작고 짧게 살다 죽는 흔한 경우에는 개별 GC 도 짧고, 이 두 가지(선점 + 프로세스별 GC)가 합쳐져 BEAM 이 흔히 보이는 "낮고 일정한 꼬리 지연(tail latency, 가장 느린 상위 몇 % 요청의 응답 시간)"을 만든다.

## OS 스레드 모델과의 대비: 왜 1:1 로는 안 되는가

그렇다면 왜 그냥 OS 스레드를 수백만 개 만들면 안 될까? 답은 비용에 있다.

OS 스레드는 커널이 관리하는 무거운 객체다. 각 스레드는 전용 스택 메모리를 예약하고(리눅스 기본 8MB, 실제 커밋은 더 적지만 주소 공간은 예약된다), 커널 안에 스케줄링 자료구조를 가진다. 스레드 사이를 전환할 때마다 커널 모드로 진입해 레지스터를 저장·복원하는 컨텍스트 스위치 비용을 치른다. 스레드가 수천 개를 넘어가면 이 컨텍스트 스위칭 자체가 CPU 시간을 잡아먹기 시작하고, 스택 예약만으로도 메모리가 바닥난다. 그래서 "OS 스레드 = 실행 단위"라는 1:1 모델로는 동시성 규모가 커널이 감당하는 수천~수만 개 언저리에서 벽에 부딪힌다.

BEAM 프로세스, Go 고루틴, Java 가상 스레드는 모두 이 벽을 같은 전략으로 넘는다. **다수의 경량 사용자 공간 실행 단위를 소수의 OS 스레드 위에 M:N 으로 다중화**하는 것이다(M:N 이란 M 개의 경량 작업이 N 개의 OS 스레드를 나눠 쓴다는 뜻이다). 런타임이 자체 스케줄러로 이들을 OS 스레드에 얹었다 내렸다 하며, 커널은 소수의 스레드만 본다. 이름만 다를 뿐(프로세스 / goroutine / virtual thread) 본질은 같은 아이디어다. 그래서 뒤에서 보겠지만 이 셋의 동시성 능력은 실제로 엇비슷하다.

## 4개 언어로 보는 카운터와 100만 스폰

이제 같은 문제를 네 언어로 풀어 보자. 문제는 시리즈 전체를 관통할 척추 예제다. **정수 상태(count)를 가진 서버가 `inc`(증가)와 `get`(조회) 메시지를 받는다.** 그리고 이런 단위를 100 만 개 만들 수 있는지 본다.

### Erlang: 프로세스가 곧 상태다

```erlang
-module(counter).
-export([start/0, loop/1]).

start() ->
    spawn(fun() -> loop(0) end).   % 프로세스 하나 = 카운터 하나

loop(Count) ->
    receive
        inc ->
            loop(Count + 1);
        {get, From} ->
            From ! {count, Count},
            loop(Count)
    end.
```

`loop/1` 은 꼬리 재귀 함수이고, 인자 `Count` 가 곧 이 프로세스의 상태다. `receive` 에서 메시지를 기다리다가 `inc` 가 오면 증가한 값으로 다시 자기를 호출하고, `{get, From}` 이 오면 보낸 쪽에 값을 돌려준다. 락도, 필드도, 클래스도 없다. 상태는 그저 재귀의 인자로 흐른다.

이 카운터를 100 만 개 만드는 것은 한 줄이다.

```erlang
Pids = [counter:start() || _ <- lists:seq(1, 1_000_000)].
%% 각 프로세스는 수 KB 규모. 100만 개면 기준선만 수 GB — 가능하지만 공짜는 아니다.
```

리스트 컴프리헨션으로 100 만 번 `spawn` 을 돌린다. 프로세스 하나가 수 KB 규모이니 기준선만으로도 총합이 수 GB 에 이르고, 여기에 각 프로세스의 상태와 메일박스가 더해진다. OS 스레드로는 시도조차 못 했을 규모를 BEAM 은 감당하지만, "공짜"가 아니라 "훨씬 싸다"가 정확한 표현이다. 실제로 얼마나 드는지는 workload 를 측정해 확인해야 한다.

### Go: 고루틴과 채널 — BEAM 프로세스의 가장 가까운 사촌

```go
type counter struct {
    inc chan struct{}
    get chan chan int
}

func newCounter() *counter {
    c := &counter{inc: make(chan struct{}), get: make(chan chan int)}
    go func() {              // goroutine 하나 = 카운터 하나
        n := 0
        for {
            select {
            case <-c.inc:
                n++
            case reply := <-c.get:
                reply <- n
            }
        }
    }()
    return c
}
```

구조가 놀랄 만큼 Erlang 과 닮았다. 고루틴 하나가 카운터 하나를 맡고, 상태 `n` 은 그 고루틴의 로컬 변수로 갇혀 있다. 바깥 세계는 채널을 통해서만 `inc` 나 `get` 을 요청한다. `select` 는 Erlang 의 `receive` 에 대응한다. Go 의 슬로건 "메모리를 공유하지 말고 통신으로 공유하라"가 그대로 코드가 된 모습이다.

```go
for i := 0; i < 1_000_000; i++ {
    go func() { /* 작업 */ }()   // goroutine 초기 스택 ~2KB
}
```

고루틴 100 만 개도 Go 에서는 일상이다. 초기 스택이 약 2KB 이고 필요에 따라 커지므로, 100 만 개라도 수 GB 안쪽에서 돌아간다. 동시성 편의성에서 Go 는 BEAM 과 정직하게 대등하다.

### Java: 가상 스레드(Loom) — 100만 개가 가능해졌다

```java
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    for (int i = 0; i < 1_000_000; i++) {
        executor.submit(() -> {
            // 작업
        });
    }
}   // 플랫폼(OS) 스레드로는 불가능. 가상 스레드라서 가능하다.
```

Java 21 의 가상 스레드(Project Loom)는 이 그림을 바꿔 놓았다. 예전이라면 `newFixedThreadPool` 로 수백 개의 플랫폼 스레드에 100 만 작업을 욱여넣어야 했지만, 가상 스레드는 JVM 이 소수의 캐리어 스레드 위에 M:N 으로 얹는 경량 단위다. 그래서 위 코드처럼 "작업 하나당 스레드 하나"를 100 만 개 만들어도 감당된다. 블로킹 I/O 를 만나면 가상 스레드는 캐리어에서 내려오고 다른 가상 스레드가 그 자리를 쓴다 — BEAM 이 오래전부터 하던 일이다.

Java 로 상태를 가진 액터를 흉내 내려면 메일박스를 직접 만들어야 한다.

```java
class Counter {
    private final BlockingQueue<Runnable> mailbox = new LinkedBlockingQueue<>();
    private int count = 0;

    Counter() {
        Thread.ofVirtual().start(() -> {
            try {
                while (true) mailbox.take().run();
            } catch (InterruptedException e) { /* 종료 */ }
        });
    }
    void inc() { mailbox.add(() -> count++); }
}
```

`BlockingQueue` 가 메일박스, 가상 스레드가 그 큐를 비우는 루프다. 한 스레드만 `count` 를 만지므로 그 안에서는 락이 필요 없다. Erlang 의 프로세스+메일박스를 손으로 재구성한 셈이다. 동작은 하지만, 언어가 기본으로 주는 것을 라이브러리 없이 조립해야 한다는 점은 기억해 두자 — 이 "조립 대 내장"의 차이는 다음 글들에서 점점 더 벌어진다.

### C++: std::thread 100만 시도 — 실패한다

```cpp
// OS 스레드 100만 개 시도 — 리소스 고갈로 실패한다
std::vector<std::thread> threads;
for (int i = 0; i < 1'000'000; ++i) {
    threads.emplace_back([]{ /* 작업 */ });  // 수천 개에서 std::system_error
}
// 실무에선 스레드 풀 / C++20 코루틴 / executor 라이브러리가 필요하다.
```

`std::thread` 는 앞서 설명한 1:1 OS 스레드 그 자체다. 각 스레드가 MB 급 스택을 예약하니 수천 개 언저리에서 `std::system_error`("resource temporarily unavailable")를 던지며 무너진다. 100 만 개는 시도조차 무의미하다. C++ 에서 대규모 동시성을 하려면 스레드 풀에 작업을 태우거나, C++20 코루틴, 또는 Boost.Asio 같은 executor 라이브러리로 직접 M:N 을 구축해야 한다. 언어가 경량 동시성을 기본 제공하지 않는다는 점이 다른 셋과 갈리는 지점이다.

## 정량 비교표

| | 스폰 단위 | 단위당 비용 | 100만 개 |
|---|---|---|---|
| Erlang/BEAM | `spawn` 프로세스 | ~수 KB부터(상태·메일박스 별도) | 쉽다 |
| Go | goroutine | ~2KB 스택(성장) | 쉽다 |
| Java (Loom) | 가상 스레드 | 가벼움 | 가능(플랫폼 스레드는 불가) |
| C++ | `std::thread` | 1:1 OS 스레드(~MB) | 사실상 불가 → 풀/코루틴 필요 |

표를 한 줄로 요약하면 이렇다. 경량 실행 단위를 언어/런타임이 기본 제공하는 세 진영(Erlang, Go, Java Loom)은 100 만 동시성을 무리 없이 소화하고, 1:1 OS 스레드에 묶인 C++ 만 별도의 라이브러리 없이는 이 규모에 닿지 못한다.

## 정직한 핵심 메시지: 동시성만으로는 BEAM 을 정당화할 수 없다

여기서 이 글의 가장 중요한 주장을 분명히 하겠다. **순수한 동시성 ergonomics 만 놓고 보면, BEAM 은 더 이상 압도적 우위가 아니다.** Go 고루틴은 Erlang 프로세스와 구조적으로 쌍둥이라 할 만큼 닮았고, Java 가상 스레드는 Loom 이후 100 만 규모 동시성을 진짜로 해낸다. 이 두 언어를 쓰는 개발자에게 "동시성 때문에 Elixir 로 오라"고 말하는 것은 설득력이 약하다. 과장하지 않고 인정하는 편이 정직하다.

C++ 만 예외다. 1:1 OS 스레드 모델에 머물러 있어 경량 대규모 동시성에 대해서는 라이브러리로 별도 구축하지 않는 한 뒤처진다.

그렇다면 왜 여전히 BEAM 인가? 답은 이 글 밖에 있다. 동시성은 세 축 중 하나일 뿐이다. Go 와 Java 가 동시성에서 따라잡았어도, 프로세스 하나가 죽었을 때 나머지가 멀쩡한가(**격리성**), 그리고 죽은 것을 누가 자동으로 되살리는가(**감독성**)에서 진짜 격차가 벌어진다. 공유 메모리 위에서 도는 고루틴과 가상 스레드는 하나의 data race 로 이웃의 상태를 함께 망가뜨릴 수 있는데, 정작 실패가 번지는 방식은 언어마다 다르다. Go 는 recover 하지 않은 고루틴의 panic 이 프로그램 전체를 종료시키고, Java 는 잡히지 않은 예외가 보통 해당 가상 스레드 하나만 끝낸다. 어느 쪽이든 여러 실행 단위가 공유하는 가변 상태(shared mutable state)의 불변식은 언어가 아니라 애플리케이션이 직접 지켜야 하며, 죽은 것을 자동으로 되살리는 감독 트리도 언어 기본기가 아니다. 그 이야기가 바로 다음 글의 몫이다.
