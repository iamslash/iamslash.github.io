# 왜 Elixir 인가, 그리고 언제 아닌가

이 시리즈의 다섯 번째 글이다. 앞선 네 편에서 우리는 Erlang/BEAM 이 동시성·격리성·감독성이라는 세 축에서 왜 특별한지, 그리고 Go/Java(Loom)/C++/Akka/Orleans 같은 현대적 대안들과 견주어도 그 조합이 여전히 유효한 이유를 살펴봤다. 스코어카드는 이제 거의 다 채워졌다 — 동시성은 정직히 말해 막상막하지만, 격리성과 감독성에서 BEAM 이 앞선다는 것. 그런데 지금까지 코드는 전부 순수 Erlang 이었다. 실제로 이 능력을 손에 쥐려는 팀이 오늘 무엇을 선택해야 하냐고 물으면, 답은 거의 항상 Erlang 자체가 아니라 Elixir 다. 이번 글은 왜 그런지, 그리고 그 선택이 언제는 틀린 답이 되는지를 정직하게 다룬다. 이 글의 정직함이 다음 글부터 시작될 POC(멀티채널 LLM 챗봇을 실제로 Elixir 로 만들어 보는 4부작)를 믿을 수 있게 만든다.

## BEAM 위의 현대적 얼굴

Elixir 는 새로운 가상 머신이 아니다. Erlang 을 만든 것과 똑같은 BEAM 위에서 돌아가는 또 하나의 언어일 뿐이다. 그래서 지금까지 살펴본 능력 — 가벼운 프로세스(빈 BEAM 프로세스는 보통 수 KB 정도에서 시작하고, 상태와 mailbox 가 쌓이면 더 커진다. OS 스레드보다는 훨씬 가볍지만 공짜는 아니다), share-nothing 격리, OTP 감독 트리 — 을 하나도 잃지 않는다. `gen_server` 는 `GenServer` 가 되고 `supervisor` 는 `Supervisor` 가 될 뿐, 런타임 수준의 보장은 정확히 동일하다. 실제로 Elixir 코드는 컴파일되면 Erlang 코드와 나란히 같은 BEAM 바이트코드로 내려가고, 필요하면 Erlang 라이브러리를 그대로 호출할 수 있다(반대도 마찬가지다).

Elixir 가 더하는 것은 순전히 개발자 경험이다. 문법은 Erlang 의 Prolog 스러운 구두점(마침표, 세미콜론, 대문자 변수) 대신 Ruby 에 가까운 표현력을 쓴다. 파이프 연산자는 그 상징이다.

```elixir
"hello world"
|> String.split()
|> Enum.map(&String.upcase/1)
|> Enum.join(" ")
# => "HELLO WORLD"
```

`|>` 는 왼쪽 값을 오른쪽 함수의 첫 인자로 넘긴다. Erlang 이었다면 안쪽 함수 호출부터 바깥쪽으로 거슬러 읽어야 했을 코드가, 데이터가 흐르는 순서 그대로 위에서 아래로 읽힌다. 사소해 보이지만 파이프라인 형태의 코드 — 메시지를 받아 파싱하고 검증하고 라우팅하는, 정확히 이 시리즈가 다루는 종류의 코드 — 를 매일 쓰는 입장에서는 누적된 가독성 차이가 크다.

3편에서 본 카운터 `gen_server` 를 Elixir 로 옮기면 이렇게 된다.

```elixir
defmodule Counter do
  use GenServer

  # --- 클라이언트 API ---
  def start_link(_), do: GenServer.start_link(__MODULE__, 0)
  def inc(pid), do: GenServer.cast(pid, :inc)
  def value(pid), do: GenServer.call(pid, :get)

  # --- 서버 콜백 ---
  @impl true
  def init(count), do: {:ok, count}

  @impl true
  def handle_cast(:inc, count), do: {:noreply, count + 1}

  @impl true
  def handle_call(:get, _from, count), do: {:reply, count, count}
end
```

`handle_cast`/`handle_call` 콜백 구조는 Erlang 의 `gen_server` 와 한 줄도 다르지 않은 개념이다. 달라진 건 문법뿐이고, 밑에 깔린 프로세스·메시지큐·감독 모델은 전혀 달라지지 않았다.

문법 위에는 두 겹이 더 있다.

첫째는 매크로와 메타프로그래밍이다. 매크로는 한마디로 "컴파일될 코드를 만들어 내는 코드"다. `defmodule`, `def`, `use` 는 그 자체가 Elixir 매크로다(반면 `@impl` 은 매크로가 아니라 컴파일러가 해석하는 컴파일 타임 모듈 속성(module attribute)이다 — "이 함수는 지정한 behaviour 의 콜백을 구현한 것"이라고 컴파일러에게 알려 주는 표식이라, 이름을 틀리면 경고를 받는다). 이 매크로 시스템 덕분에 라이브러리 저자는 DSL(domain-specific language, 특정 문제를 그 문제에 맞는 읽기 쉬운 문법으로 표현하게 해주는 작은 언어)을 언어에 자연스럽게 얹을 수 있다. Ecto 의 쿼리 문법이나 Phoenix 의 라우터 정의가 대표적인 예다.

둘째는 생태계와 툴링이다. `mix` 는 빌드·테스트·의존성 관리를 하나의 CLI 로 통합하고, Hex 는 패키지 저장소 역할을 하며, Phoenix 는 웹 프레임워크다. Phoenix 의 LiveView 는 개발자가 커스텀 자바스크립트를 거의 작성하지 않고 서버 코드 중심으로 실시간 UI 를 만들게 해준다(자바스크립트가 아예 없는 건 아니다 — 내부적으로는 브라우저에서 도는 JS 클라이언트와 WebSocket 이 서버와 화면 사이를 잇는다). 최근에는 Nx(텐서 연산)와 Bumblebee(허깅페이스 모델 추론)가 붙으면서 수치 계산과 ML 까지 BEAM 생태계 안에서 돌릴 수 있게 됐다 — 이 시리즈의 POC 에서는 LLM 호출을 외부 API 로 뺄 것이므로 직접 쓰진 않지만, Elixir 진영이 그 방향으로도 투자하고 있다는 신호로 봐 둘 만하다. 정리하면: Erlang 이 증명한 런타임 능력에, Elixir 는 현대적인 문법과 완성된 개발자 도구 체인을 얹은 것이다.

## 메신저/실시간 채팅에 유독 잘 맞는 이유

이 시리즈가 다루는 도메인 — 여러 채널로 들어오는 메시지를 받아 대화 상태를 유지하며 응답하는 시스템 — 은 우연히 잘 맞는 게 아니라 구조적으로 잘 맞는다.

첫째, 대화 하나를 프로세스 하나에 매핑할 수 있다. 사용자마다, 혹은 대화 스레드마다 독립된 BEAM 프로세스를 하나씩 띄우면 그 프로세스가 자연스럽게 "이 대화의 상태"를 들고 있는 단위가 된다. 2편에서 본 100만 프로세스 스폰이 여기서 실전 용도를 얻는다: 동시에 열려 있는 대화가 수만~수십만 개여도 프로세스당 비용이 낮으니 문제가 되지 않는다.

둘째, 이 워크로드는 soft-realtime 이다. 채팅 응답은 밀리초 단위로 완벽히 결정적일 필요는 없지만(hard-realtime 이 아니다), 사용자가 체감할 정도로 지연되면 안 된다(그래서 "soft"). BEAM 스케줄러는 정확히 이런 프로파일을 위해 설계됐다 — 선점형 스케줄링으로 하나의 무거운 프로세스가 다른 프로세스들의 응답성을 떨어뜨리지 않도록 리덕션 카운트를 기준으로 실행을 잘라낸다.

셋째, 이 워크로드는 IO-bound 다. 채널 어댑터가 웹훅을 받고, LLM API 호출을 기다리고, DB 에 쓰는 것 — 전부 네트워크 대기다. BEAM 의 경량 프로세스와 논블로킹 IO 는 정확히 "수만 개가 동시에 뭔가를 기다리는" 상황을 위해 최적화되어 있다.

이 조합이 실제로 얼마나 극단적으로 확장되는지 자주 인용되는 예가 2015 년 Phoenix Channels 벤치마크다. Phoenix 팀은 40 코어·128GB 짜리 장비 한 대에서 200 만 개의 동시 WebSocket 연결을 유지하는 것을 측정해 공개했다 — 다만 이 연결들은 대부분 유휴(idle) 상태, 즉 붙어만 있고 활발히 메시지를 주고받지는 않는 연결이었다. 그래서 이 숫자가 실제로 보여주는 건 "연결 하나를 붙들고 있는 비용 자체가 매우 낮다"는 점이지, 메시지 처리량·TLS 종단·브로드캐스트 팬아웃·고가용성까지 노드 하나로 감당된다는 용량 계획(capacity plan)이 아니다. 실제 프로덕션에서 필요한 노드 수는 메시지 페이로드와 브로드캐스트 팬아웃 방식에 따라 완전히 달라진다. 그래도 이 숫자는 "커넥션을 오래 유지하며 상태를 들고 있는" 워크로드에 BEAM 이 구조적으로 얼마나 유리한지를 보여주는 증거로는 충분하다.

## 정직한 별표: Elixir 가 약한 지점들

여기까지만 보면 만능처럼 들릴 텐데, 그렇지 않다. 이 시리즈의 규칙대로 과장은 하지 않는다.

**CPU-bound 연산에 약하다.** BEAM 은 프로세스 스케줄링과 메시지 전달에 최적화된 런타임이지, 수치 연산 처리량에 최적화된 런타임이 아니다. 행렬 곱셈, 이미지 인코딩, 압축, 암호화 같은 순수 연산 작업에서 Elixir/Erlang 네이티브 코드는 C++/Rust/최적화된 Go 코드보다 명백히 느리다. 이건 Elixir 커뮤니티도 숨기지 않는 사실이다. 실제로 Discord — Elixir 로 유명한 대규모 프로덕션 사례 — 는 대규모 길드(서버)의 멤버 목록을 정렬하고 갱신하는 뜨거운(hot) 경로를, Rust 로 만든 `SortedSet` NIF(Native Implemented Function)로 내려서 BEAM 밖에서 돌린다. 즉 "메시지를 라우팅하고 상태를 지키는" 일은 Elixir 가, "대량 데이터를 정렬하는 무거운 연산"은 다른 언어가 맡는 하이브리드 구조를 실전에서 채택했다.

**생태계 폭이 좁다.** Go, Java, Node 진영과 비교하면 라이브러리 개수 자체가 다르다. 특정 클라우드 벤더의 최신 SDK, 특정 결제/CRM/분석 서비스의 공식 클라이언트 같은 것들이 Elixir 용으로는 아예 없거나 커뮤니티가 유지하는 비공식 버전만 있는 경우가 흔하다. HTTP 로 두들기면 되는 REST API 라면 큰 문제가 아니지만, 벤더가 SDK 사용을 강하게 권장하거나 SDK 안에 복잡한 재시도/서명 로직이 들어 있는 경우엔 직접 포팅해야 하는 부담이 생긴다.

**채용과 팀 친숙도.** 이건 기술적 약점이 아니라 조직적 현실이지만, 실제 의사결정에서는 종종 가장 크게 작용한다. Elixir 를 이미 아는 엔지니어의 인력 풀은 Go/Java/Node/Python 에 비하면 훨씬 작다. 팀을 꾸리거나 새 인원을 온보딩할 때, "이 언어를 아는 사람을 뽑는다"보다는 "우리가 가르쳐야 한다"는 전제를 깔아야 하는 경우가 많다.

**OTP 패러다임 학습 곡선.** 문법은 Ruby 스러워서 며칠이면 읽을 수 있지만, GenServer/Supervisor/프로세스 간 메시지 전달로 상태를 설계하는 사고방식은 객체지향이나 절차형 배경의 개발자에게 익숙하지 않다. "이 상태를 프로세스에 둘까, DB 에 둘까", "이 실패를 어느 감독자가 잡아야 할까" 같은 질문에 익숙해지는 데는 시간이 걸린다.

**순수 무상태 요청/응답이라면 우위가 줄어든다.** 만약 시스템이 단순히 요청을 받아 DB 를 조회하고 JSON 을 돌려주는 무상태 REST API 라면 — 프로세스당 장수명 상태를 지킬 이유도, 수만 개의 동시 연결을 붙들고 있을 이유도 없다면 — BEAM 의 핵심 강점(경량 프로세스, 장수명 상태 격리)은 활용될 기회 자체가 없다. 이런 경우엔 Elixir 를 골라도 나쁘지 않지만, 다른 언어 대비 결정적 우위가 사라진다.

## 경쟁자들에게도 공정하게

이 별표들은 다른 선택지들이 정당한 이유이기도 하다.

**Go**: 채용이 쉽고(인력 풀이 크다), 운영이 단순하며(단일 정적 바이너리, 낮은 메모리 풋프린트), raw 성능에서 유리하다. goroutine 이 BEAM 프로세스만큼 격리되지도 감독되지도 않는다는 건 3·4편에서 정직하게 짚었지만, 팀이 이미 Go 에 익숙하고 시스템이 극단적인 장수명 상태 관리를 요구하지 않는다면 Go 는 충분히, 어쩌면 더 나은 답이다.

**JVM + Loom + Akka**: 이미 JVM 조직이라면(자바/코틀린 팀, 기존 스프링 인프라, 기존 운영 도구) 새 런타임을 들이는 비용 자체가 크다. Loom 의 가상 스레드가 동시성 격차를 좁혔고, Akka 를 얹으면 감독 트리에 준하는 것도 만들 수 있다. "새 언어/런타임을 배우는 비용" 대 "얻는 이득"을 저울질했을 때 기존 JVM 조직에게는 전자가 더 클 수 있다.

**Rust**: CPU-bound 핫패스에서는 Elixir 보다 명백히 우월하고, 안전성 보장(소유권 모델)도 강력하다. 다만 프로세스 감독·경량 동시성·장수명 상태 관리 같은 이 시리즈의 주제에서는 Rust 가 그 자체로 답이 되기보다는, Discord 사례처럼 Elixir/BEAM 옆에서 뜨거운 경로를 보완하는 역할로 가장 잘 맞는다.

즉 "정답"은 도메인과 팀 상황에 달렸다. 지금까지 다룬 스코어카드는 절대적 우열이 아니라, 어떤 상황에서 어떤 축이 결정적으로 작용하는지를 보여주는 도구였다.

## 그런데 LLM 챗봇이라는 케이스에선 별표가 지워진다

여기서 이 시리즈의 다음 이야기로 넘어가는 이유가 나온다. 우리가 만들 시스템은 멀티채널(iMessage/Slack/Discord 등)로 들어오는 메시지를 받아 LLM 에게 물어보고 응답을 돌려주는 챗봇 게이트웨이다. 이 도메인에 방금 나열한 약점들을 하나씩 대입해 보자.

가장 무거운 CPU-bound 연산 — LLM 추론 그 자체 — 은 애초에 Elixir 프로세스 안에서 돌지 않는다. OpenAI 나 Anthropic 같은 외부 API 를 HTTP 로 호출해서 그쪽 GPU 클러스터에서 처리하고, 결과를 스트리밍으로 받아올 뿐이다. 즉 이 시스템에서 가장 연산 집약적인 작업은 처음부터 BEAM 바깥에 있어서, 워크로드가 대체로 IO-bound 로 기운다. 다만 "CPU 를 전혀 안 쓴다"는 뜻은 아니다. JSON/SSE 응답 파싱, 긴 대화 히스토리를 매 요청마다 조립하기, TLS 암복호화, 압축, 로깅, 여러 클라이언트로의 팬아웃 — 이런 게이트웨이 자체의 일은 여전히 CPU 를 쓴다. 그러니 "CPU 약점이 발동될 일이 아예 없다"고 단정하기보다는, 게이트웨이의 CPU 병목도 실제로 측정해 봐야 한다는 게 정직한 표현이다. 다만 이 부하는 LLM 추론 자체에 비하면 훨씬 가벼운 편이다.

그럼 Elixir 프로세스가 실제로 하는 일은 뭘까: 채널마다 웹훅/소켓 연결을 오래 붙들고 있고(고동시 장수명 연결), 대화마다 히스토리와 상태를 들고 있으며(상태 있는 대화), 그 상태를 쥔 채로 외부 API 응답을 기다린다(외부 API 대기, 즉 IO-bound). 이 세 가지 — 고동시 장수명 연결, 상태 있는 프로세스, IO 대기 — 는 정확히 앞서 말한 "BEAM 이 구조적으로 잘 맞는 세 가지 이유" 그 자체다. 다시 말해 이 특정 도메인은 Elixir 의 가장 큰 약점(CPU-bound)은 문제 밖으로 밀어내고, 가장 큰 강점(경량 프로세스·격리·soft-realtime IO)만 정면으로 사용하는, 교과서적으로 유리한 케이스다.

물론 생태계 폭과 채용이라는 별표는 여전히 남는다. 이건 이 시리즈가 해결해 줄 수 있는 문제가 아니라 각 팀이 스스로 판단할 몫이다. 다만 적어도 기술적 적합성 측면에서는, 이 도메인이 Elixir 의 강점만 쓰고 약점은 피해 가는 드문 경우라는 것은 분명히 말할 수 있다.

## 결론과 다음 이야기

지금까지 네 편에 걸쳐 본 것을 한 문장으로 압축하면: 동시성·격리성·감독성이라는 세 특성을 하나의 런타임 위에서 통합적으로 제공하는 게 Erlang/BEAM 이고, Elixir 는 그 런타임에 현대적인 문법과 완성된 툴링(Mix, Hex, Phoenix, LiveView)을 얹은 얼굴이다. 그래서 이 문제 — 여러 채널로 들어오는 메시지를 받아 대화 상태를 유지하며 외부 LLM 을 호출해 응답하는 시스템 — 에는 Elixir 가 탁월한 선택이다. 단, CPU-bound 연산과 팀/생태계라는 별표를 정직하게 달고서.

다음 글부터는 막3 이다. 지금까지는 "왜"라는 질문에 답했다면, 이제부터는 "어떻게"다. Elixir 와 PostgreSQL 만으로 멀티채널 LLM 챗봇의 프로토타입을 실제로 설계하고 짠다 — 대화당 프로세스, 채널 어댑터, GenServer 로 관리되는 대화 코어, LLM 스트리밍 클라이언트까지 코드로 확인한다.
