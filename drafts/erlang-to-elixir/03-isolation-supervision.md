# 격리성과 감독성: Let It Crash 와 OTP 감독 트리

이 시리즈의 세 번째 글이다. 앞 글에서는 **동시성**을 다뤘다. 결론은 다소 김빠지는 것이었다. Erlang 의 경량 프로세스는 훌륭하지만, Go 의 goroutine 과 Java 21 의 가상 스레드(Loom)도 수백만 개를 거뜬히 띄운다. "수백만 개의 작은 실행 단위"라는 관점만 보면 셋은 막상막하였다. 정직하게 인정하자. 동시성 하나만 놓고 BEAM 을 선택할 이유는 생각보다 약하다.

그런데 이 글에서 다룰 두 축, **격리성(isolation)** 과 **감독성(supervision)** 에서 그림이 완전히 달라진다. 진짜 차이가 여기서 벌어진다. 그리고 이 둘은 하나로 묶어 이야기하는 게 자연스럽다. Erlang 커뮤니티의 유명한 슬로건 "let it crash"(그냥 죽게 놔둬라)는 격리가 있어야 안전하고, 감독이 있어야 복구된다. 격리 없는 크래시는 재앙이고, 감독 없는 크래시는 그냥 다운이다. 둘이 맞물려야 비로소 "실패를 정상 흐름으로 취급하는" 설계가 성립한다.

## 격리성: share-nothing 이라는 토대

2편에서 각 BEAM 프로세스가 자기만의 힙과 GC 를 가진다고 했다. 이 사실을 다시 꺼내는 이유는, 그것이 단순한 성능 특성이 아니라 **격리성의 물리적 토대**이기 때문이다.

BEAM 프로세스는 서로 메모리를 공유하지 않는다(share-nothing). 프로세스 A 가 프로세스 B 에게 데이터를 보내면, 그 데이터는 **복사되어** B 의 힙으로 전달된다. Erlang 의 모든 데이터는 불변(immutable)이므로 "복사본을 보낸다"는 개념이 자연스럽고, 보낸 쪽과 받은 쪽이 같은 메모리를 가리키다 서로를 오염시킬 일이 없다.

이 구조의 결정적 결과가 있다. **한 프로세스가 크래시해도 다른 프로세스의 힙을 오염시킬 수 없다.** A 가 잘못된 상태로 뭉개져 죽어도, B 는 A 의 메모리를 단 한 바이트도 공유하지 않았으므로 A 의 손상된 상태가 B 로 샐 수 없다. A 의 힙은 그대로 회수되고, B 는 자기 일을 계속한다. 프로세스별 힙과 GC 는 여기서 방화벽처럼 작동한다.

다만 이 "격리"를 과장하지는 말자. 방화벽이 막아 주는 것은 어디까지나 **메모리 상태의 오염**이다. 프로세스들은 여전히 같은 노드의 CPU·메모리를 나눠 쓰고, ETS 테이블·port·NIF 리소스처럼 프로세스 바깥에 사는 자원은 공유되며, 곧 볼 link 는 오히려 실패를 옆 프로세스로 **의도적으로 전파**한다. 그러니 BEAM 프로세스는 **보통의 애플리케이션 실패 경계**이지, OS 프로세스 같은 보안 경계도 아니고 노드 전체의 장애 경계도 아니다. 그 범위 안에서 하나의 프로세스가 하나의 실패 격리 단위(fault isolation unit)로 작동한다.

공유 메모리 언어에서는 스레드 하나가 저절로 이런 실패 격리 경계가 되지는 않는다. 스레드들이 같은 주소 공간을 공유하기 때문에, 한 스레드가 자료구조를 반쯤 망가뜨린 채 죽으면 그 망가진 상태가 다른 스레드에게 그대로 노출된다. 같은 경계를 얻으려면 별도의 OS 프로세스로 분리하거나, 액터 프레임워크를 얹거나, 소유권(ownership)·불변성(immutability) 규칙을 스스로 지켜 설계해야 한다. BEAM 은 그 경계를 런타임이 기본으로 그어 준다는 점이 다르다.

## "Let it crash" 철학

공유 메모리 세계에서 우리는 방어적으로 코딩하도록 훈련받았다. 모든 함수 경계에서 입력을 검증하고, 모든 위험한 호출을 try/catch 로 감싸고, 예외를 잡아 어떻게든 프로그램을 계속 굴러가게 만든다. 왜? 스레드 하나가 죽으면 그게 무슨 상태를 남길지 알 수 없고, 최악의 경우 프로세스 전체가 내려가기 때문이다. 실패는 반드시 국소적으로 봉합해야 하는 재앙이다.

Erlang 은 정반대로 간다. 예상 못 한 상황을 만나면 **그냥 죽게 놔둔다.** 방어 코드로 억지로 회복시키려 하지 않는다. 대신 프로세스를 깔끔하게 죽이고, 감독자(supervisor)가 그 프로세스를 **알려진 초기 상태에서 새로 시작**한다(이때 프로세스가 들고 있던 상태는 잃는다 — 왜 그게 대개 문제가 아닌지, 그리고 언제는 문제가 되는지는 뒤의 감독성 절에서 다룬다).

왜 이게 더 견고할까? 세 가지 이유가 있다.

첫째, 실패에는 두 종류가 있다. **일시적(transient) 실패** — 순간적인 네트워크 단절, 잠깐의 외부 서비스 오류, 드문 타이밍 경합 같은 것 — 은 프로세스를 깨끗한 상태로 재시작하면 상당수가 그냥 사라진다. "껐다 켜기"가 실제로 통하는 경우다. 반면 **코드 버그, 잘못된 설정, 항상 같은 결과를 내는 입력**은 재시작해도 똑같이 반복된다. 이런 반복은 뒤에서 볼 재시작 강도(restart intensity)가 끊어서, 재시작으로 낫지 않는 실패를 상위 감독자로 올려보낸다. 즉 재시작은 일시적 실패를 지우는 수단이지, 버그를 고치는 수단이 아니다. 흔히 "대부분의 버그는 일시적이다"라고 뭉뚱그리지만, 정확히는 버그가 아니라 일부 *실패*가 일시적인 것이다.

둘째, 방어 코드는 **모든** 오류 경로를 예측해야 한다. 하지만 진짜 위험한 버그는 우리가 예측하지 못한 곳에서 나온다. 예측 못 한 상태를 억지로 이어가는 것보다, 손상된 상태를 통째로 버리고 알려진 좋은 상태에서 다시 시작하는 편이 훨씬 안전하다. 반쯤 망가진 상태로 계속 굴러가는 프로그램이 조용히 잘못된 결과를 내는 것보다, 죽고 재시작하는 편이 낫다.

셋째, 이 철학은 **행복 경로(happy path)에 집중**하게 해준다. 비즈니스 로직을 방어 코드로 뒤덮는 대신 정상 흐름을 깨끗하게 쓰고, 실패 처리는 감독 구조에 위임한다. 코드가 짧아지고 읽기 쉬워진다.

여기서 가장 흔한 오해를 못 박아 두자. "let it crash"는 **실패 처리를 생략하라는 뜻이 아니다.** 무엇을 죽이고 무엇을 죽이지 않을지가 핵심이다.

- **예상 가능한 실패는 정상 흐름으로 처리한다.** 사용자 입력 검증(validation), 타임아웃, "값이 없음" 같은 케이스는 크래시가 아니라 코드가 명시적으로 다뤄야 할 정상 분기다.
- **부수 효과(side effect)는 방어한다.** DB 쓰기나 외부 API 호출은 트랜잭션이나 멱등성(idempotency — 같은 요청을 여러 번 보내도 결과가 한 번 보낸 것과 같아지도록 설계하는 것)으로 보호해, 재시작이 중복 결제 같은 사고를 내지 않게 한다.
- **오직** 예측하지 못한 내부 오류로 상태를 더는 믿을 수 없을 때만 프로세스를 죽이고, supervisor 가 깨끗한 상태에서 다시 시작하도록 맡긴다.

즉 죽이는 대상은 "모든 오류"가 아니라 "손상됐을지 모를 상태를 들고 있는 프로세스"다. 예상되는 오류는 정상적으로 처리하고, 예상 못 한 오류 앞에서만 영웅적으로 버티지 말고 죽으라는 것이다.

## 크래시는 어떻게 전파되는가: 4개 언어 비교

"let it crash"가 왜 다른 언어에서 위험한지는, 각 언어에서 실패가 어떻게 번지는지를 보면 분명해진다.

**C++ — 잘못된 포인터 하나면 끝난다.** 널 포인터 역참조나 해제 후 사용(use-after-free) 하나면 세그폴트가 나고, 프로세스 **전체**가 즉사한다. 격리 단위가 없다. 스레드 하나의 실수가 프로세스 안의 모든 스레드를 함께 데려간다.

```cpp
int* p = nullptr;
*p = 42;   // 세그폴트 → 프로세스 전체 사망. 다른 스레드도 함께 죽는다.
```

**Go — 복구 안 한 panic 은 프로그램 전체를 내린다.** goroutine 은 가볍지만 격리되어 있지 않다. 한 goroutine 에서 `recover()` 없이 panic 이 나면 런타임이 프로세스 **전체**를 종료시킨다. 게다가 goroutine 들은 메모리를 공유하므로, 죽기 직전에 공유 자료구조를 망가뜨렸을 수 있고 data race 위험이 상존한다.

```go
go func() {
    panic("boom")   // recover() 가 없으면 프로그램 전체가 죽는다
}()
```

`recover()` 로 잡을 수는 있다. 하지만 그건 **모든** goroutine 마다 방어 코드를 손으로 심어야 한다는 뜻이고, 회복한다 해도 공유 메모리가 어떤 상태로 남았는지는 여전히 보장할 수 없다.

**Java — 예외는 스레드에 국한되지만 공유 상태는 그대로다.** Java 는 C++/Go 보다 낫다. 한 스레드에서 잡히지 않은 예외는 보통 그 스레드만 죽이고 JVM 은 계속 돈다. 격리가 "스레드 단위"로는 어느 정도 있는 셈이다. 하지만 그 스레드가 만지던 **shared mutable state** 는 반쯤 갱신된 채로 남는다. 다른 스레드가 그 오염된 객체를 그대로 보게 된다. 그리고 언어 차원의 감독 트리는 없다 — Akka 같은 별도 액터 프레임워크를 얹어야 비슷한 걸 흉내 낼 수 있다.

```java
Thread.ofVirtual().start(() -> {
    throw new RuntimeException("boom");   // 이 스레드만 죽는다
});
// JVM 은 계속 살지만, 이 스레드가 손댄 공유 객체는 오염된 채 남는다
```

**Erlang — 격리된 실패를 감지하고, 나머지는 무사하다.** 다른 프로세스들은 메모리를 공유하지 않으므로, 한 프로세스가 죽어도 나머지는 아무 영향 없이 자기 일을 계속한다. 죽음을 **어떻게 알리느냐**에는 자주 뭉뚱그려지지만 동작이 전혀 다른 두 메커니즘이 있다.

- **link(링크) — 양방향 실패 전파.** 두 프로세스를 링크해 두면, 한쪽이 비정상 종료할 때 다른 쪽으로 exit 시그널이 간다. 받는 쪽이 `trap_exit` 플래그를 켜 두지 않았다면 그 시그널을 받고 **함께 죽는다**(이게 기본 동작이다). `trap_exit` 를 켜 둔 경우에만 시그널이 죽음으로 이어지지 않고 `{'EXIT', Pid, Reason}` **메시지**로 우편함에 들어와, 받는 쪽이 직접 처리할 수 있다.
- **monitor(모니터) — 단방향 관찰.** 관찰자가 대상을 모니터하면, 대상이 죽을 때 관찰자에게 `{'DOWN', Ref, process, Pid, Reason}` **메시지**만 간다. 시그널이 아니라 메시지이므로 관찰자는 결코 함께 죽지 않고, 죽음을 통보만 받는다.

그러니 "실패가 오염이 아니라 하나의 메시지가 된다"는 것은 monitor(또는 `trap_exit` 를 켠 link)에 해당하는 이야기다. 감시하던 쪽이 그 메시지를 받아 "재시작할까, 무시할까"를 결정한다.

```erlang
%% monitor: 대상이 죽으면 관찰자에게 '메시지'만 온다(관찰자는 함께 죽지 않는다).
{Pid, Ref} = spawn_monitor(fun() -> error(boom) end),
receive
    {'DOWN', Ref, process, Pid, Reason} ->
        %% Reason = boom. 죽음이 오염이 아니라 메시지로 도착했다.
        %% 다른 프로세스의 힙은 공유되지 않으므로 전혀 오염되지 않는다.
        handle_down(Reason)
end.

%% link 로 하고 싶다면, 받는 쪽에서 먼저 trap_exit 를 켜야
%% 죽음이 시그널이 아니라 {'EXIT', Pid, Reason} 메시지로 온다:
%%   process_flag(trap_exit, true),
%%   spawn_link(fun() -> error(boom) end).
%% trap_exit 를 켜지 않으면 link 는 이 프로세스까지 함께 죽인다.
```

이 링크/모니터 메커니즘이 바로 감독 트리를 떠받치는 하부 구조다. 죽음이 메모리 오염이 아니라 관측 가능한 이벤트라는 점이 핵심이다.

## OTP 감독성: gen_server 와 supervisor

격리가 "안전하게 죽는" 능력이라면, 감독은 "자동으로 복구하는" 능력이다. OTP(Open Telecom Platform)는 이 복구를 표준화한 프레임워크다.

먼저 상태를 가진 서버를 `gen_server` 행동양식(behaviour)으로 작성한다. 2편의 카운터 예제를 OTP 스타일로 옮긴 것이다.

```erlang
-module(counter_server).
-behaviour(gen_server).
-export([start_link/0, inc/1, value/1]).
-export([init/1, handle_call/3, handle_cast/2]).

start_link() -> gen_server:start_link(?MODULE, 0, []).

inc(Pid)   -> gen_server:cast(Pid, inc).
value(Pid) -> gen_server:call(Pid, get).

init(Count) -> {ok, Count}.
handle_cast(inc, Count)       -> {noreply, Count + 1}.
handle_call(get, _From, Count) -> {reply, Count, Count}.
```

`gen_server` 는 메시지 루프, 상태 관리, 동기(`call`)/비동기(`cast`) 호출 구분 같은 반복적인 뼈대를 다 제공한다. 개발자는 콜백만 채운다. 콜백이 돌려주는 튜플의 뜻만 알면 위 코드가 다 읽힌다. `{noreply, Count + 1}` 은 "caller 에게 답을 돌려주지 않고, 두 번째 값(`Count + 1`)을 다음 상태로 삼아라"라는 뜻이다(비동기 `cast` 는 응답이 필요 없으므로 noreply). `{reply, Count, Count}` 는 "두 번째 값(`Count`)을 caller 에게 반환하고, 세 번째 값(`Count`)을 다음 상태로 삼아라"라는 뜻이다(동기 `call` 은 응답이 필요하므로 reply). 여기엔 방어 코드가 한 줄도 없다는 점에 주목하자. 실패 처리는 다음 계층인 감독자의 몫이다.

이제 이 서버를 감독하는 `supervisor` 를 얹는다.

```erlang
-module(counter_sup).
-behaviour(supervisor).
-export([start_link/0, init/1]).

start_link() ->
    supervisor:start_link({local, ?MODULE}, ?MODULE, []).

init([]) ->
    Flags = #{strategy => one_for_one, intensity => 10, period => 60},
    Child = #{id => counter_server,
              start => {counter_server, start_link, []},
              restart => permanent},
    {ok, {Flags, [Child]}}.
```

이게 전부다. 이 감독자는 `counter_server` 를 시작하고, 그것이 죽으면 **자동으로 재시작**한다. 개발자가 재시작 로직을 짤 필요가 없다.

여기서 정확히 짚어야 할 게 있다. Supervisor 가 되살리는 것은 프로세스의 **실행 가능한 상태**(다시 메시지를 받을 수 있는, 살아 있는 프로세스)이지, 그 프로세스가 들고 있던 **비즈니스 상태(business state)**가 아니다. 위 예제의 카운터는 재시작되면 이전 count 를 **잃고 다시 0 에서 시작**한다. 정말로 그 값이 필요하다면, 재시작된 프로세스가 DB 나 이벤트 로그에서 상태를 **다시 읽어 복원**하도록 앱이 직접 설계해야 한다. 또 기본 supervisor 에는 지수 백오프(exponential backoff — 재시도 간격을 실패할수록 점점 벌리는 것)가 없다. OTP 가 기본으로 주는 것은 재시작 전략(strategy)과 강도(intensity)까지고, 상태 복원·멱등성·백오프는 앱이 그 위에 얹어야 할 몫이다.

`init/1` 이 반환하는 설정을 뜯어보자.

**재시작 전략(strategy)** — 자식이 여럿일 때 하나가 죽으면 어떻게 대응할지 정한다.
- `one_for_one`: 죽은 자식만 재시작한다. 자식들이 서로 독립적일 때. 위 예제가 이 경우다.
- `one_for_all`: 자식 하나가 죽으면 **모든** 자식을 함께 재시작한다. 자식들이 강하게 얽혀 있어 하나가 죽으면 나머지 상태도 못 믿을 때.
- `rest_for_one`: 죽은 자식과, 그 뒤에 시작된 자식들만 재시작한다. 자식들 사이에 시작 순서 의존성이 있을 때.

**재시작 강도(intensity/period)** — `intensity => 10, period => 60` 은 "60초 안에 재시작이 10번을 넘으면 감독자 자신도 포기하고 죽는다"는 뜻이다. 이게 왜 중요할까? 무한 재시작 루프를 막기 위해서다. 어떤 프로세스가 구조적 이유로 계속 죽는다면(예: 설정 파일이 없다), 재시작을 반복해봐야 소용없다. 그럴 때 감독자는 스스로 죽어서 **자신의 상위 감독자**에게 문제를 위임한다. 실패가 트리를 타고 위로 전파되면서, 더 넓은 범위의 복구(예: 하위 시스템 전체 재초기화)를 촉발한다. 이것이 감독 **트리**의 진짜 힘이다. 실패가 적절한 계층에서 처리되도록 구조가 잡혀 있다.

## "등가 코드의 부재"라는 논증

여기서 가장 중요한 대목이다. 위 감독자 spec 을 다시 보라. 실질적으로 **5줄짜리 선언**이다. 재시작 전략, 강도, 자식 명세만 적으면 나머지는 런타임이 알아서 한다.

이제 Go/Java/C++ 에서 같은 것을 만들려면 무엇이 필요한지 상상해보자.

- 자식 프로세스/스레드를 감시하는 감독 루프
- 죽음을 감지하는 메커니즘(exit code, future 예외, 신호 핸들러…)
- 재시작 로직과 새 상태 초기화
- 폭주 재시작을 막는 **백오프**와 카운터(60초 창에 몇 번? 넘으면?)
- 상태 복구: 죽은 워커가 들고 있던 상태를 어떻게 되살릴 것인가
- 이 모든 걸 여러 스레드가 동시에 죽고 재시작하는 상황에서 **경합 없이** 처리하기

이걸 제대로 짜면 최소 수십 줄, 현실적으로는 50줄을 훌쩍 넘는다. 그리고 결정적으로, **그마저도 엣지케이스가 샌다.** 재시작 도중 또 죽으면? 백오프 상태는 스레드 세이프한가? 감독자 자신이 죽으면? 공유 메모리로 상태를 복구하다 절반만 복구되면? 이런 질문 하나하나가 새로운 버그의 씨앗이다.

핵심은 이것이다. 이 목록에서 **감시 루프, 죽음 감지, 재시작, 폭주 재시작을 끊는 크래시레이트 제한(intensity/period), 그리고 이 모두를 경합 없이 처리하기**는 Erlang 에선 고민한 흔적조차 없다 — **런타임이 이 뼈대를 일급으로 제공하기 때문**이다. 다만 정직하게 덧붙이자. 목록의 나머지 두 가지 — 지수 백오프와 비즈니스 상태 복구 — 는 Erlang 에서도 공짜가 아니라, 앞 절에서 봤듯 앱이 직접 설계할 몫이다. 여기서 대비하는 5줄 vs 50줄은 바로 그 **감독 뼈대**에 대한 것이다. 다른 언어에는 프레임워크(Akka, Go 의 supervisor 라이브러리들)를 얹거나 직접 짜야 하고, 어느 쪽도 언어/런타임에 통합되어 있지 않다. **비교할 등가 뼈대가 존재하지 않는다는 사실 자체가 논증이다.** "Erlang 5줄 vs 직접 짜는 ~50줄(그마저 불완전)"의 대비. 이건 문법 설탕의 차이가 아니라, 실패 복구의 뼈대가 런타임의 일급 개념이냐 아니냐의 차이다.

## 스코어카드: 이제 진짜 차이가 보인다

1편에서 소개하고 2편에서 동시성 행을 채운 관통 스코어카드로 돌아가자. 이번 글의 두 행을 채운다.

| 특성 | Erlang/BEAM | Go | Java (Loom) | C++ |
|---|---|---|---|---|
| 동시성 | ✅ 수백만 프로세스 | ✅ goroutine | ✅ 가상 스레드 | ⚠️ OS 스레드 한계 |
| 격리성 | ✅ share-nothing | ❌ 공유 메모리 | ❌ 공유 메모리 | ❌ 공유 메모리 |
| 감독성 | ✅ OTP 감독 트리 | 직접 구현 | 직접 구현(Akka 별도) | 직접 구현 |

2편에서 동시성 행은 사실상 무승부였다. 셋 다 ✅ 였다. 하지만 격리성과 감독성 행을 채우고 나니 표가 다르게 읽힌다. 격리성에서 BEAM 만 ✅ 이고 나머지는 전부 ❌(공유 메모리)다. 감독성에서 BEAM 만 언어에 내장된 ✅ 이고, 나머지는 "직접 구현" — Java 는 Akka 같은 별도 프레임워크가 필요하다.

이것이 이 시리즈의 핵심 서사다. **동시성은 막상막하다. 정직하게 인정한다. 하지만 격리성과 감독성에서 진짜 차이가 벌어진다.** 그리고 이 두 축은 "let it crash"라는 하나의 철학으로 묶인다 — 격리가 있어 안전하게 죽을 수 있고, 감독이 있어 자동으로 복구된다. 실패를 예외가 아니라 정상 흐름의 일부로 다루는 시스템. 그게 Erlang 이 통신 교환기와 WhatsApp 을 몇 년씩 재부팅 없이 굴린 비결이다.

그렇다면 자연스러운 반문이 남는다. "BEAM 밖에서, 즉 Kubernetes 나 Akka, Tokio, Loom 같은 현대적 도구로 같은 특성을 얻을 수는 없나?" 다음 글에서 이 도구들을 하나씩 살펴보며, 어디까지 따라오고 어디서 갈라지는지를 따진다.
