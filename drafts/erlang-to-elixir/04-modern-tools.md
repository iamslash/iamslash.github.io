# BEAM 밖에서 같은 특성 좇기

이 시리즈의 4번째 글이며, 앞의 세 편에서 Erlang/BEAM 이 왜 통신 산업에서 성공했는지, 그리고 동시성·격리성·감독성이라는 세 축에서 Go/Java/C++ 와 어떻게 비교되는지를 다뤘다. 지금까지는 줄곧 BEAM 쪽에서 바라본 비교였다. 이번 글부터는 시선을 반대로 돌린다. BEAM 밖의 현대적인 도구들은 같은 문제 — 수많은 동시 작업, 그중 하나가 죽어도 전체가 무너지지 않는 격리, 죽은 것을 자동으로 되살리는 감독 — 를 어떻게 풀고 있을까. 액터 모델을 흉내 낸 라이브러리도 있고, 언어 런타임 자체에 동시성을 박아 넣은 경우도 있고, 아예 인프라 레벨로 문제를 밀어 올린 경우도 있다. 이 글의 목적은 그것들을 정직하게 저울질하는 것이다. 어디까지 따라왔고, 어디서 여전히 다른 층에 의존하는지.

## 액터 모델의 확산

BEAM 이 유일하게 액터 비슷한 것을 가진 런타임은 아니다. 액터 모델 자체는 1970년대 Carl Hewitt 의 이론에서 나왔고, 여러 생태계가 각자의 방식으로 이를 구현해 왔다.

### Akka/Pekko — 가장 근접한 대안, 그러나 라이브러리

JVM 위에서 Akka 는 OTP 와 가장 닮은 것을 제공한다. 액터가 있고, 메일박스가 있고, 감독 전략(supervision strategy)이 있고, 재시작 시 상태를 어떻게 다룰지 정할 수 있다. 다만 API 세대에 따라 방식이 다르다는 점은 짚고 넘어가자. 예전 Akka Classic 에서는 액터 클래스에 `preRestart`/`postRestart` 메서드를 둬서 재시작 직전 정리와 직후 초기화를 처리했다. 반면 아래 예제가 쓰는 Akka Typed 에서는 `PreRestart` 시그널을 받아 정리를 하고, 재시작 후의 초기화는 `Behaviors.setup` 블록이나 생성자에서 다시 이뤄진다.

```java
public class CounterActor extends AbstractBehavior<CounterActor.Command> {
    // 부모 액터가 감독 전략을 지정한다: 예외 시 재시작할지, 멈출지, 무시할지
    static Behavior<Command> create() {
        return Behaviors.supervise(Behaviors.setup(CounterActor::new))
                .onFailure(RuntimeException.class, SupervisorStrategy.restart());
    }
}
```

이 코드만 보면 Erlang supervisor 의 `restart => permanent` 와 거의 같은 그림이 그려진다. 실제로 Akka 는 "OTP 를 JVM 에 이식하려는" 의도로 출발했고, 감독 트리·`let it crash` 철학·위치 투명성(location transparency, 액터가 같은 서버에 있든 다른 서버에 있든 똑같은 참조로 호출할 수 있다는 성질)까지 개념적으로 이어받았다. 이 시리즈의 논조대로 정직하게 인정하자면, 세 축 중 감독성에서 Akka 는 Go/C++ 진영과는 확실히 다른 급이다. 라이브러리 차원에서나마 "감독 트리"라는 어휘 자체가 존재한다.

다만 두 가지는 짚어야 한다. 하나는 라이선스 문제다. Akka 는 2022년 Business Source License(BSL) 로 전환했고, 그 결과 커뮤니티는 Apache 2.0 라이선스를 유지하는 포크인 **Apache Pekko** 를 만들었다. 지금 신규 프로젝트에서 완전히 오픈소스인 Akka 계열 액터를 쓰려면 사실상 Pekko 를 선택하게 된다. 생태계 자체가 라이선스 때문에 갈라진 셈이다.

더 근본적인 두번째 지점은, Akka/Pekko 가 **JVM 이라는 공유 메모리 런타임 위에 얹힌 라이브러리**라는 사실이다. BEAM 에서 프로세스 격리는 VM(런타임) 이 강제한다 — 프로세스마다 독립된 힙을 갖고, 한 프로세스의 코드가 다른 프로세스의 가변 힙을 직접 읽거나 수정할 수 없다. 여기서 정확히 해 둘 것은, 이게 하드웨어가 보장하는 게 아니라 런타임 수준의 보장이라는 점이다(BEAM 프로세스들은 같은 OS 프로세스 안에서 돌기 때문에 물리 메모리 자체는 공유하며, 큰 불변 바이너리나 ETS 테이블처럼 의도적으로 공유되는 예외도 있다). Akka 의 액터에는 이런 런타임 수준의 보장이 없다. 액터 A 의 핸들러 코드가 실수로 공유 가변 객체의 참조를 캡처해서 다른 스레드와 나눠 쓰면, data race 는 여전히 일어난다. Akka 는 "액터 안에서는 상태를 스레드 안전하게 다룰 수 있다"는 **규율(discipline)** 을 제공하지, "다를 수 없다"는 **보장(guarantee)** 을 제공하지 않는다. 이 차이는 작지 않다. BEAM 의 격리는 런타임이 강제하는 보장이고, Akka 의 격리는 팀이 지켜야 하는 코딩 컨벤션에 가깝다.

### Microsoft Orleans — 가상 액터

.NET 진영의 Orleans 는 조금 다른 각도로 접근한다. "가상 액터(virtual actor)" 라는 개념을 도입해서, 개발자는 액터(Orleans 용어로는 grain — Orleans 에서 액터 하나를 가리키는 단위 이름이다)의 생명주기를 신경 쓰지 않아도 된다. 존재하지 않는 grain 을 호출하면 런타임이 알아서 활성화하고, 오래 안 쓰면 알아서 비활성화한다.

```csharp
public interface ICounterGrain : IGrainWithIntegerKey
{
    Task Increment();
    Task<int> GetValue();
}
```

이건 감독성 문제를 다른 방식으로 풀어낸 것에 가깝다. "죽으면 재시작" 이 아니라 "애초에 항상 존재하는 것처럼 다룬다." 분산 상태 관리(특히 클라우드 오토스케일링 환경에서 액터를 어느 노드에 둘지)에는 강점이 있지만, Erlang 의 `let it crash` 와는 철학이 다르다. Orleans 는 실패를 감추는 쪽에 가깝고, OTP 는 실패를 드러내고 빠르게 재시작하는 쪽이다.

### Proto.Actor — 다언어 액터 프레임워크

Proto.Actor 는 Go/C#/Java/Kotlin 등 여러 언어에서 동일한 액터 모델을 쓸 수 있게 만든 크로스 플랫폼 라이브러리다. 액터, 메일박스, 감독까지 Akka 와 유사한 구조를 제공하지만 역시 호스트 언어의 런타임(가비지 컬렉터, 스레드 모델)에 얹혀 돌아간다는 근본적인 제약은 같다.

## CSP: 공유 없는 통신, 그러나 격리는 별개

액터 모델과 자매뻘인 접근이 CSP(Communicating Sequential Processes) 다. Go 의 고루틴과 채널이 대표적이다. 2편에서 이미 봤듯, Go 는 동시성 스폰 비용에서 BEAM 과 막상막하다. `go func() { ... }()` 로 goroutine 을 뿌리고 채널로 메시지를 주고받는 패턴은 실제로 액터 패턴을 손으로 구현한 것과 크게 다르지 않다.

```go
// 구조적 동시성: errgroup 으로 여러 goroutine 을 묶는다.
// WithContext 는 하나가 실패하면 ctx 에 취소 신호를 보내지만,
// 각 goroutine 이 ctx.Done() 을 확인해야 실제로 멈춘다 — 그리고 "재시작"은 없다
g, ctx := errgroup.WithContext(context.Background())
for _, url := range urls {
    url := url
    g.Go(func() error {
        return fetch(ctx, url)
    })
}
if err := g.Wait(); err != nil {
    log.Println("작업 중 하나 실패:", err) // 여기서부터는 직접 판단
}
```

구조적 동시성(structured concurrency)은 최근 여러 언어가 채택하는 패턴으로, "부모가 자식들의 생명주기를 명시적으로 소유한다"는 규율을 강제해서 goroutine leak 을 줄여준다. 다만 위 예제의 `errgroup` 은 Go 언어의 표준 기능이 아니라 `golang.org/x/sync/errgroup` 이라는 준표준 패키지라는 점을 짚어 두자. 그리고 `WithContext` 는 자식 하나가 실패하면 공유 `ctx` 에 취소 신호를 보낼 뿐, 그 신호를 받은 각 goroutine 이 `ctx.Done()` 이나 context 를 인식하는 I/O 를 스스로 확인해야 비로소 실제로 멈춘다 — 신호를 무시하고 도는 goroutine 은 계속 돈다. 그래도 이건 유의미한 발전이고, 감독의 아주 초보적인 형태 — "부모가 자식의 완료/실패를 안다" — 를 제공한다.

하지만 3편에서 짚었듯 격리와 감독은 여전히 직접 조립해야 하는 몫이다. goroutine 내부에서 panic 이 발생했는데 `recover()` 로 잡지 않으면 프로그램 전체가 죽는다. 공유 메모리이기 때문에 두 goroutine 이 같은 슬라이스나 맵을 잠금 없이 건드리면 data race 가 난다(`go run -race` 로 잡아낼 수 있지만, 애초에 안 나게 만드는 언어 차원의 보장은 없다). 재시작 정책, 백오프, 최대 재시도 횟수 같은 것도 `errgroup` 이 알아서 해주지 않는다. Go 는 **동시성을 표현하는 문법**을 훌륭하게 제공하지만, **격리를 강제하는 런타임**도 **감독을 표준화하는 프레임워크**도 언어 자체에는 없다. Kubernetes 나 supervisor 프로세스 같은 바깥층이 그 자리를 메운다.

## 런타임 레벨의 동시성 추격: Loom 과 Tokio

동시성 ergonomics 만 놓고 보면, 최근 몇 년 사이 격차는 눈에 띄게 좁혀졌다.

Java 는 Project Loom(Java 21 에서 정식 릴리스)으로 가상 스레드를 언어 런타임에 넣었다. 2편에서 봤듯 `Executors.newVirtualThreadPerTaskExecutor()` 로 수백만 개의 동시 작업을 띄울 수 있다. 이 가상 스레드들은 플랫폼 스레드 하나에 몰아넣는 게 아니라, 소수의 캐리어(carrier, 실제 OS 플랫폼 스레드) 풀 위에 M:N 으로 스케줄된다. 어떤 가상 스레드가 I/O 로 블로킹되면 캐리어에서 잠시 내려오고, 그 캐리어는 그동안 다른 가상 스레드를 실행한다 — 그래서 수백만 개가 소수의 OS 스레드만으로 굴러간다. 이건 진짜다 — 예전에는 "Java 에서 대량 동시성을 하려면 콜백 지옥이나 리액티브 스트림을 써야 한다"고 했지만, Loom 이후로는 그냥 블로킹 스타일 코드를 수백만 번 띄우면 된다. 동시성 표현력에서 BEAM 을 거의 따라잡았다고 인정하는 게 정직하다.

Rust 는 async/await 문법에 Tokio 같은 런타임을 얹어서 비슷한 결과를 낸다.

```rust
// Tokio: async 태스크는 가볍고, 수십만 개를 동시에 띄울 수 있다
let mut handles = Vec::new();
for i in 0..1_000_000 {
    handles.push(tokio::spawn(async move {
        // 작업 수행
    }));
}
for h in handles { let _ = h.await; }
```

Rust 의 소유권 시스템은 컴파일 타임에 data race 를 상당 부분 막아준다는 점에서 오히려 C++ 보다 격리에 유리한 면이 있다. `Send`/`Sync` 트레이트(각각 "이 값을 다른 스레드로 넘겨도 안전한가", "여러 스레드가 동시에 참조해도 안전한가"를 나타내는 Rust 의 표식이다)를 이용해, 스레드 경계를 넘는 값의 안전성을 컴파일러가 검증하게 만든다. 하지만 이것도 "공유하지 않아도 되게 설계된 타입" 을 강제할 뿐, BEAM 처럼 프로세스마다 힙을 런타임 수준에서 분리해 두는 것과는 다르다. 그리고 `panic!` 이 발생한 태스크를 감독하고 재시작하는 정책은 Tokio 자체에는 없다 — `tokio::spawn` 이 반환하는 `JoinHandle`(비동기 작업이 끝났을 때 그 완료 결과나 실패를 돌려받는 손잡이다) 이 에러를 담아 오면, 그걸 보고 재시작할지 말지는 여전히 애플리케이션 코드의 몫이다.

정리하면: 동시성이라는 축에서는 Go, Loom, Rust/Tokio 모두 BEAM 과 견줄 만한 표현력을 갖췄다. 이건 허수아비를 세우지 않고 인정해야 할 사실이다. 격차가 벌어지는 곳은 격리와 감독 쪽이다.

## 인프라 레벨의 감독: Kubernetes

언어/런타임 레벨에서 감독이 빠진 자리는 결국 인프라가 채워왔다. Kubernetes 의 liveness/readiness probe 와 `restartPolicy` 는 기능적으로 "감독 트리"와 놀랍도록 닮았다.

```yaml
livenessProbe:
  httpGet:
    path: /healthz
    port: 8080
  periodSeconds: 10
  failureThreshold: 3
restartPolicy: Always
```

컨테이너가 liveness probe 에 연속으로 실패하면 kubelet 이 그 컨테이너를 죽이고 다시 띄운다. 여기서 두 종류의 probe 를 구분해 둘 필요가 있다. liveness 실패는 방금처럼 컨테이너 재시작을 유발하지만, readiness 실패는 재시작이 아니라 해당 Pod 를 Service 엔드포인트 목록에서 잠시 빼내 트래픽만 끊는다 — 컨테이너 자체는 그대로 살아 있다. 어쨌든 liveness 재시작은 Erlang supervisor 가 자식 프로세스의 종료를 감지하고 `restart => permanent` 정책에 따라 재시작하는 것과 개념적으로 동일한 패턴이다. Deployment 컨트롤러가 원하는 replica 수를 유지하는 것도 `one_for_one` supervisor 가 자식 개수를 유지하는 것과 닮았다. 이 유사성은 우연이 아니다 — 둘 다 "선언적으로 원하는 상태를 명시하고, 감시자가 실제 상태를 그에 맞춰 되돌린다"는 같은 제어 이론적 아이디어를 구현한 것이다. Kubernetes 를 "컨테이너를 위한 감독 트리"라고 부르는 건 과장이 아니다.

다만 감독하는 대상, 즉 fault domain 자체가 다르다. Kubernetes 는 container/Pod 단위로 감독하고, OTP 는 하나의 VM 안에서 도는 process 단위로 감독한다. 그래서 입자의 크기(granularity)가 전혀 다르다. Erlang 의 supervisor 는 프로세스 하나, 즉 어떤 사용자의 대화 세션 하나, 어떤 연결 하나 단위로 감독을 건다. 수백만 개의 개별 프로세스 각각에 재시작 정책을 걸 수 있고, 그 재시작은 밀리초 단위로 끝난다. Kubernetes 의 재시작 단위는 컨테이너/파드다. 파드 안에는 보통 하나의 애플리케이션 프로세스가 통째로 들어 있고, 그 프로세스 내부에서 처리 중이던 수천 개의 개별 요청/세션은 파드가 재시작되는 순간 전부 함께 죽는다. "사용자 한 명의 대화 세션이 이상 상태에 빠졌으니 그 세션 프로세스 하나만 재시작한다"는 세밀함은 Kubernetes 층에서는 표현할 수 없다 — 그건 애플리케이션 내부의 문제이기 때문이다. 인프라 감독과 프로세스 감독은 층이 다르고, 둘 다 필요하지만 서로 대체하지 못한다.

## 핵심 논지: 통합된 런타임 vs 조립된 스택

여기까지 훑어본 도구들을 한 문장으로 요약하면 이렇다 — BEAM 이 **하나의 런타임 안에서 통합 제공**하는 것(동시성, 격리, 감독, 그리고 아직 다루지 않았지만 분산까지)을, 현대 스택은 **여러 층에 걸쳐 조립**한다.

- 동시성은 언어/런타임 레벨(Go 고루틴, Java 가상 스레드, Rust async)에서 해결한다.
- 격리는 프로그래밍 컨벤션(불변 데이터 선호, `Send`/`Sync` 같은 타입 시스템 규율)이나 별도 프로세스/컨테이너 경계로 흉내 낸다.
- 감독은 애플리케이션 레벨 라이브러리(Akka/Pekko)나 인프라 레벨 오케스트레이터(Kubernetes)로 밀어 올린다.
- 분산(다음 편 이후에 더 다루겠지만)은 별도의 서비스 메시(service mesh, 서비스 간 통신을 애플리케이션 코드 밖의 proxy 계층에서 관리하는 인프라), 메시지 브로커, 서비스 디스커버리 도구가 담당한다.

이 조립에는 나름의 장점이 있다. 각 층을 독립적으로 교체하고 전문화할 수 있고, 이미 그 생태계에 익숙한 팀이라면 각 도구를 따로 배울 필요 없이 조합할 수 있다. 하지만 대가도 명확하다. 층과 층 사이의 경계에서 의미가 새기 쉽다. 애플리케이션이 "이 요청 하나만 재시도하고 싶다"고 생각할 때, Kubernetes 는 파드 전체 재시작만 알고, 언어 런타임은 goroutine/가상 스레드 하나의 예외 전파만 안다. 그 사이 어딘가에서 사람이 직접 접착제 코드를 짜야 한다. 그리고 각 층은 서로 다른 팀, 다른 설정 파일, 다른 장애 모드를 갖고 있어서 운영 복잡도가 층의 수만큼 곱해진다.

가장 뉘앙스가 중요한 지점은 이거다. Go 와 Loom 은 동시성이라는 축에서는 정말로 BEAM 을 따라잡았다. 하지만 그 동시성 위에 격리(공유 메모리이므로 data race 는 언제나 잠재적으로 가능하다)와 감독(재시작 정책이 언어에 내장돼 있지 않다)까지 얹어주지는 못한다. 동시성만으로는 세 축 중 하나일 뿐이다. 나머지 둘은 여전히 사람이 그 위에 손으로 쌓아야 하는 별개의 작업이다.

## 스코어카드 완성

1편부터 채워온 표를 여기서 마무리한다.

| 특성 | Erlang/BEAM | Go | Java (Loom) | C++ |
|---|---|---|---|---|
| 동시성 | ✅ 수백만 프로세스 | ✅ goroutine | ✅ 가상 스레드 | ⚠️ OS 스레드 한계 |
| 격리성 | ✅ share-nothing | ❌ 공유 메모리 | ❌ 공유 메모리 | ❌ 공유 메모리 |
| 감독성 | ✅ OTP 감독 트리 | 직접 구현 | 직접 구현(Akka 별도) | 직접 구현 |

표에는 들어가지 않지만 이번 글에서 다룬 도구들을 곁들이면 그림이 더 선명해진다. Akka/Pekko 는 Java 열의 "감독성: 직접 구현" 을 "라이브러리로 흉내" 수준까지는 끌어올리지만, 그 감독은 여전히 공유 메모리 JVM 위에서 동작하는 규율이지 격리 자체를 바꾸지는 못한다. Kubernetes 는 모든 열 바깥에서 파드 단위의 거친 감독을 얹어주지만, 프로세스 단위의 세밀한 재시작은 대체하지 못한다. Rust 는 동시성 행에서 Go/Loom 과 같은 등급을 받을 자격이 있고, 격리 행에서는 타입 시스템 덕에 C++ 보다는 낫지만 Erlang 의 런타임 수준 힙 분리에는 못 미친다.

결국 동시성은 정말로 막상막하다 — 이건 인정할수록 논증이 강해진다. 진짜 차이는 격리성과 감독성에서 벌어지고, 그 차이를 메우기 위해 현대 스택은 언어 런타임 하나가 아니라 라이브러리(Akka), 타입 시스템(Rust), 오케스트레이터(Kubernetes)까지 여러 층을 동원해야 한다. BEAM 은 그 여러 층이 할 일을 하나의 런타임 설계 안에 접어 넣었다. 다음 편에서는 이 통합이 실제로 Elixir 를 선택할 이유가 되는지 — 그리고 언제는 이유가 안 되는지 — 를 정직하게 따져본다.
